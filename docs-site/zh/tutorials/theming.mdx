当前 Record/Reports 契约不提供 `--theme`，也不装载任意主题文件。`show`、本机 `view` 与静态 export 消费同一份 `ReportExecution`；网页外壳由当前 NiceEval exporter 的内建 runtime、基础样式和字体完整提供。

```sh
niceeval view --latest
niceeval view --latest --report ./reports/site.ts --out ./report-site
```

## Report 可以控制什么

Report 通过结构化 `ReportPageModel` 决定标题、内容、表格、图表数据、状态提示与文字替代。它可以组织信息和选择合适的内建组件，但不能返回 script、CSS、font、worker、WASM、网络 URL 或本地文件路径。

颜色和交互只能增强已有语义。partial、unavailable、unsupported 与 invalid 必须同时有文字或表格表达，不能只靠颜色区分。

## 为什么不纳入任意主题注入

静态报告的核心承诺是自包含、可预检和断网可用。如果 Report 或 CLI 能临时装载任意 CSS/脚本/字体，export 就必须重新处理代码执行、资源闭包、网络 URL、路径逃逸和版本漂移；这会把“分享一份固定结果”变成另一套插件与构建系统。

固定宿主让导出器可以在写文件前穷尽全部资产，保证 manifest 与普通文件一一对应，也保证本机页面和静态站不会因外部主题包变化而产生不同解释。

## 需要品牌化怎么办

当前选择是先把品牌化作为未来宿主能力设计，而不是让用户注入任意资源。新增能力必须仍满足：

- 只改变外观，不改变 Calculation、分母或状态；
- 资源集合能在 export 前穷尽验证；
- 不读取网络或任意用户路径；
- 同一 `ReportExecution` 的终端文字与网页语义一致；
- 不破坏静态站的断网与内容安全边界。

在这套契约落地前，需要完全自定义品牌页面的产品可以消费 Report 的结构化结果，在自己的应用边界内实现宿主；NiceEval 的静态 export 仍保持固定、安全的内建外壳。
