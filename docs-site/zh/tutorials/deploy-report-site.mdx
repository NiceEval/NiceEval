先用明确的 `niceeval view --out` 或 `niceeval view --run <id> --out` 生成报告站，再部署该目录。报告站已经含有页面、宿主数据、下载项、内建精确 runtime 和 manifest；托管平台无需读取源 Record，也无需执行 NiceEval。

```sh
npx niceeval view --experiment checkout \
  --out ./report-site \
  --no-open
```

需要发布特定运行时，使用 receipt 中的 Run ID：

```sh
npx niceeval view --run 01J9ZK3M6P4T7V9X2C5N8QW0RY \
  --out ./report-site \
  --no-open
```

## CI 流程

一个静态托管流程通常有三步：

1. 运行 Experiment，并保留最后的 receipt。
2. 用当前项目结果或明确 Run 运行 `view --out`。
3. 将输出目录交给静态托管服务。

GitHub Actions 的构建任务示例：

```yaml
- name: 生成报告站
  run: npx niceeval view --experiment checkout --out ./report-site --no-open

- name: 上传静态站点目录
  uses: actions/upload-pages-artifact@v3
  with:
    path: ./report-site
```

后续部署任务使用托管平台提供的发布步骤。无论使用 GitHub Pages、对象存储或其它静态托管服务，发布目标都是 `./report-site`，不是源 Record。

## 发布前检查

导出会列出所有页面、参数化页面、下载项与内建 runtime 文件，并写入 `StaticAssetManifest`。导出失败时不会发布半完成目录。`--out` 必须指向不存在的目录；更新内容时使用新的输出目录。

部署后用浏览器检查首页、参数化页面和下载项。站点在断网条件下也应正常显示，因为所有引用都是目录内的相对路径。

## 更新站点

每次需要更新内容时，重新选择 Sample，导出到新的目录，再部署该目录。已发布目录表示那次导出时的固定 `ReportExecution`；它不会随着之后的 Record 编辑而变化。

有关选择范围和导出内容，请阅读[发布静态报告](/zh/tutorials/publish-report)。
