当评估任务要求 Agent执行 `docker build`、`docker run`或 `docker compose`时，先按任务的信任边界
选择 Docker access：

| 模式 | 什么时候用 | 启动成本 | 安全边界 |
| --- | --- | --- | --- |
| Docker socket | 可信 Agent、个人开发机、已有 daemon，优先启动速度 | 最低，共用已有 daemon | Agent拥有该 daemon的完整控制权；rootful socket通常等价宿主 root |
| Raw privileged DinD | 一次性 VM或专用 runner，需要独立 image、network和 cache | 每个 Sandbox启动 inner daemon | outer container是 raw privileged，不是安全隔离方案 |
| Managed rootless DinD | 不可信 Agent、共享宿主、并发评估、需要资源准入和强杀恢复 | 最高，需要宿主 profile | privileged限制在受管 rootless user namespace或专用 VM，并有 watchdog与容量契约 |

三种模式都要求镜像预装 Docker CLI。两种 DinD模式还要求镜像安装 Docker daemon，并用 root
entrypoint启动它。NiceEval负责宿主侧布线和 `docker info`探活，不会向任意镜像动态安装 Docker。

## 方案一：直接挂 Docker socket

先准备只有 CLI、Node和评估工具的镜像：

```dockerfile title="sandbox/Dockerfile"
FROM docker:29-cli

RUN apk add --no-cache ca-certificates git nodejs npm python3 \
  && addgroup -g 1000 node \
  && adduser -D -u 1000 -G node node
```

在 Experiment里显式填写宿主 Unix socket。NiceEval不会从 `DOCKER_HOST`或 Docker context猜这个
路径：

```ts title="experiments/docker-socket.ts"
import { defineExperiment } from "niceeval";
import { codexAgent } from "niceeval/adapter";
import { dockerSandbox } from "niceeval/sandbox";

export default defineExperiment({
  agent: codexAgent(),
  model: "gpt-5.4",
  sandbox: dockerSandbox({
    source: {
      type: "dockerfile",
      context: new URL("../sandbox/", import.meta.url),
    },
    user: "node",
    dockerAccess: {
      mode: "socket",
      socketPath: "/var/run/docker.sock",
    },
  }),
});
```

NiceEval会解析 symlink、确认最终目标是 Unix socket，把它挂到 Sandbox内固定的
`/var/run/docker.sock`，设置 `DOCKER_HOST`，并按 socket的数值 GID给 `node`添加补充组。随后默认以
Sandbox用户执行 `docker info`；CLI缺失或用户无法访问 socket时，Sandbox创建失败。

<Warning>
  这不是隔离方案。Agent可以通过 socket创建 privileged容器、挂宿主目录，并操作同一 daemon上的
  其它容器、image、volume和 network。不要给不可信 Agent挂 rootful宿主 socket。
</Warning>

## 方案二：Docker-in-Docker

DinD让每个外层 Sandbox拥有自己的 inner daemon。先创建镜像：

```dockerfile title="sandbox/Dockerfile"
FROM docker:29-dind

RUN apk add --no-cache ca-certificates git nodejs npm python3 \
  && addgroup -g 1000 node \
  && adduser -D -u 1000 -G node node

ENV DOCKER_HOST=unix:///var/run/docker.sock
ENV DOCKER_TLS_CERTDIR=""
COPY --chmod=755 niceeval-dind-entrypoint.sh /usr/local/bin/niceeval-dind-entrypoint
ENTRYPOINT ["niceeval-dind-entrypoint"]
```

生产评估应把 `FROM`钉到审核过的 digest，并把被测 Agent需要的固定 CLI烘焙进镜像。

```sh title="sandbox/niceeval-dind-entrypoint.sh"
#!/bin/sh
set -eu

dockerd-entrypoint.sh dockerd --host=unix:///var/run/docker.sock >/tmp/dockerd.log 2>&1 &
dockerd_pid=$!

attempt=0
until docker info >/dev/null 2>&1; do
  attempt=$((attempt + 1))
  if ! kill -0 "$dockerd_pid" 2>/dev/null || [ "$attempt" -ge 120 ]; then
    cat /tmp/dockerd.log >&2
    exit 1
  fi
  sleep 0.25
done

chown root:node /var/run/docker.sock
chmod 660 /var/run/docker.sock
exec "$@"
```

### 为什么还需要 NiceEval entrypoint

Docker官方的 `docker:<version>-dind`镜像已经提供 `dockerd-entrypoint.sh`，NiceEval没有重新实现
daemon的 iptables、PID清理或 init逻辑。区别在于进程契约：官方示例让 `dockerd`作为容器前台进程；
NiceEval则必须把 Sandbox保活命令作为容器 `Cmd`传入。若直接保留官方 `ENTRYPOINT`，它收到以
`sh`开头的 NiceEval `Cmd`后会直接执行该命令，不会同时启动 `dockerd`。

因此这个薄包装只负责组合两套契约：在后台调用镜像内置的官方入口启动 daemon，等待
`docker info`可用并把 socket交给 Sandbox用户，然后 `exec "$@"`运行 NiceEval传入的前台命令。
调用中的显式 `dockerd`参数不能省略；如果只把 `--host`作为首个参数传给官方入口，它会进入默认
参数模式，并在关闭 TLS时额外监听未认证的 `tcp://0.0.0.0:2375`。这里显式传入完整 daemon命令，
保证 inner daemon只监听 Unix socket。参见 Docker的
[privileged DinD说明](https://docs.docker.com/engine/containers/run/#runtime-privilege-and-linux-capabilities)
和 [`dockerd-entrypoint.sh`官方源码](https://github.com/docker-library/docker/blob/master/dockerd-entrypoint.sh)。

最后的 `exec "$@"`不能省略。NiceEval会把自己的保活命令作为容器 `Cmd`传给镜像；entrypoint先
启动 inner `dockerd`，再执行这个 `Cmd`。inner daemon只监听 Unix socket，不要增加 TCP listener。

### Raw privileged DinD

在一次性 VM或专用 runner上，可以显式选择 raw privileged：

```ts title="experiments/dind-raw.ts"
import { defineExperiment } from "niceeval";
import { codexAgent } from "niceeval/adapter";
import { dockerSandbox } from "niceeval/sandbox";

export default defineExperiment({
  agent: codexAgent(),
  model: "gpt-5.4",
  sandbox: dockerSandbox({
    source: {
      type: "dockerfile",
      context: new URL("../sandbox/", import.meta.url),
    },
    user: "node",
    dockerAccess: {
      mode: "dind",
      isolation: "raw-privileged",
    },
  }),
});
```

必填的 `raw-privileged`字面量是风险授权。NiceEval不会把 raw模式描述成 rootless，也不会在失败时
自动改用 managed profile。

### Managed rootless DinD

共享宿主或不可信 Agent使用 managed模式。它在 inner daemon之外增加 profile attestation、单容器
资源限制、跨进程容量准入、独占外层网络和 watchdog恢复：

```ts title="experiments/dind-managed.ts"
import { defineExperiment } from "niceeval";
import { codexAgent } from "niceeval/adapter";
import { dockerSandbox } from "niceeval/sandbox";

const GiB = 1024 ** 3;
const MiB = 1024 ** 2;

export default defineExperiment({
  agent: codexAgent(),
  model: "gpt-5.4",
  maxConcurrency: 4,
  sandbox: dockerSandbox({
    source: {
      type: "dockerfile",
      context: new URL("../sandbox/", import.meta.url),
    },
    user: "node",
    dockerAccess: {
      mode: "dind",
      isolation: "managed-rootless",
      profile: "default",
    },
    resources: {
      cpus: 4,
      memoryBytes: 6 * GiB,
      pidsLimit: 2048,
      readOnlyRootfs: true,
      tmpfs: {
        "/var/lib/docker": { sizeBytes: 3 * GiB, mode: 0o711, executable: true },
        "/home/sandbox/workspace": {
          sizeBytes: 2 * GiB,
          mode: 0o755,
          uid: 1000,
          gid: 1000,
          executable: true,
        },
        "/home/node": { sizeBytes: 512 * MiB, mode: 0o700, uid: 1000, gid: 1000 },
        "/tmp": { sizeBytes: 1024 * MiB, mode: 0o1777 },
        "/run": { sizeBytes: 128 * MiB, mode: 0o755 },
      },
    },
  }),
});
```

profile缺失、拼错、attestation失败或容量不足时，NiceEval会在模型调用前失败，绝不降级成 raw
privileged。宿主部署完成后先检查 profile：

```bash
npx niceeval docker profile list
npx niceeval docker profile doctor default --smoke
npx niceeval exp dind-managed
```

`doctor --smoke`会在该 profile上启动一次 DinD容器，并实际运行内层
`docker run --rm alpine:3.20 true`。它证明 profile支持 nested Docker，但不会检查项目自己的
Dockerfile；项目镜像仍由默认 `docker info` readiness验证。

## 在 Eval里验证 Docker任务

三种模式对 Eval暴露相同的 Docker CLI用法：

```ts title="evals/docker-compose.eval.ts"
import { defineEval } from "niceeval";
import { commandSucceeded } from "niceeval/expect";

export default defineEval({
  description: "Agent can repair and start a Docker Compose project",
  async test(t) {
    await t.send("修复 Compose 项目，然后启动服务并确认健康检查通过。");

    t.check(
      await t.sandbox.runCommand("docker", ["run", "--rm", "alpine:3.20", "true"]),
      commandSucceeded(),
    );
  },
});
```

socket模式的命令操作显式选择的外层 daemon；两种 DinD模式操作 Sandbox内的 inner daemon。
`sandbox`也可以直接写在 `defineEval({ sandbox: ... })`里；多条 Eval共用配置时写在 Experiment上。
