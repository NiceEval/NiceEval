好的评估用例把「是否成功」拆成可解释的信号。[NiceEval](https://niceeval.com/) 允许你混合精确断言、语义 Judge、事件流检查和真实测试。

## 选择断言类型

| 目标 | 推荐机制 |
|---|---|
| 回复包含固定子串或命中正则 | `includes` |
| 结构化 JSON 完全匹配 | `equals` |
| 工具调用是否发生 | `t.calledTool` / `t.notCalledTool` |
| 输出是否语义正确 | `t.judge.*` |
| 代码是否工作 | `t.check(await t.sandbox.runCommand("npm", ["test"]), commandSucceeded())` |
| 成本是否可控 | `t.maxTokens` / `t.maxCost` |

## 值断言

```ts
import { includes, equals } from "niceeval/expect";

t.check(t.reply, includes("refund"));
t.check(turn.data, equals({ intent: "refund" }));
t.check(t.reply, includes(/order #\d+/));
```

`includes` 同时接受子串和正则。`matches` 只接受 Standard Schema / Zod schema，用于结构校验，不做正则匹配。值断言适合精确、稳定、低歧义的结果。

## 作用域断言

```ts
t.succeeded();
t.calledTool("search");
t.usedNoTools();
t.sandbox.fileChanged("src/app.ts");
t.check(await t.sandbox.runCommand("npm", ["test"]), commandSucceeded());
```

它们检查整次运行的事实，通常来自标准事件流或 Sandbox artifact。

## LLM-as-judge

```ts
t.judge.autoevals.factuality("Refunds are available within 30 days.", { on: t.reply }).atLeast(0.8);
t.judge.autoevals.closedQA("回答具体、礼貌，并且没有编造政策。", { on: t.reply }).atLeast(0.75);
```

Judge 适合语义质量，不适合替代所有确定性断言。能精确检查的地方优先精确检查。

## 一条断言不通过会怎样

链在断言上的词决定它的失败怎么向上传播。不链词就用 matcher 自带的严重度——`includes`、`calledTool` 这些默认是 gate，`t.judge.*` 默认是无线的 soft。

三个词的分工：

- `.gate(x)`：硬要求，分数低于 `x` 就 failed。省略 `x` 用 matcher 自身的及格线。
- `.atLeast(x)`：带通过线的 soft，低于线如实记 failed、判定不动，`--strict` 下升级成 gate。
- `.soft()`：不设线，纯记录一个分数，永不 failed。要设线用 `.atLeast(x)`。

`.atLeast` 的参数是分数线，不是调用次数。「至少调用两次」是匹配条件，写在 `t.calledTool("shell", { count: 2 })` 里。

## 走完三步也要记三分

`defineEval` 把一次运行折成一个「过」或「不过」。有些任务分步骤，走完三步比一步没走强得多——这类任务用 `defineScoreEval`，题内用给分 API 累加挣分，`niceeval show` / `view` 的默认报告读总分而不是通过率：

```ts
import { defineScoreEval } from "niceeval";
import { commandSucceeded, isTrue } from "niceeval/expect";

export default defineScoreEval({
  description: "安装并启动 DB-GPT",
  async test(t) {
    await t.send("把 DB-GPT 装起来并通过健康检查。");

    // 前置条件没过，后面步骤没意义：t.require 记硬失败并就地结束 test()
    await t.require(await t.sandbox.pathExists("db-gpt/README.md"), isTrue());

    t.sandbox.fileChanged("db-gpt/.env").points(1);
    // 值 1 分，而且没装依赖后面全白跑——挣分和硬前置可以是同一条
    await t.calledTool("shell", { input: { command: /pip install/ } })
      .points(1).gate().stopOnFailure();

    const health = await t.sandbox.runShell("curl -s localhost:5670/health");
    t.check(health, commandSucceeded()).points(1);
  },
});
```

- `.points(n)` 挂在任意断言后面：通过挣 `n` 分，不过挣 0。`t.judge.*` 这类连续打分断言按比例挣 `n × score`。
- 失败一个检查点只是少挣分，后面照跑。要「这步不成立就别往下跑了」，链 `.stopOnFailure()`。
- `t.score(label, n)` 用于自己算好条件和分数后直接累加，比如按代码行数分档给分。
- 计分是叠加制，从 0 往上挣，不声明满分：同一条评估用例的代码对每个实验是同一把尺子，模型 A 挣 3 分、模型 B 挣 1 分，结论不需要分母。
- 丢分不是失败：五步走完三步的 Attempt 是 `passed` 且挣 3 分。「做到几成」由分数回答，不借判定表达。
- `.points()` 与 `t.score` 只存在于 `defineScoreEval` 的 `t` 上。在 `defineEval` 里写是类型错误。
- 一个实验可以同时选中两种题型，报告分别给通过率和总分，两个读数不相加。

## 代码任务用测试评分

在 `.eval.ts` 里运行项目测试或临时探针：

```ts
import { commandSucceeded, includes } from "niceeval/expect";

const testResult = await t.sandbox.runCommand("npm", ["test"]);
t.check(testResult, commandSucceeded());

const src = await t.sandbox.runShell("find . -name '*.ts' -exec cat {} +");
t.check(src.stdout, includes(/z\.object\s*\(/));
```

判分标准本身是一份文件（隐藏测试、参考实现、跑测脚本）时，用 `loadText` 读它，改一字节就自动重跑这条评估用例，见[隐藏测试判分](/zh/tutorials/criteria-files)。

## 成本和效率

```ts
t.maxTokens(25_000);
t.maxCost(0.1);
```

对 coding agent 和长链路 agent 尤其有用，可以防止用大量重试或工具调用掩盖质量问题。

## 实用建议

- 先写 1–2 条 gate，保证任务底线。
- 再加 soft 分数比较质量。
- 复杂语义用 Judge，并给 Judge 明确的评分标准。
- coding-agent 结果尽量用真实测试验证。
- 把失败消息写清楚，方便从报告直接定位问题。
- CI 里加 `--strict`，让不达标的 soft 也拦住合并，见 [CI 集成](/zh/tutorials/ci-integration)。
