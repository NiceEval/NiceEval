NiceEval gives clear ownership to evaluation definitions, execution, current data, and reports. You define evals and Experiments, then the Runner executes them. Once the directory is quiescent, the current data lives in an editable Record. Viewing and sharing select a Sample from the Record, then form ReportInput.

```text
Eval and Experiment
        ↓
Runner
        ↓
Record
        ↓
Sample
        ↓
ReportInput
        ↓
show, view, or a static report site
```

## How an eval runs

An Eval defines a task, assertions, and needed Fixtures. An Experiment selects Evals and declares the Agent, model, concurrency, budget, and other run conditions. An Adapter connects the system under test; a Sandbox provides an isolated place to execute work.

The Runner creates one Run for every selected Experiment. A Run lists its expected slots, which define the denominator for that run. Each slot adopts at most one Attempt.

| Member | Meaning |
| --- | --- |
| `executed` | This Run actually executed the Attempt. |
| `carried` | The planner adopted an eligible existing Attempt. |
| `accepted` | An operator explicitly adopted an existing Attempt. |

An Attempt always retains the `origin` where it actually ran. Adoption does not copy business values; a later read sees the Attempt channel's current values.

## Record is current data

A Record lives in `.niceeval/record/`. People and tools read or write it only while the directory is quiescent. Business values such as Verdicts, Usage, assertions, and diagnostics live in named owner-local channels. That allows channel-level reading and user edits after the directory settles.

A Record does not retain an edit history. Validation of structure, paths, identities, and references exists only to detect contradictory data.

On read, an unknown or retired channel becomes `unsupported` only at that channel. A requested invalid channel fails; an uncollected `unavailable` channel is neither `unsupported` nor `invalid`. Durable collection completeness and current decoding completeness remain separate.

## Sample determines comparison scope

A viewer must select explicit Runs or use the named `latest` policy. A Sample builds its denominator from a Run's expected slots and marks each item `included`, `not-recorded`, `invalid`, or `excluded`.

That lets a Report honestly show missing members, core problems, and excluded items instead of counting only the slots that have values. See [Viewing Results](/tutorials/viewing-results) for selection rules.

## A Report receives ReportInput only

A Report runtime does not read disk. First, a Sample selects core data and its denominator. Then a ReportPlan lists facts, and the one composition adapter builds ReportInput. The Report computes and generates pages once from that input.

Every Page and Calculation declares its facts and completeness requirement. Partial values show their observed count and full denominator. `unavailable`, `unsupported`, and `invalid` remain visible.

## Deliver a Report

`niceeval show --latest` presents one `ReportExecution` in the terminal. `niceeval view --latest` presents the same data path locally in a browser. `niceeval view --latest --out <directory>` produces a self-contained static report site with the exact built-in runtime, every page, host data, downloads, and manifest. Replace `--latest` with one or more explicit `--run` values when needed.

A static report site opens offline. Its browser reads only the export directory, never the network or source Record. See [Publish a Static Report](/tutorials/publish-report) for publishing steps.
