# niceeval Setup Guide (Execution Steps for AI)

You are being asked to integrate [niceeval](https://github.com/CorrectRoadH/niceeval) into **the repository currently open here** (not niceeval's own source repository). Communicate with the user in the user's language. Do not improvise from stale API knowledge in model memory.

This file is responsible for exactly one thing: getting the package into the project. The integration workflow itself (exploring the project, confirming the path with the user, writing adapter / experiment / eval, getting the first run green) lives entirely in the bundled docs, which ship with the installed version — so this file contains no online doc links. Once installed, route everything through `node_modules/niceeval/INDEX.md`. The bundled docs are written in Chinese — read them anyway; they are the version-accurate source, and you still communicate with the user in the user's language. In particular, do not fetch niceeval.com or GitHub looking for an English version of a page: an English page for a different version is worse than a Chinese page for yours.

## First write a TODO: installing the package is only the first step

When the user says "install niceeval," the bar for done is **not** "added the dependency." It is **getting at least one real evaluation to run against the system under test in this repo, then inspecting it through the fixed public surface: an agent or script first uses `niceeval query discover`, then executes a fixed `runs.list` request with `niceeval query run --request <file>` to confirm the sealed Run is visible; a person uses `niceeval view`**. Before you begin, turn the checklist below into a checkable TODO and track it item by item — don't call it done the moment the package is installed:

- [ ] Install the package and run `init` (Steps 1–2)
- [ ] Read `node_modules/niceeval/INDEX.md` and pick the "onboarding from scratch" tutorial page; from this step on, do every step by following the bundled docs (Step 3)
- [ ] Explore this repo: identify the system's core user job; every plausible public endpoint and the distinct job each one serves; the chosen endpoint's protocol and request-response shape; and how its service or runtime is started, checked for readiness, configured, and stopped. Do not stop at the first route named `chat` or `completions` when the product has a more specific data, tool, or agent path
- [ ] Before writing code, record the discovered integration plan: target endpoint / protocol / request-response shape; startup, readiness, cleanup, and credential boundaries; available tracing / OTel; configuration variants; and integration tier. Respect an explicit plan or authorization already in the task. Ask the user only when a material decision is still missing; otherwise proceed with the documented plan.
- [ ] Turn the confirmed plan into four checkable chains before writing code: **protocol** (Experiment → Adapter → exact target request → response/events), **core job** (real user input → product-specific mode/data/tool → business assertion), **configuration** (every declared model/flag/static option → a named consumer → target runtime), and **lifecycle** (start → process-only credentials → readiness → cleanup). A hard-coded value, an already-running service, or a generic chat example does not satisfy the corresponding chain
- [ ] Write the adapter / experiment / eval trio from those chains. Hand-writing the adapter means reading the bundled write-send page **before** you start, not after it fails (see idea 5 below for what "finished" means there)
- [ ] Actually run it once against the real target and obtain a completed, non-`errored` Attempt, then inspect the final receipt's `createdRunIds`, opaque `publicationCutoff`, and `completion`. Use `niceeval query discover` before a fixed `runs.list` request with `niceeval query run --request <file>` to confirm a created Run is visible; use `niceeval view` when a person needs to read it. A receipt hands off one invocation and does not itself prove the integration task is complete. Inspect Assertion details or score instead of treating a completed Score Eval as perfect. A valid business mismatch may be `failed` and should be reported, not rewritten until green. When the system under test will not start, repair or start the runtime within the user's existing authorization and then continue the affected verification. Ask only when a real external condition is missing, such as a credential, database, or model service. A throwaway stub may prove wiring but is not a deliverable, and the summary must say the evaluation has not run against the real system.
- [ ] Follow the wrap-up self-check on the tutorial page, then ask the user whether they want to go to a deeper integration level

Until every item on the list is checked off, this task is not done.

## Step 0: Five core ideas

niceeval is a TypeScript evals library: you define "what a good result looks like" with a declarative API, then apply that to a coding agent, a deployed agent/service, or a pure function. These five ideas are all you need for the install decision:

1. Each of the three files owns exactly one concern: **adapter** (how to talk to the system under test), **experiment** (what to evaluate, with what config, how the real target is started and stopped, and how many runs), and **eval** (what input to send and what to assert). If the target is not already a separately managed deployment, the Experiment, Plugin, or Sandbox lifecycle must start it, inject credentials only into that process, wait for readiness, and clean it up even after failure. Manually starting a process before the run does not make the experiment reproducible.
2. niceeval **does not define any agent protocol**. If you are connecting to the user's own service, the adapter is just a normal HTTP request. URL and auth belong in adapter factory params, not in niceeval config.
3. CLI positional arguments are only for selecting "which evals to run" (by eval id prefix). Choosing "which agent/model to run against" must always be done via flags or experiment files. Do not overload positional args with URLs, agent names, or runtime config. If you set up a model comparison, first find out which models the system under test actually accepts (its `/models` endpoint, its config, its README, the model picker in its UI) and pin a real one per experiment file — two files pinned to the same value, including two files that both fall back to the same env-var default, is not a comparison. Cannot find out? Compare something else via `flags`, or ship a single baseline and say why.
4. **"It runs" is not the bar for "it is done."** The eval input must make the system under test do its differentiating core job (not answer meta-questions about itself, like "what are you / what can you do," or fall back to generic arithmetic/chat). For a data product, exercise a real configured table or data source through its data-specific mode; for a tool-using agent, require a real tool path. Trace that capability from the Eval input through Adapter request fields to a business assertion. Assertions must turn red when the system under test makes things up — never assert words that already appear in the input, because then echoing the question back is enough to pass. For open-ended replies do not pin a single exact phrase either (the wording changes every run and a correct answer goes red): use a regex covering equivalent wordings, a shape assertion, or the judge; save exact matches for deterministic results like a number or an id. Whenever possible, include one negative case against the same real capability: ask for a missing table, field, document, or tool result and assert that the target refuses to fabricate it. After the run, distinguish execution failure (`errored`) from a completed business result (`passed`, `failed`, or scored), then inspect the individual Assertions. The wrap-up checklist lives in the bundled tutorial page.
5. **An adapter that returns only the final answer is not finished.** Its job is to normalize the app's response into niceeval's standard event stream — tool calls become paired `operation.started` / `operation.finished` events, and multi-turn state hangs off `ctx.session`. Mapping just the final text still runs green, so nothing will tell you: it silently switches off the entire tool-assertion family (`calledTool` / `toolOrder` / `noFailedActions`) and every multi-turn case, leaving an evaluation that can only see the last paragraph. Standard response shapes (Chat Completions / Responses / AI SDK) need no mapping at all — one official converter call; anything else follows the mapping table on the bundled write-send page. This belongs in the first version of the adapter, not in a "we could add it later" list.

## Step 1: Confirm prerequisites

- The system under test can be built with any language or platform (iOS, Python service, anything else). niceeval only requires that this machine has Node and can run commands like `npx` or `pnpm exec`. The adapter/experiment/eval trio is written in TS, but the host repo does not need to be a TS/JS project. Do not stop just because the host project uses another language.
- The only real prerequisite is: this machine can install Node dependencies and run Node commands. Only if even that is confirmed impossible, tell the user honestly and stop for their decision.
- Check whether niceeval is already installed: look for `niceeval.config.ts`, an `evals/` directory, or a `niceeval` dependency in `package.json`. If it is already set up, skip installing, go straight to Step 3 and read the bundled docs, then add the missing files within the existing structure. Do not run `init` again.
- **Decide where the eval workspace lives — before detecting the package manager.** If the repo root's own `package.json` *is* the system under test (a JS/TS host project), install there as a devDependency. Otherwise — a Python or other-language host, or a repo that merely *contains* JS subprojects (`web/`, `frontend/`, a docs site) — create a fresh subdirectory (e.g. `niceeval/`) with its own new `package.json` and install there — and give that new `package.json` `"type": "module"` (`npm init -y` defaults to CommonJS; niceeval runs either way, but ESM keeps top-level `await` available in config and eval files). **Never install into an existing subproject's `package.json`**: its lockfile and toolchain belong to the system under test, and mixing the eval harness into them can break the niceeval CLI (older loaders in the host's `node_modules` cannot resolve it) and pull the host's own type errors into your typecheck.
- Detect the package manager **from the lockfile at the chosen install location only** (`pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`), and use it for every command afterward. A lockfile deep inside a host subproject does not decide for you. In a fresh subdirectory, use any package manager available on this machine; do not default to npm when a lockfile says otherwise.

## Step 2: Install

Installing is adding one dev dependency — cheap and reversible. You do not need to understand the whole project before doing it; exploring the project belongs to the post-install integration workflow:

```sh
<detected package manager> add -D niceeval
<detected package manager> exec niceeval init
```

`init` generates `niceeval.config.ts` and `evals/`, and adds a managed block to the project's `AGENTS.md` (or to `CLAUDE.md` when that is the only file present), reminding future coding agents to read the bundled docs. Do not delete or hand-edit the content inside the markers; re-run `init` after upgrading niceeval to refresh it.
