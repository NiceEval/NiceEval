# 行宽守护治不了长难句:agent 用换行把它绕过去了

**现象**:`docs/` 的可读性守护最初只有行宽一条(120 列,`pnpm test:docs`)。
它红灯时,写文档的 agent 的修法几乎全是在句子中间敲回车——行数变多、每行变短、绿灯,
渲染结果一个字没变,那句长难句原样躺在页面上。用户 2026-07-26 直接点破:
「我本质是想解决长难句的」,行宽只是当时能想到的代理指标。

**根因**:行宽量的是**单行**,而 Markdown 软换行不改变渲染。
凡是量在行上的规则,换行都是合法且零成本的逃逸口;要治的对象(句子)跨行存在,
守护却看不到跨行的那个整体。代理指标与目标之间只要有这么一条零成本的旁路,
优化压力就全跑到旁路上——这不是 agent 偷懒,是规则的可满足面写错了地方。

**修法**(2026-07-26,`scripts/docs-writing-lint.ts` + `docs/writing-rules.json`):
先把软换行拼回段落(`proseBlocks`),再在拼接后的文本上量两条新规则——
`sentenceLength` 单句 ≤ 140 字、`paragraphLength` 一段 ≤ 320 字(列表项各算一段)。
三处细节决定这条规则有没有用:

- **只有句末标点算断句**(`。！？!?`)。分号和破折号串起来的分句仍算同一句——
  长难句正是这么长起来的,把 `；` 当断句等于放过要治的对象(实测把它算上,>140 的命中从 659 掉到 236)。
- **段长不看句数,只看长度**。若写成「一段超过 N 句才查」,逃逸口就变成分号:
  一段 300 字只写一个句号即可过关。段长这条同时堵住「把长难句改成几句挤成一堵墙」。
- **行宽这条 2026-07-30 整条删掉**:先是留着改定位(只管排版与 diff 粒度),
  但它对写文档的 agent 仍是一条硬约束,产出里到处是句中的莫名换行——用户点破自己
  从来只要句长与段长两条。「拦一段一行、diff 整段重排」那个否决理由不成立:
  软换行怎么排是作者的排版自由,不值得用一条守护逼出违反语义的断行。
  落点:`scripts/docs-writing-lint.ts` 去掉 `visualWidth` 与 `lineWidth` 计数,
  `docs/writing-rules.json` / `docs/writing-baseline.json` 去掉该节。
- **删完立刻暴露出长度度量本身依赖折行**:段落是把软换行用空格拼回去再量的,
  折行越多凭空越长(一段 319 字拆成三行就变 321 判红)。同批把句长段长改成
  只数字不数空格(`proseLength`),这两条从此与怎么折行无关——这本来就是它们的本意。

阈值按实测分布定:单句 p50=52 / p90=122,140 落在 p93 附近(台账 654 处);
段落 p50=79 / p90=229,320 落在 p96 附近(台账 228 处)。都是尾巴不是主体,走既有台账棘轮清理。
「一段 5 句」那条旧的人读规矩同批删掉——它和 320 字上限打架,且从来没有守护。

**适用场景**:给文本/代码质量加机器守护时,先问「这条规则能不能被一个不改变输出的编辑满足」。
能,它就是代理指标,压力会全跑到那条旁路上。量的粒度必须等于要治的对象的粒度:
治句子就在句子上量,治段落就在段落上量,而不是在恰好好实现的那个单位(行)上量。
同一份检查里的另一条踩坑见 [`docs-line-width-cjk-token-exemption`](docs-line-width-cjk-token-exemption.md)。
