# 裁决:provider environment case + Agent Ensure 取代拓扑表与构建中间件

- **日期**:2026-07-30
- **裁决**:多容器环境采 PLAN-4(公共主 Sandbox + 各 provider 的完整 environment case,Docker 原生消费 Compose、只列黑名单);Agent 安装配方采 PLAN-4(Ensure 协议:检查→缺失时安装→复检,身份进指纹)。两案互为前提,一起改判。用户同场定调:sandbox 各 provider 把原生能力做到最大、不为跨 provider 兼容让步,每个 provider 像 adapter 一样单独成篇文档,不承诺 profile 跨 provider 迁移。
- **曾选方案**:多容器曾采 PLAN-1(规范化拓扑表 + compose 导入器,经一轮正反评审加固);安装配方曾采 PLAN-2(withCodingAgent / withNodeToolContract 中间件),PLAN-3(recipe DSL)曾留启用条件待命。
- **否决理由**:CASES.md 四道真实 TB 题证明规范化拓扑封闭字段集表达不了 named volume、一次性 init 容器、只读卷投影、坏 DNS 题面,导入器白名单会被 Compose 上百字段逼成追上游的解析器;逐题按需构建(数百环境产物)让「把 agent 烘进产物」强制生成题目×Agent 制品矩阵,构建期组合形态(工厂/中间件/recipe 三案皆然)解决不了。PLAN-3 的三个启用条件在 Ensure 下全部失去指向,改判为否决(幂等短路形态被吸收、InstallStep DSL 被拒)。
- **连带翻案**:多容器 PLAN-2 的两条否决理由被反转采纳(依赖 docker compose CLI 合法化为 provider 原生依赖;mainService 即主 Sandbox 由题目 Compose 现场构建+Ensure 后装),旧 DECISION「agent 沙箱镜像推导仍在边界外」遗留风险随之关闭。`composeEnvironment` 名字被 PLAN-2 与 PLAN-4 复用但语义不同(解析子集的 config 实体 vs 交给 materializer 的 source 声明),重裁时已在 DECISION 点名。
- **同批补裁的含糊点**:缺键=启动错误、缺能力=计划期 skipped(全 skipped 升级报错);SandboxSpec 双入口 `environments`(profile 表)与 `materializers`(source kind 注册),显式表项优先。
- **命名裁决(用户提出,两轮)**:第一轮:Environment 只留给 eval 侧的轴(`eval.environment`、profile 名、`environments` 表键);provider 侧实现实体一律 Sandbox 词族(`SandboxCase` / `SandboxGroupEntry`,key 正式名 `BuildKey` / `CaseKey`,run 记录字段 `sandboxBuilds`)。第二轮用户追问「为什么叫 e2bTemplateSandbox、E2BSandbox 为什么不行」,暴露我把旧构造函数一比一换皮的惯性——终裁:内置 case **不导出构造函数**,表值是 provider 原生纯数据判别键(`{ template }` / `{ build }` / `{ compose }`),E2B 词汇只剩 `e2bSandbox` 一个名字;保留函数的只有 eval 侧 `composeSandbox`(目录推导+brand)与 `defineSandboxCase`(携带行为)。理由:表值已在 provider 工厂括号里,前缀构造函数=把 provider 说两遍+白背导出名的兼容义务;Environment 口袋词问题与 `composeEnvironment` 同名撞车一并消解。
- **落点**:docs/design/multi-container-environments/ 与 docs/design/agent-install-recipe/ 的 DECISION、GOALS、PLAN 标注、LIMITS、CASES 同批重写;上一轮评审台账见 [multi-container-design-review-ledger](multi-container-design-review-ledger.md)。feature/docs-site 的契约搬迁(逐 provider 一篇文档、Ensure 进 agent 接入页、加速指南)是后续工作。
