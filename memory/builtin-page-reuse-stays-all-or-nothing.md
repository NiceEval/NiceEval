# 内建报告的复用面保持整站粒度：页级 override 与 page 具名导出都否决

**裁决（2026-07-25）**：`extends` 只有整站语义——页列表整体来自 base，外壳字段逐字段覆盖。想改内建页里的任何内容，就照抄那页并从此拥有它（`built-in.md` 里有 `standard` 全文）。`niceeval/report/built-in` 不为内建页开新的具名导出。

**起因**：下游项目（MemoryBench 一类的 benchmark 站）反馈「往内建页插一块内容就得整页抄下来，被改的那页从此不跟随内建演进」，把它列为四条 DX 缺口里最该修的一条，并建议提上游。

**曾选方案**：

1. **页级插槽 / override**——`extends` 之外声明「这一页的这个位置插什么」。当场否决：一开槽位，「这份报告会渲染什么」就有两份答案（给了走一套、不给走另一套），读报告文件的人必须去翻内建定义才知道槽在哪、默认填的什么。这条与组件树那次「组合组件不收结构子节点」是同一个判据。
2. **把内建四张 page 都具名导出**（先例是已有的 `standardAttemptPage`），让作者 `{...standardReportPage, content: <Col><Markdown/>{standardReportPage.content}</Col>}` ——引用而非复制，那块内建内容仍跟随演进。方案已写成提案交用户裁决。

**否决理由（用户 2026-07-25 裁决方案 2）**：只解决了「往外面加」，删不掉内建页里的任何一个组件；而一旦把删除也开出来，就是在给内建页发明选择器/槽位，等于绕回方案 1。**半套复用面比没有更糟**——它会让人以为内建页是可组装的，直到撞上删不掉才发现要整页重写。

**因此对下游的答复是**：#2 是有意关着的契约，不是遗漏。照抄一页的成本就是复制十几行公开组件。
