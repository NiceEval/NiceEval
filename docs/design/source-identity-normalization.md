# Eval 源码身份忽略注释与排版

## 要决定什么

Eval 源码闭包现在按文件原始字节计算内容哈希。只改注释、缩进或空行，也会让依赖这份源码的结果全部作废，只能付费重跑。
NiceEval-Eval 这类付费评测项目因此不敢整理注释，也不敢格式化 Eval 源码。

本设计决定：源码闭包里的 JavaScript / TypeScript 文件按什么规范化文本计算身份，怎样迁移已有结果，以及哪些情况仍按原始字节计算。

非目标：

- 不改变 loader 数据、criteria、private 文件与 transfer manifest 的哈希方式；它们是数据，格式变化可能就是语义变化。
- 不让语义等价的改写（改变量名、调整语句顺序）沿用结果。
- 不改变 Provider、installer 等 owner 声明的身份。

## 现状

- `runner/fingerprint.ts` 的 `sourceClosure` 从 Eval 入口出发，用正则匹配 `import` / `export ... from` 找相对模块，逐个读文件，按 `[相对路径, sha256(原始文本)]` 进入身份载荷。
- 这个正则也匹配被注释掉的 import，于是注释里的路径会被拉进闭包；`import()` 动态导入不被识别。
  这与 [Eval 架构](../feature/eval/architecture.md) 写的“静态相对 import 在所属 owner 内递归捕获”不符。
- Agent Judge、普通 Judge 与模拟用户的能力识别用正则扫描同一份原始文本（例如 `/\bagentJudge\s*\(/`），注释里提到这些名字也会触发。
- Eval 输入的身份域是 `fingerprintAlgorithm: 5` 与 `fingerprintCoverage: 3`，变更登记在 `runner/identity-domains.ts`，规则见 [身份域变更](../feature/experiments/architecture/cache.md#niceeval-身份域变更)。

## 方案

### 规范化文本

对扩展名为 `.ts`、`.tsx`、`.mts`、`.cts`、`.js`、`.jsx`、`.mjs`、`.cjs` 的闭包文件，先用解析器取得精确的注释区间与受保护区间，再生成规范化文本：

1. 受保护区间原样保留：字符串字面量、模板字面量的静态片段、正则字面量、JSX 文本、hashbang 与指令（`"use strict"`）。
2. 注释区间删除。注释本身跨行时替换为一个换行，否则替换为一个空格。
3. 受保护区间以外的空白连续段：只要包含换行就折叠为一个 `\n`，否则折叠为一个空格；文件首尾空白删除。

保留“有没有换行”是为了不改变自动分号插入的语义：`return\nvalue` 与 `return value` 的规范化文本不同。
所以只改缩进、空行和注释不会作废结果；把一行代码拆成两行，或把两行合并成一行，仍然作废。这是有意保守的边界。

身份载荷里这类文件的条目变为 `[相对路径, sha256(规范化文本)]`。规范化文本只用于计算身份，Sources 与断言源码定位仍保存原始字节。

### 解析器

解析器只用来确定区间，规范化规则由 NiceEval 自己实现，所以身份不依赖解析器的 AST 形状或版本。
候选是 `oxc-parser`：完整解析 TS / TSX / JSX，返回带精确偏移的注释列表和 AST 节点区间，有原生二进制与 wasm 两种发行。
依赖固定到精确版本；升级时由发布校验的固定样例证明规范化文本不变。

文件解析失败时，该文件退回按原始字节计算，载荷条目标为 `raw`。
解析失败的源码本来就无法运行，退回原始字节不会让两个不同的程序共用身份。

### 闭包成员与能力识别

- 相对模块从 AST 收集：`import` / `export ... from` 声明，以及参数为字符串字面量的 `import()`。注释里的路径不再进入闭包。
- Agent Judge、普通 Judge 与模拟用户的能力识别改为扫描规范化文本，因此注释不再触发识别。字符串里出现这些名字仍会被识别，属于保守误判，不影响正确性。
- 非 JavaScript / TypeScript 文件（例如被 import 的 `.json`）继续按原始字节计算。

### 身份域迁移

登记两条 `encoding-only` 变更：

| 变更 | 内容 |
|---|---|
| `fingerprint-algorithm/5-to-6` | JavaScript / TypeScript 源码条目由原始字节哈希改为规范化文本哈希；能力识别扫描规范化文本 |
| `fingerprint-coverage/3-to-4` | 闭包成员由正则收集改为 AST 收集 |

两条都保留旧域的计算作为纯函数：重建时用当前文件按旧正则收集成员、按原始字节计算哈希、按原始文本识别能力。
谓词恒为真：新域不新增用户输入，当前输入总能在旧域中表示。

后果：

- 升级 NiceEval 后，源码字节没变的 Eval 由重建证明等价，直接沿用，不需要重跑，也不需要 `accept`。
- 升级后才改注释的 Eval：旧结果属于旧域，旧域按原始字节重建得到不同 digest，因此会作废一次。从那以后的注释修改都不再作废。
- 曾经因注释里的 import 多拉进闭包的文件，新域里不再属于闭包；重建走旧域，所以已有结果照样沿用。

## 取舍

| 做法 | 优点 | 代价 | 判断 |
|---|---|---|---|
| A：解析器给区间，NiceEval 自己规范化（本方案） | 身份不随解析器版本漂移；注释判定精确 | 新增一个原生依赖 | 采用 |
| B：AST 去掉位置后整体哈希 | 连换行都能忽略，自动分号插入语义由解析器保证 | 身份依赖解析器的 AST 形状，升级解析器可能整体作废 | 不采用：身份稳定性比多忽略换行更重要 |
| C：自写词法器去注释 | 无新依赖 | 正则字面量与除号有歧义，误判会把代码当成注释，导致不同程序共用身份，静默沿用错误结果 | 不采用：错误方向是静默错误 |
| D：用 TypeScript scanner | 词法精确 | `typescript` 包体积大，用户项目不一定安装 | 备选：`oxc-parser` 不可用的平台可以改用它 |

## 已知边界

- 运行时把源码文本当数据的写法不受保护：`Function.prototype.toString()` 或用 `fs` 读取自己的源码。改注释会改变这类程序的行为，身份却不变。Eval 读取文件应使用 `loadText`，它按原始字节进入身份。
- 规范化只针对注释与空白；格式化工具改动引号风格、尾逗号或括号会作废结果。

## 验收

- 同一 Eval 只改注释、缩进、空行：`exp --dry` 显示沿用。
- 把一行拆成两行、改字符串内容、改正则字面量：显示 `identity-mismatch`。
- 字符串或正则字面量里含 `//`、`/*`：规范化文本保留它们，修改这些字面量仍作废。
- 注释掉的 import 指向的文件被修改：不影响该 Eval；去掉注释后它进入闭包。
- 注释里写 `agentJudge(`：载荷不出现 `agentJudge` 项。
- 用 NiceEval 升级前的 Record 运行 `--dry`：源码未变的 Eval 显示 `match`，`via` 列出两条变更名；不出现 `identity-domain-unregistered` 或 `unversioned-identity-change`。
- 解析失败的文件按原始字节计算，载荷条目标 `raw`。
- 发布校验的固定样例覆盖以上每种输入。
