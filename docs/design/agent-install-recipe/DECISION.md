## 待复审候选

[PLAN-4](PLAN-4.md) 在本结论之后新增。它把运行时
「检查→必要时安装」定为契约本体,官方 template 与构建
中间件退回快速路径;现有 PLAN-2 结论尚未据此重裁。
复审时应重点判断:预制 Agent 是否只是性能优化、任意任务
template 是否都应通过同一 Ensure 协议运行,以及身份与检查
单源能否替代安装步骤 DSL。

## 结论

采纳 **PLAN-2(中间件拆分)**:`withCodingAgent` 与
`withNodeToolContract` 公开为可叠加中间件,工厂退化为组合
糖;任意底座支持面第一期锁定 **apt 系 + glibc**,范围外
构建期报错。PLAN-3 不否决,作为 PLAN-2 之上的递进方案
保留,启用条件见「遗留风险」。

## 依据

对照 [GOALS](GOALS.md) 逐条:

- **R1 底座可换**:中间件叠到 `fromImage` 底座,契约内容
  留在 niceeval,下游零手抄——TB 八道题的卡点解除。
- **R2 Case A 不回归**:工厂签名不变且与 Case B 共享同一
  份中间件实现,不产生平行路径。
- **R3 支持面显式**:apt 系 + glibc 覆盖 Case B 的全部
  真实底座([LIMITS](LIMITS.md) TB 节),用既有校验链在
  构建期拦范围外底座。选探测式全发行版(Harbor 路线)的
  收益当下没有需求方,而它引入的静默降级点正是设计原则
  排除的。
- **R4 / R6**:PLAN-2 只推进版本单源、不达成命令单源与
  片段引用;取舍是这两条的需求方还没有出现
  ([PLAN-3](PLAN-3.md) 缺点节),不为它们预付 DSL 契约面。
- **R5 自定义口子**:构建期半边由中间件形态天然给出;
  运行时半边随 PLAN-3 启用条件走。

## 否决的候选项

- **PLAN-1(工厂加选项)**:R5 / R6 无法达成且不构成向
  PLAN-2 的台阶——选项参数一旦公开就有兼容义务,后续拆
  中间件要背两副契约([PLAN-1](PLAN-1.md) 关系节)。两案
  成本的大头(契约层任意底座能力)完全相同,省下的只有
  两个导出的评审,买不回损失的能力面。
- **PLAN-3 立即全量**:严格递进方案,否决的只是付出
  时机——收益的两个需求方(安装命令变更、未内置 agent
  接入)都还没有出现,而步骤词汇表是公开即永久的契约面。
  推迟到需求出现时启用,PLAN-2 的拆分保证了届时的迁移
  路径([PLAN-3](PLAN-3.md) 落地路线第 1 步即 PLAN-2)。
- **Harbor 式运行时安装为主路径**:与预制产物主路径原则
  直接冲突([GOALS](GOALS.md) 设计原则第一条),在候选
  展开前即排除;其配方形态(幂等短路、探测)由 PLAN-3
  按启用条件吸收。

## 遗留风险

- **PLAN-3 的启用条件**,任一成立即启动:内置 agent 的
  安装命令再次出现构建期与运行时两处不一致;第一个未内置
  agent 的接入请求到达;Docker 侧 Node 工具契约片段第二次
  被下游手抄。三个信号都指向「配方需要脱离 E2B builder
  存在」,届时按 [PLAN-3](PLAN-3.md) 落地。
- **非 apt 底座的需求**:出现 rpm 系或 musl 的真实基准
  底座时,扩支持面走 `withNodeToolContract` 的包管理器
  分发,不改中间件公开面。musl 要注意官方 Node 二进制
  不可用([LIMITS](LIMITS.md) Harbor 节的 nvm 限制同样
  适用)。
- **`fromImage` 底座的运行用户差异**:任意镜像的默认用户
  与 UID 不受 niceeval 控制,契约校验必须以运行用户身份
  断言可写性,不能以 root 身份跑出假绿。这条写进
  `verifyE2BNodeToolContract` 的断言语义,验收时用一个
  非 root 默认用户的镜像回归。
