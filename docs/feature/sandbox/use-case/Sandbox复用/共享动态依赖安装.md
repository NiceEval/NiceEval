# 共享一次随当前项目变化的依赖安装

## 解决什么问题

一批 Eval 使用同一个 checkout，每条都要先按当前 `pnpm-lock.yaml` 安装依赖。依赖集合随被测 commit
变化，还可能读取本次实验的私有 registry 配置；为每个 commit 构建、发布一份新 template 反而更重。

默认隔离模式会让每条 Attempt 各付一次 `pnpm install`。这段准备不随 Eval 变化，放进
SandboxSpec `setup` 并声明复用后，只需每个实际创建的 Sandbox 安装一次：

```ts
export default defineExperiment({
  sandboxReuse: true,
  maxConcurrency: 2,
  sandbox: e2bSandbox({
    template: "node-base",
    lifetimeMs: 60 * 60_000,
  }).setup(async (sandbox, ctx) => {
    ctx.progress({ message: "uploading project checkout" });
    await sandbox.uploadDirectory(process.cwd(), ".", {
      ignore: [".git", ".niceeval", "node_modules"],
    });

    ctx.progress({ message: "installing project dependencies" });
    const result = await sandbox.runCommand("pnpm", ["install", "--frozen-lockfile"]);
    if (result.exitCode !== 0) {
      throw new Error(`pnpm install failed: ${result.stderr}`);
    }
  }),
});
```

SandboxSpec `setup` 在题间重置点之前执行。安装完成后的 workdir 与 `node_modules` 成为该 Sandbox
后续 Attempt 的共同起点；每条 Attempt 开始前只把 workdir 重置回这个点，再准备自己的 Fixture。

## 实际分摊多少

收益按实际 Sandbox 数计算，不是整场无条件只装一次：

```text
默认隔离：Attempt 数 × pnpm install
Sandbox 复用：实际 Sandbox 数 × pnpm install
```

上例允许两个并发，因此 Runner 通常创建两个 Sandbox、各安装一次，再分别承接多条 Attempt。
若实验本来必须串行，配 `maxConcurrency: 1` 后整批才只安装一次。

运行反馈把安装记为 Run 级 Sandbox 准备，不重复塞进每条 Attempt 的时间树。结束反馈中的 Sandbox
创建数与复用次数可以核对这次是否真的摊销了准备工作。

## 为什么不总是做成 template

- 所有实验、所有 commit 都相同的 Node 与 pnpm 版本适合进 template。
- 由当前 lockfile、实验 flags、临时凭据或动态生成配置决定的安装适合 SandboxSpec `setup`。
- 只有某条 Eval 需要的依赖仍归 `EvalDef.setup`，不能借复用注入其它题。

template 与复用可以叠加：template 提供稳定工具链，SandboxSpec `setup` 安装本批次的动态依赖。

## 边界

- `sandboxReuse` 只重置 workdir，不清理 `$HOME`、`/tmp`、后台进程或外部服务状态。不能接受这些
  残留的实验继续使用默认隔离。
- 复用结果不参与后续 Run 的结果沿用。跳过部分 Attempt 会改变整批 Sandbox 生命周期，不能把两种
  运行形态混成同一份缓存。
- 安装命令必须能在新 Sandbox 上确定地完成；失败会淘汰该 Sandbox，不让半安装环境承接 Attempt。
