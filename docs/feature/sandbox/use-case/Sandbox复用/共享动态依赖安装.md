# 共享一次随当前项目变化的依赖安装

## 解决什么问题

一批 Eval 使用同一个 checkout，每条都要先按当前 `pnpm-lock.yaml` 安装依赖。
依赖集合随被测 commit 变化，还可能读取本次实验的私有 registry 配置；为每个 commit 构建、发布一份新 template 反而更重。

默认隔离模式会让每条 Attempt 各付一次完整的下载与安装。
这段准备不随 Eval 变化,写进 Experiment layer 的 `prepare()` 并声明复用后,真正的下载只在每个实际创建的 Sandbox 上发生一次:

```ts
export default defineExperiment({
  sandboxReuse: true,
  maxConcurrency: 2,
  sandbox: e2bSandbox({
    template: "node-base",
    lifetimeMs: 60 * 60_000,
  })
    .before(uploadDirectory({
      id: "project-checkout",
      source: new URL("../../../project/", import.meta.url),
      to: ".",
      changeFrequency: changeFrequency.rare,
    }))
    // pnpm install 自己就是真实检查:node_modules 在分类账排除清单里、活过题间 clean,
    // lockfile 未变时第二条 Attempt 起秒级收敛,未命中才走网络。
    .before(shell("pnpm install --frozen-lockfile")),
});
```

每条 Attempt 都要满足上传与安装 action。缓存命中通过 restore 满足，不重复传输或运行命令；miss 才 replay。`node_modules` 活过题间 clean，Provider 只支持 invocation-local 时，后续 Attempt 也只付 restore 或探测成本。
安装完成后每条 Attempt 再准备自己的 Fixture。

## 实际分摊多少

收益按实际 Sandbox 数计算，不是整场无条件只装一次：

```text
默认隔离:Attempt 数 × 完整安装(下载 + 链接)
Sandbox 复用:实际 Sandbox 数 × 完整安装 + 其余 Attempt × 命中核对
```

上例允许两个并发,因此 Runner 通常创建两个 Sandbox、各完整安装一次,再分别承接多条 Attempt。
若实验本来必须串行，配 `maxConcurrency: 1` 后整批才只安装一次。

每条 Attempt 的 prepare 记进它自己的时间树,归 `sandbox.prepare.experiment`。
第一条的完整安装耗时与后续的命中耗时并排可读；结束反馈的 Sandbox 创建数与承接序号可以核对这次是否真的摊销了下载。

## 为什么不总是做成 template

- 所有实验、所有 commit 都相同的 Node 与 pnpm 版本适合进 template。
- 由当前 lockfile、实验 flags、临时凭据或动态生成配置决定的安装适合 Experiment layer 的 `prepare()`。
- 只有某条 Eval 需要的依赖归该 Eval layer 的 `prepare()` 或 `test(t)`，不能借共享层注入其它题。

template 与复用可以叠加：template 提供稳定工具链，Experiment layer 的 `prepare()` 安装本批次的动态依赖。

## 边界

- `sandboxReuse` 只重置 workdir，不销毁 `$HOME`、`/tmp`、后台进程或外部服务状态。
  不能接受这些残留的实验继续使用默认隔离。
- 复用结果按普通 Experiment 的终态、指纹、资格与 `--rerun` 判据参与后续 Run 的结果沿用。
  携带的 Attempt 不创建 Sandbox，未携带的 Attempt 才进入本次复用生命周期。
- 安装命令失败时当前 Attempt 形成 `errored` Verdict，执行已登记 cleanup;reset 成功后该 Sandbox 可以继续承接,reset 失败才停用它。
