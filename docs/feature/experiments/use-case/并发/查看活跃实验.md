# 查看 Session 里的正在执行的 Experiment

另一位同事已经启动几批长跑 Experiment。你想确认哪些配置仍在执行、它们各自占了多少 Attempt，以及另开终端是否真的能为剩余工作加速。

活动查询不是结果阅读。一次 `niceeval exp` 调度形成一个 Session，里面有多个 Experiment Run；Run 和 Attempt 的历史判定仍用 `niceeval show` / `niceeval view`。完整 CLI 形状在 [CLI · Session 查询](../../cli.md#session-查询)，登记与失活判定在 [Architecture · Session 登记](../../architecture.md#session-登记)。

```sh
# 在项目根查看所有仍有心跳的 Session
niceeval session list

# 只看某个 Experiment 路径下仍活跃的 Session
niceeval session list compare/codex
```

输出按 Session 分组，并在组内逐 Experiment 列出状态：

```text
ACTIVE SESSIONS (2)
s_01J5R0H3K8 · pid 41267 · 2m 14s · heartbeat 1s ago
  compare/codex       @run:9dcf6f83  2 running · 1 queued
  compare/claude      @run:ef572a11  setup · 3 queued
s_01J5R0M8P2 · pid 41802 · 48s · heartbeat now
  compare/bub         @run:3ae91b42  1 running · 2 elsewhere

NEXT  niceeval exp compare --max-concurrency 2
```

`running` 是已经派发但尚未结局的 Attempt，`queued` 等待本 Invocation 的条件，`elsewhere` 等待另一个 Invocation 的用例锁或共享状态租约。`setup` 与 `teardown` 表示 Experiment 的运行级 Hook 正在执行；它们不占 Attempt 并发位。短 `runId` 只用来把活动行和稍后落盘的 Run 对上，不能替代 Attempt locator。

需要查看已经结束的同一批工作或给脚本接入时，使用 `--all` 与静态 JSON 文档，而不是订阅另一套事件流：

```sh
niceeval session list --all --json
```

默认查询只显示心跳仍有效的 Session。`--all` 还列出已经封口的 Session；强杀、断电或网络文件系统异常留下的过期条目会在 `EXPIRED` 区单列，并明确标为不是运行中的工作。它们不计入 ACTIVE，也不阻塞新的 `exp`。要观察某条 Session 的后续变化，重复执行此查询；持续运行中的细粒度阶段仍只在启动该 Session 的 live 面板可见。

## 决定下一步

1. 有 `queued` 且本机、Provider、Agent 服务都有余量时，在新终端对同一选择器启动 `niceeval exp … --max-concurrency N`。用例锁会让新 Session 接手未领取的 Eval，而不是双跑已领取的 Eval。
2. 只有 `elsewhere` 时，说明同一 Record 根里的其它 Session 已经持锁；等待它落盘，或选择不相交的 Experiment / Eval 范围。
3. 看见 `EXPIRED` 时，不把它当成正在消耗资源。重新运行原命令即可让缓存、用例锁与过期接管共同补齐未完成工作。

## 边界

- 查询范围只限同一工作副本和同一 `.niceeval` Record 根。不同机器或不共享 Record 根的 Session 不会出现在同一清单。
- Session 不保存 agent 消息、命令、密钥或完整执行事件；这些证据在 Attempt 完成后由 Run artifact 保存，并经 `niceeval show @<locator>` 阅读。
- `session list` / `show` 不发现 Experiment 源码、不加载配置、不启动 Sandbox，也不修改结果或锁。它们是只读的运行时观测入口。
