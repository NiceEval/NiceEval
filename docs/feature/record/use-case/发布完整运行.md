# 发布一轮完整 Run

本用例面向 Experiment Host、Runner 和 capture authority。它说明一个 `RunWriteSession` 怎样在 Effect
Scope 中收集事实、封口并发布；字段和错误的唯一契约仍在 [Library](../library.md) 与
[Architecture](../architecture.md)。

## 1. 昂贵工作前打开边界

```ts
const program = Effect.scoped(
  Effect.gen(function* () {
    const reader = yield* record.current.openRead({ root });
    const selection = yield* reader.selectRuns(request);
    const context = {
      experimentId,
      execution: { agentId, model, reasoningEffort, flags },
      labels,
    };
    const run = yield* record.current.createRun({
      root,
      experimentId,
      context,
      startedAt: clock.now(),
      expectedSlots,
    });
    return yield* executeAndSeal({ reader, selection, run });
  }),
);
```

打开 reader 验证 current root / Core definition，并取得 shared read lease。`createRun()` 取得 shared append lease，
先 exact-validate 必填 RunContext，并 refine `context.experimentId === experimentId`。随后它确认或一次性初始化
`record.json`，生成 RunId，并排他创建 `runs/<RunId>/`。任一步失败时，Runner 不会启动模型、Sandbox、外部命令
或付费调用。

全引用的运行改用 `createReferenceRun()`，但 request 仍必须携带同一完整 context、`startedAt` 和
`expectedSlots`；writer 路径不会因为没有新 Attempt 而省略历史解释事实。

这不是一个全量历史 snapshot。`selection` 只固定已封口 RunId、SlotId、预期分母和问题；query 需要
具体 Attempt、Evidence 或 trace 时才读取。新的 Run 可以在 selection 形成后封口，不会改变本轮计划。

## 2. 对每个 Slot 决定引用或执行

Experiment 在真正 dispatch 一个 Slot 前取得 execution claim，再用新的 read session 复查可复用事实：

```ts
const claim = yield* coordination.claimExecution(executionKey);
const freshReader = yield* record.current.openRead({ root });
const decision = yield* experiments.recheck({ slot, reader: freshReader });

if (decision.kind === "reuse") {
  yield* run.referenceAttempt({ slotId: slot.id, attempt: decision.attempt });
} else {
  const attempt = yield* run.createAttempt({ slotId: slot.id });
  yield* runner.execute({ attempt, eval: slot.eval });
}
```

reference 只保存 `{ originRunId, attemptId }`，不复制 Assertions、Observation、Sources 或 blob。claim
等待时释放本 Invocation 的 concurrency permit；不会占住执行名额。承载新 Attempt 的 Run durable seal
之前不能释放 claim，因为其它进程还看不到 `complete`。

## 3. Capture authority 提交 Attachment

Runner 把窄 `AttemptWriteSession.record` 交给各 capture authority。producer 先通过 callable definition 构造惰性
command，再交给 matching owner：

```ts
yield* attempt.record.write(family(({ content, reference }) => ({
  ...value,
  report: content.text(report),
  source: reference.to(exactDefinition, semanticValue),
})));
yield* attempt.complete(outcome);
```

Assertions、Observability、File Changes 与 Artifacts 各自在事实边界多次 capture，封口后形成一个 exact logical
value 与 owner-local content closure，再各自 write 一次。逐条 append、canonical order、去重和 complete/partial
判断仍属于该 family 的唯一领域 collector。调用者不能写 raw JSON、path 或 content digest；第三方 rich family 也必须
先经 branded definition 与 session-local catalog。

只含 context-free plain-data item 的 Attempt family 可以改用 `defineAttemptRecordCollection`。Host/capture producer
通过 `attempt.record.start/append` 分批采集，Attempt complete 时自动形成一份 logical value。这个入口没有 Run 版本，
也不进入普通 Eval `TestContext`、Adapter 或 Plugin。完整路径见
[多次 send 怎样收集 Attempt 事实](多次send怎样收集Attempt事实.md)。

`record.write()` 返回 `void` 只表示 rich value 已进入 staging。重复或并发同 family write 会在 callback、Stream 与 I/O
前失败 `record-already-written`，并 poison 本次未发布 Run。rich family 没有 write 时读为 `not-recorded`；它的
complete-empty 与 partial 由领域 collector 显式表达。simple collection 则只有 start/append 才激活。完整矩阵见
[Record Library](../library.md#write--append-case-matrix)。

Run owner 在 seal 前写 Sources、Run Observability 和 Run Artifact。Sources 以 origin Run 为 owner，
让所有 origin Attempt 和后续 reference Run 读取同一份当时源码闭包。

## 4. `seal()` 是发布边界

```ts
const receipt = yield* run.seal({ completedAt: clock.now() });
```

`seal()` 立刻将 session 从 `open` 转为 `sealing`，拒绝新 mutation，并等待在飞 Attempt、collector 和 write command
停稳。它在 marker 前完成：

1. expected Slot、origin/reference、owner 和精确 identity 验证；
2. current catalog 中每个 contributed family 的 exact value、reference 与 content closure 验证；
3. 含必填 `RunDocument.context` 的 Run Core、Member、Attempt 与 receipt 构造；
4. 所有 durable handle 的 final flush 与 close。

最后仅在短暂 `Effect.uninterruptibleMask` 中排他创建零字节 `complete`，同步 consume writer，并同步
Run 目录与 `runs/` 父目录。此后没有可失败的业务步骤。

## 5. 失败、中断与重新读取

`complete` 前发生 typed failure、defect、interruption 或进程退出时，session 进入 `failed`。目录留在
`runs/<RunId>/`，但不属于 Record；reader 忽略它，并只向 maintenance 保留 `incomplete-run` warning，不进入
Analysis 或 Report warning。Scope finalizer 只释放 lease 和 handle，不自动删除目录。

用户可明确运行：

```sh
niceeval clean
```

`clean` 在 maintenance lease 下重验 `complete`，只删除仍 incomplete 的目录。它不删除已封口但 Core
invalid 的事实。

`complete` 后发生 interruption 时，Run 已经 durable 发布。receipt 没有返回不等于撤销事实。当前
reader selection 也不会自动看到这个新 Run；下一次 `openRead()` 和 `selectRuns()` 才会看到它。

## 反例

| 错误做法 | 违反的边界 |
|---|---|
| 没有 `complete` 就把 directory 加入 reuse candidates | 半成品进入分析与沿用 |
| `complete` 后补写 `completedAt` 或 Attachment | 已发布 Run 不再 immutable |
| 一个 writer 修改 root manifest 或别人的 Run | 并行追加失去隔离 |
| claim 在 Run seal 前释放 | 另一个 Invocation 可能重复执行 |
| 把 session、lease 或 cache 写进 Record | local operation state 进入 portable boundary |
| 给 producer 暴露 raw JSON、path 或 content writer | definition closure 边界失效 |
| 把 `record.write()` 的 `void` 当成 durable receipt | staging mutation 被误认为已发布事实 |
| 多个 producer 分别 append 同一个 family | 破坏单一 capture authority、canonical order 与 create-once write |
