# 上层变化不改持久格式

Assert-first author API、Experiment 计划、reuse 判断、Analysis 和 Report 可以独立演进。判断依据是
已封口事实的语义是否改变，不是函数改名、内部求值顺序或页面改版。

## 稳定边界

```text
author API / matcher / adapter mapper / experiment planning
                         │
                         ▼
fixed Record family catalog
                         │
                         ▼
Record Core and complete publication
                         │
                         ▼
Analysis / Report
```

Record 保存 AssertionResult、Observation、file change、Sources 和 Artifact 等发生过的事实。它不保存
matcher object、memoization、作者调用图、执行计划、cache hit、通行率、P95 或页面路由。

## 每层拥有自己的变化

| 变化 | owner | 动作 |
|---|---|---|
| Assertion authoring、matcher、Plugin lifecycle | behavior | 必要时更新 input 或 reuse identity |
| Adapter mapper、OTel 采集策略或 redact rule | fixed collector | 不改变已封口 payload 时不改 Record |
| 读取用的 typed view | Analysis | 发布新的读取 API 或 Calculation |
| 图表、下载、组件与页面 | Report | 改 Report，不改 Record |
| 此前未保存的不可恢复事实 | NiceEval Record | 扩展既有 family，或加入新的 static fixed family；不改 Core |
| family 字段、单位、基数或 closure 语义 | NiceEval Record | 提高 numeric schemaVersion 并提供相邻 migration |
| Core identity、owner、引用、目录或 `complete` 判断 | NiceEval Record | 发布新的 format identity 与显式 conversion；不增加全局 schemaVersion |

相同 fixture 产生相同 bytes 不足以证明 behavior 等价。reuse 条件改变时，behavior identity 必须改变；
这不会把新 policy 回写进历史 Record。

## Assertions、观察与分析各自独立

Assertion producer 封口 `niceeval.assertions`；它保存 criterion、material、coverage、Evidence 和
result。Observability collector 封口 `niceeval.observability`；它保存运行中的安全观察。两者都不
计算 Sample denominator、通过率或 dashboard summary。

Analysis 只能从 `RecordReadSession` 按需读取这些事实，显式定义 population、missing、reduction 与
measure。Report 只消费闭合的 Analysis 结果。改变指标、统计口径或页面不要求 Record migration。

## current 读取与以后版本

current root 的领域值固定为 `{ format: "niceeval.record", recordId }`，没有 schemaVersion。每个 Attachment envelope 都以稳定
family name 加 numeric schemaVersion 表示自己。ordinary reader 只读取 current definition；`niceeval migrate`
对完整 current Record 返回 `already-current`。

root format / Core 不相容时返回 `unsupported-format`。已知 family 的旧
schemaVersion 只在完整固定 chain 存在时可 migrate。独立未知 future family、已知 future 版本与未发布的
`/vN` 后缀草案都在 ordinary session 形成前拒绝整份 Record。

当 NiceEval 把任一 fixed family 升到下一 schemaVersion 时，必须把固定相邻 migration 与新 schema 一起发布。迁移只能从
已保存的 payload 和 own blob closure 形成目标事实，不能读取当前源码、运行 matcher、重新做 reuse planning
或调用外部服务。中断恢复始终由 Git 完整恢复历史字节。

## 验收问题

每次上层重构只检查：

1. 已封口 payload、unit、cardinality 或 closure 的语义是否改变？
2. 是否只是 typed view、Calculation 或 Report 变化？
3. 相同输入的可观察行为或 reuse 安全条件是否改变？
4. 是否改变所有 reader 都必须理解的 Core 公理？
5. 是否试图把此前未保存的不可恢复事实写入开放字段，或交给调用方定义 durable family？

前四项分别归 Record schema、Analysis / Report、behavior identity 与 Record format。
第五项的答案必须是否定的。
