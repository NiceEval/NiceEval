# 上层变化不改持久格式

matcher、Experiment planning、Inspection 与 Delivery 可以在 sealed facts 不变时独立演进。判断标准是业务事实与 reuse 安全条件，
不是函数名、SQL query、页面或内部求值顺序。

| 变化 | owner | Record action |
|---|---|---|
| matcher、author API、reuse policy | behavior / Experiment | 必要时推进 behavior identity，不写历史 rows |
| 新的第一方统计、比较或 typed view | Inspection | 用 bounded read/Stream 扩展具名 operation |
| 固定图表、下载或页面 | Delivery | 不取得 Record database 或 Content handle |
| 新 Attempt plain-data fact | capture owner | 新 `Record.attemptCollection()` family |
| 新 rich 或 Run-owned fact | semantic owner | 新 `Record.attempt()` / `Record.run()` family |
| family canonical fields/content/reference 改变 | family owner | adjacent family/data migration，重建 Logical Seal |
| table/index/trigger 改变但 facts 不变 | Record Host | checked-in physical schema migration，保留 `LogicalSealIdentity` |
| owner、Run/Attempt/reference/Seal 公理改变 | Record Core | 新 format identity 与显式 import |

相同输入产生相同 SQLite bytes 不是必要条件；physical schema migration 可以改变 bytes 与 storage generation，同时保持同一
Logical Seal。反过来，仅仅保持 table layout 也不能掩盖 family business facts 已改变。

OS-user feature Repository 只维护自己的最终 schema、fixed operations 与 typed decoder；数据库演进进入 UserDatabase 的全局编号 migration catalog。
central `UserDatabase` 仍拥有 connection、transaction 与 migration orchestration。
Repository 不能取得 raw SQL 扩张边界。cache Repository 的 schema、cleanup 或业务失败也不能成为 durable user-state、
credential-reference 或其它 Repository 的逻辑前置。

验收时逐项问：是否出现此前未保存且不可恢复的事实？是否只改变读取/展示？是否改变 reuse policy？是否只改变 physical
representation？是否改变所有 reader 都必须理解的 Core identity？答案分别决定新 family、上层变更、behavior identity、
physical migration 或新 Record format。
