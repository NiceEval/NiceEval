# 选择正确的演进边界

新增能力时先找 owner，再选择 Calculation、projector、RecordAttachment schema、behavior identity 或 Record major。migration 是 Core 的演进出口，不是把所有业务字段放进 Core 的理由。

## 判断顺序

1. 这只是从已声明数据重新计算或展示吗？
2. consumer 需要的 typed view 是否改变？
3. 当时需要持久化的 payload shape 或语义是否改变？
4. 该事实属于 Run 还是 Attempt？
5. 执行行为或 reuse gate 是否改变？
6. 所有 reader 都必须理解的 owner、引用、目录或 Core shape 是否改变？

| 答案 | 动作 |
|---|---|
| 只重新计算或展示 | Calculation、Page 或 Report |
| typed view 改变 | 新 projector/API |
| payload 改变 | 新相邻 `RecordAttachmentSchemaId` 与 migration policy |
| 新运行事实 | 新 RecordAttachment |
| 行为或 reuse 条件改变 | 新 behavior/reuse identity |
| Core 公理改变 | 新 `RecordFormatId` 与相邻 converter |

## 自定义 RecordAttachment

```ts
interface GpuEnergyV1 {
  readonly joules: number;
  readonly source: "device-estimate";
}

const gpuEnergyV1 = Either.getOrThrow(
  defineJsonRecordAttachment({
    owner: "attempt",
    name: "com.example.gpu-energy",
    schemaId: "com.example.gpu-energy/v1",
    schema: Schema.Struct({
      joules: Schema.Number,
      source: Schema.Literal("device-estimate"),
    }),
  }),
);
```

producer 用 typed family 与 payload 形成 write。Record Core 不增加 `gpuEnergy` 字段；没有安装该 definition 的 reader 仍能读取同一 Attempt 的 Verdict 与 Assertions。

设备估算与机房电表实测不是同一事实，应使用不同 RecordAttachment name，而不是在一个开放对象中用可选字段猜语义。

## RecordAttachment v2

如果 v2 增加误差区间：

```text
com.example.gpu-energy/v1
  → converter 或 not-losslessly-migratable
com.example.gpu-energy/v2
```

owner 不变，因此 Record Core 不变。新功能请求 v2 而磁盘仍是 v1 时，converter 返回 migration-required；明确不可无损迁移返回 migration-unavailable。

converter 可以把 v1 的精确值转换成 v2；无法得到的事实必须表达 unavailable，或者把该边声明为不可无损迁移。它不能读取今天的设备重新估算昨天的能耗。

unknown RecordAttachment 始终是 unsupported，不能因为已知 family 也有不可无损迁移边而改称 migration-unavailable。

## Verdict、Score 与质量信号

`niceeval.verdict/v1` 保存每个 origin Attempt 的四态 Verdict。Score Eval 另用 `niceeval.score/v1` 保存 Score；Pass Eval 没有 Score RecordAttachment。

Verdict 与 Score 不互斥，也不可互推。额外质量信号拥有自己的 RecordAttachment。reuse planning 显式声明所需 RecordAttachment 与 behavior domain；“可以展示”不等于“当前可以沿用”。

## 不能走的捷径

- 同一 schema ID 接受多个 shape；
- 用 optional 字段组合猜版本；
- 给 generic writer 增加业务专用 `writeX2()`；
- 暴露 raw JSON 或 path writer；
- 把 session、lock、migration history 或 cache 写进 Record；
- 普通 open 自动迁移；
- converter 运行今天的业务算法；
- 为了少做 migration，把 Core 改成 `Record<string, unknown>`。

## 验收

一个持久能力只需回答：

1. owner 是 Run 还是 Attempt？
2. RecordAttachment name 与 schema identity 分别冻结什么？
3. current schema 与上一版之间是 converter 还是明确不可无损迁移？
4. typed projector 返回什么？
5. unsupported、migration-unavailable 或 invalid 是否只影响这一次读取？
6. behavior/reuse identity 是否也需要变化？
7. 是否真的改变所有 reader 都必须理解的 Core？

只有第 7 项触发 Record major。
