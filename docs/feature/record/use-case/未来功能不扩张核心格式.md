# 选择正确的持久边界

新增能力先判断它是已保存事实的读取、一个新的不可恢复事实，还是所有 reader 都必须理解的 Core
公理。migration 不是把业务字段写入 Core 或开放新 registry 的理由。

## 判断顺序

1. 这只是从已保存事实重新计算、展示或下载吗？
2. consumer 需要的 typed view、Measure 或 Report component 是否改变？
3. 是否出现了无法从现有事实恢复的新事实？
4. 该事实属于 Run 还是 Attempt？
5. 是否改变了现有 family 的字段、单位、基数或 blob closure 语义？
6. 是否改变了 Run、Slot、Member、Attempt、owner、reference、目录或原子发布边界？

| 答案 | 正确动作 |
|---|---|
| 只重新计算或展示 | Analysis、Projection、Calculation 或 Report |
| 只改变 typed view | 发布新的读取 API，不改 Record |
| 新的不可恢复事实 | NiceEval 评审后加入五个 fixed family 的明确语义，或发布一个新的固定 family |
| family 持久语义改变 | 发布下一 `/vN` schema，并同批提供相邻 migration |
| Core 公理改变 | 发布下一 Record format，并同批提供相邻 migration |

## 五个 family 不是扩展点

Adapter、Plugin 和 Report 作者不能这样做：

```ts
defineRecordAttachment(...); // 不存在
registerRecordFamily(...);   // 不存在
registerMigration(...);      // 不存在
```

例如 GPU 能耗、私有 trace 或新的 file evidence 不能由外部 producer 写入
`com.example.gpu-energy/v1`。如果它确实是 NiceEval 需要保存的不可恢复事实，先裁决 owner、exact
payload、cardinality、closure、collector 和 migration。随后由 NiceEval 作为固定协议发布。

## 事实、行为和派生结果不能互换

`niceeval.assertions/v1` 保存 sealed check result，`niceeval.observability/v1` 保存安全运行观察，
`niceeval.sources/v1` 保存当时源码。它们不能替代当前 matcher、input identity 或 reuse policy。

反过来，平均值、通过率、P95、成本汇总、trace tree、图表点位和页面布局都能从固定事实及显式
Calculation 形成，不应变成 Attachment 字段。能展示一个 Attempt 不等于当前 Experiment 可以 reuse 它；
reuse gate 明确声明所需 facts 和 behavior identity。

## v1 的版本边界

v1 是首个支持格式，只解码 exact v1 bytes。`niceeval migrate` 对 v1 返回 `already-current`，对非支持
格式返回 `unsupported-format`。发布 v2 时，NiceEval 必须同时交付
固定 v1→v2 migration，且只从旧的 saved closure 形成新 bytes。

## 不能走的捷径

- 用 optional field、自由 object 或多个 shape 猜一个 schema version；
- 让 generic writer 接受任意 JSON、path、bytes 或手写 blob ref；
- 把 session、claim、lease、migration history 或 cache 写进 Record；
- 普通 open 自动迁移或把另一 schema 伪装成 v1 值；
- 为了少做 migration，把 Core 改成 `Record<string, unknown>`；
- 让第三方 converter 或当前业务算法重写历史事实。
