# 未来功能不扩张核心格式

新增持久能力时分别回答四个问题：

1. 能否从现有 normalized facts 推导，只改 Report？
2. 业务语义是否仍是现有 ChannelName？
3. 精确 bytes shape 是否仍是现有 ChannelSchemaId？
4. owner、identity、membership、path 或发布原子性是否改变，需要新的 core format？

这四层不能互相代替。新增一个 payload 文件会改变 Record 内容，但不会自动改变 `niceeval.record/v1`；反过来，owner 或发布单位变化也不能伪装成普通 channel schema 升级。

## 放置顺序

设计者按下列顺序命中后停止：

1. 只影响显示或计算，并能从 ReportPlan 已请求的 facts 推导：只改 Report。
2. 语义和精确 shape 都不变：继续写既有 schema ID。
3. 语义相同、shape 改变：发布同一 ChannelName 的新 schema ID与永久 decoder。
4. 业务语义改变：发布新的 ChannelName、schema ID 与 FactRequirement。
5. 触及 core owner、identity、membership、路径或发布边界：使用新的完整格式名。

发布新的完整格式名（例如 `niceeval.record/v2`）不授权删除 v1 reader，也不把 v2 对象混写进 v1 root。写入既有 v1 root 只能使用 v1 core 与可局部演进的 channel；只有显式离线转换到新的完整 root，才会把 Record 从 v1 迁到 v2。

所有正式 built-in schema 必须先登记 [channel registry](../architecture.md#built-in-channel-registry)：schema ID、owner、media type、FactRequirement identity、兼容级别、永久 decoder 与消费者缺一不可。不能先写任意 JSON，等 reader 出现后再猜它是哪一代。

## 给图表增加短名

若短名能由现有 Experiment labels 稳定形成，Record 不增加字段。Report 使用一个纯函数从已计划 labels 形成显示名。

若作者需要显式值，并且 labels 已经定义为开放参数袋，可以增加业务 key：

```ts
const labels = {
  line: "codex",
  memory: "nowledge",
  shortName: "Codex + Nowledge",
};
```

这不会给 RunDocument 加字段。若短名后来需要 locale、有效期或 provenance，labels 已无法准确表达，应创建 presentation channel，而不是把 `shortName: string` 原地改成对象。

## 增加 GPU 能耗

GPU 能耗不是现有 usage 或 timing 的同义字段。producer 增加 `niceeval.gpu-energy/v1`，登记 Attempt owner、`application/json`、`gpuEnergyFact` 与标准消费者。

第二代若仍表达同一种能耗事实，但 document shape 为了增加测量误差区间而改变，发布 `niceeval.gpu-energy/v2`。v2 reader永久保留 v1 decoder，并把两者归一到 requirement 能表达的共同值；v1 reader看到 v2 时只让该 requirement unsupported。

若“设备估算”变成“机房电表实测”，业务口径已经改变。此时发布新的 ChannelName，或让 normalized value 用穷尽判别表达两种口径；不能只换 schema 数字却继续让消费者把值当成同一种测量。

这些变化都不触碰 AttemptDocument 或 core format。

## 更换 fingerprint 或 carry gate

eligibility v1 包含四个 opaque token：

```ts
type EligibilityDocumentV1 = {
  reuseContract: EqualityToken;
  inputIdentity: EqualityToken;
  configIdentity: EqualityToken;
  executionDuration: DurationToken;
};
```

fingerprint 算法或输入闭包改变时，切换相应 identity domain。新增、删除或改变任一 carry gate 时，至少切换 `reuseContract.domain`；持久形状改变时再发布 `niceeval.eligibility/v2`。

每个 execution projector 显式列出接受的 eligibility schemas 与 reuse domains。policy identity 只写入 `niceeval.actions` 解释当时决定，不能单独充当前向栅栏。

### 旧 CLI × 新 gate 反例

假设 v1 projector 接受：

```text
schema: niceeval.eligibility/v1
reuse domain: niceeval.reuse/base-v1
```

未来把人工复核变成 required gate。新 writer 至少切换到 `niceeval.reuse/human-review-v1`；若 eligibility shape 也变化，则发布 v2。它不能同时留下一个 base-v1 legacy descriptor。

旧 CLI 读取新 Attempt 时，required eligibility fact 得到 schema unsupported 或 reuse domain mismatch，结果必须是 gap。旧 CLI 不认识 human-review channel 不能成为 carried 的理由。这条反例是每次新增 gate 的验收项。

## 给 Verdict 增加 warning

`niceeval.verdict/v1` 的四态精确为 `passed | failed | errored | skipped`。

- warning 只是附加质量信号：写新的 `niceeval.quality-signal/v1` 与 requirement。
- warning 是新的终态：同一 Verdict 语义若仍成立则发布 `niceeval.verdict/v2`；若含义已经不同则使用新的 terminal-state channel。

execution projector 必须显式接受新的 verdict schema。标准详情永久保留 v1 decoder；旧 reader看到 v2 只让 Verdict requirement unsupported，不把整个 Record 判坏。

## 增加多模态附件

图片、音频和视频使用 origin Attempt-owned blob，新 channel 保存 media type、角色和相对 blob ref。新附件角色若不在旧 schema 的精确联合内，发布新的 schema ID。

把 blob 改成跨 Attempt 去重、远端对象引用或 root 外路径，会改变 owner、portable closure 与目录 rename 的原子性。这不是 channel payload 升级，必须使用新的完整 core format，或放到 Record 之外的导入/导出系统。

## 为什么这次不会重演全局 1→18

旧 Results Format 把业务对象、展示事实、carry 资格与目录协议放在同一个全局整数下。一处字段变化就让整个 Run 对所有消费者失效。

Record v1 把影响范围分开：

| 变化 | 失效范围 |
|---|---|
| Report 推导规则 | 重新执行 Report |
| 新 channel schema | 只影响请求该 requirement 的消费者 |
| 新 carry gate/domain | 只让不兼容 Attempt 形成 gap |
| 新业务语义 | 新 ChannelName 与 requirement |
| core owner/identity/atomicity | 新完整 format |

局部 schema 仍会累积，这是主动承担的兼容成本。正式 decoder 永久保留，避免把复杂度重新推给每个 Report。若某个团队不愿永久维护 decoder，就不能把该 schema 作为 built-in 正式发布。

## 不能走的捷径

- 同一 schema ID 同时接受多个对象形状。
- decoder 用可选字段组合猜代际。
- 为兼容展示并写两个 eligibility descriptor，让旧 projector 误通过。
- 把业务字段写回 Run/Member/Attempt core。
- 给每次 schema 变化增加新的 storage method。
- 把 local session/cache 放进 Record，或把局部 Run 当成 portable Record。

## 设计验收

每次增加持久能力时回答：

1. producer 写出的业务语义是什么？
2. owner 为什么是 Run 或 Attempt？
3. ChannelName 与 schema ID 分别是什么？
4. exact object、media type、coverage 与 blob 引用由谁拥有？
5. normalized FactRequirement identity 与消费者是什么？
6. 新 reader 怎样读取每个旧 schema？
7. 旧 reader看到新 schema 时怎样局部 unsupported？
8. 展示兼容与 carry accept set 是否明确分开？
9. 新 gate 如何让旧 CLI 必然 gap？
10. 是否改变 core owner、identity、path、membership 或 publish boundary？

答不清其中任一项时，不得以“只是加一个 optional 字段”为理由写入正式 Record。
