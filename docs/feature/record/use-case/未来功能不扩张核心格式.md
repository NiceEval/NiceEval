# 未来功能怎样不扩张核心格式

本用例面向准备给 NiceEval 增加持久化业务能力的设计者。目标不是让 Record 的文件和内容永远不变，而是让新业务事实不反复扩张 Run、Member、Attempt 和通道 descriptor 这组永久核心。

加入功能时，必须分别回答三件事：

1. Record 的内容会不会改变；
2. 某个局部通道的字段契约会不会改变；
3. <code>niceeval.record</code> 的核心协议会不会改变。

新增通道文件或 descriptor 会改变第一项。给既有通道增加兼容字段会改变第二项。前两项都不自动等于第三项。

## 先走选择顺序

设计者按下列顺序放置新能力，命中后停止。

1. 能从现有已计划 facts 推导的显示或计算，只改 Report。
2. 已有稳定参数袋可以准确表达的声明，增加参数袋中的业务键。
3. 与既有通道语义相同、字段确实可以缺席，并且该通道已经承诺忽略新增可选字段时，增加可选字段。
4. 新事实、破坏性字段变化或不同语义，发布新的描述性通道或 event 名称。
5. 触及 [Architecture 的格式演进边界](../architecture.md#格式演进边界) 时，更换整个格式名。

不能为了避免更换格式名，把不相干的值写入现有字段。通道数量增加是这里主动接受的代价；语义混用会把局部兼容问题重新变成隐含的全局 schema。

## 给图表增加短名

假设柱状图已经通过 Experiment labels 得到 <code>codex+nowledge</code>，而散点图只显示完整 <code>experimentId</code>。产品要让两种图统一显示短名。

### 只需要报告规则

若短名可以由现有 labels 稳定形成，Record 不增加字段。Report 把 labels 声明为输入，并使用同一个纯函数：

```ts
function experimentDisplayName(input: {
  experimentId: string;
  labels: Readonly<Record<string, string | number>>;
}): string {
  const line = input.labels.line;
  const memory = input.labels.memory;

  return typeof line === "string" && typeof memory === "string"
    ? `${line}+${memory}`
    : input.experimentId;
}
```

这次变化只重新生成 Report。Record 文件、通道和规划 identity 都不改变。

### 作者需要明确指定短名

若作者希望用声明值替换推导结果，优先使用已有 labels 参数袋：

```ts
labels: {
  line: "codex",
  memory: "nowledge",
  shortName: "Codex + Nowledge",
}
```

这里增加的是一个 map entry，不是 RunDocument 的新字段。旧 reader 仍能读取 labels map；不知道 <code>shortName</code> 的旧 Report 继续使用原显示规则，新 Report 优先使用它。

不要仅为兼容旧数据写 <code>shortName: null</code>。字段缺失已经准确表达“作者没有明确指定”。如果产品真的需要区分“从未声明”和“作者明确清除”，应使用一个穷尽业务状态，而不是让 <code>null</code> 同时承担旧版本占位和业务含义。

```ts
type DisplayNameOverride =
  | { state: "specified"; value: string }
  | { state: "cleared" };
```

若短名以后需要多语言、有效期或 producer provenance，labels 已经不能准确表达它。此时发布新的 presentation 通道，不把 <code>shortName: string</code> 原地改成对象，也不把字段写入 RunDocument。

## 增加 GPU 能耗和碳排数据

未来的 Sandbox provider 可能采集 GPU 能耗。现有 timing、usage 或 telemetry 并不承诺这种语义，因此 writer 增加新的 <code>niceeval.gpu-energy</code> Attempt 通道。

旧 Record 没有该通道。只请求 Verdict 或成本的报告继续工作；请求 GPU 能耗的页面把该事实呈现为 unavailable。旧 reader 不认识新通道时保留 descriptor，并只把这个通道标为 unsupported。

若第二代采集从“设备估算值”改成“机房电表实测值”，两者不能复用同一个数值字段。它们可以作为两个含义稳定的字段并存，或使用新的描述性通道名。不能把旧 <code>joules</code> 悄悄改成另一种测量口径。

这会增加 Record 文件和 descriptor，但不改变 AttemptDocument 或通道协议。

## 更换 fingerprint 算法

规划器未来可能把 lockfile、远端模型 revision 或 Sandbox image digest 加入 fingerprint。eligibility 通道仍保存同一个形状：

```ts
type EqualityToken = {
  domain: string;
  value: string;
};
```

算法或输入闭包语义改变时，writer 使用新的 domain。规划器只比较 domain 相同的 value；旧 Attempt 因 domain 不同而不能自动 carry。

这次变化会改变新写入的 identity token，也可能导致重跑，但不会增加核心字段。若实现试图继续沿用旧 domain，它就不是兼容演进，而是在让同一个值偷偷改变含义。

## 增加人工复核结果

人工复核不是 Member 的第四种 kind，也不是 Verdict 的 provenance 字段。它是新的 Attempt 业务事实，进入独立的 <code>niceeval.human-review</code> 通道。

报告可以同时显示机器 Verdict 与人工复核。规划器仍只依赖永久支持的 Verdict 与 eligibility；不知道人工复核的旧工具不受影响。

如果需求只是“给失败加一个复核注释”，也不能把 comment 加进 Member。Member 只负责一个 slot 采用哪个 Attempt。

## 给 Verdict 增加 warning

现有 planner-critical Verdict 永久定义为 <code>passed</code>、<code>failed</code>、<code>errored</code> 与 <code>skipped</code>。未来页面希望显示 warning 时，先判断它是否真的改变终态。

- 若 warning 只是附加质量信号，写入新的 <code>niceeval.quality-signal</code> 通道，Verdict 仍保持四态。
- 若 warning 真的是第五种终态，并且会改变退出码、carry 和分母解释，就不能伪装成附加字段。它破坏 planner-critical 语义，必须更换整个格式名。

这个反例说明“使用通道”不是绕过核心变化的借口。业务语义真正进入永久核心后，格式名仍然需要改变。

## 增加多模态附件

图片、音频和视频使用 Attempt-owned blob，新通道保存 media type、角色和 blob 相对引用。它不把二进制内联进 AttemptDocument，也不跨 Attempt 建共享摘要表。

以后增加一种附件角色时，如果旧 decoder 已承诺忽略未知 event variant，可以兼容添加；否则使用新的 event 名。把 blob 改成跨 Attempt 去重或远端对象引用，则改变 owner、路径和可见性规则，不能作为普通通道字段升级处理。

## 改成远端 Record 或跨 Attempt 去重

假设未来为了节省空间，希望所有 Attempt 共享一个内容寻址 blob store，或者让 Run、Attempt 直接指向远端对象。

这会改变当前的核心约束：blob 不再由单个 Attempt 拥有，路径不再完全位于 Record root，目录 rename 也不再提供同样的原子可见性。因此不能只增加 <code>remoteUrl</code> 或 <code>hash</code> 字段来假装兼容。

这种能力必须使用新的完整格式名，或作为 Record 之外的导入导出系统存在。

## 挑战：这套设计没有解决什么

### 它没有消灭局部 schema

document channel 仍然有字段契约，JSONL event 仍然有 variant 契约。增加可选字段、发布新通道和退役 decoder 都是演进。这里消除的是“一个业务字段让全部历史数据一起升全局整数版本”，不是消除数据契约本身。

### 可选字段不一定兼容

只有同时满足以下条件才属于兼容添加：

- 缺失确实是合法业务状态；
- 新 reader 对旧数据有唯一解释；
- 已发布的旧 decoder 承诺忽略并保留未知可选字段；
- 新字段不改变已有字段、判别值、规划或聚合的含义。

任一条件不满足，就使用新的描述性通道或 event 名。仅仅在 TypeScript 后面加问号不能证明兼容。

### 通道也可能变成另一套全局版本

如果每次变化都创建 <code>thing2</code>、<code>thing3</code>，或者 decoder 同时猜十种旧形状，设计只是把 schema 1 至 15 搬进通道。新名称必须描述新的业务语义；composition adapter 必须按 ReportPlan 具名请求，并对互斥通道冲突报错。

### 老 Report 不会自动拥有新功能

旧 Report 可以继续使用它已经声明的 facts，但它不会自动显示 GPU、人工复核或新短名。需要新能力时重新编译或导出 Report。静态 Report 携带自己的 runtime，不由未来 NiceEval 再次解释。

## 验收未来功能设计

每次增加持久化能力时，用下面的问题验收：

1. 这个值是执行事实、作者声明，还是纯显示派生值？
2. 为什么不能从现有已计划 facts 推导？
3. 它的 owner 是 Run 还是 Attempt？
4. 它为什么属于现有通道，或者为什么需要新通道？
5. 缺失、<code>null</code>、unavailable、unsupported 与 invalid 是否各只有一种含义？
6. 旧数据由新 reader 怎样得到唯一结果？
7. 新数据由旧 reader 怎样局部降级？
8. 是否改变规划、membership、origin、path、coverage 或原子可见性？
9. 若改变已有语义，新的描述性身份是什么？
10. 最坏情况下失效的是一个字段、一个通道、一个页面，还是整个 Record？

答不清这些问题时，不得以“只是新增 nullable 字段”为理由修改落盘契约。
