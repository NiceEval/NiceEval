# `--out`：把报告导出成静态站

## 解决什么问题

复盘判断要交给未安装 NiceEval 的读者时，导出一份独立 Report artifact。
它包含已生成的页面、ReportExportPlan、资产和本次报告实际引用的可验证 evidence closure。

## 全流程

1. 先生成要交付的固定 Sample，并在本地确认对应 ReportDefinition：

   ```bash
   niceeval view --exp compare/candidate
   niceeval view --exp compare/candidate --out site
   ```

2. `--out` 先调用 `loadReportDefinition(entryModule)`，再调用
   `exportReport(frozenDefinition, { sample, sources, parameters, target })`。export 入口先用
   Sample-owned `validateMaterializedSample()` 验证 caller-supplied Sample。失败包装成带完整
   `SampleValidationError` cause 的 `report-sample-invalid`，此时尚未读取 target、Record source 或运行
   plan。

   验证通过后才固定 Record reader。
   loader 已冻结完整 module graph。executor 形成执行前 ReportPreparedPlan，执行所选 target 的
   Projector / Calculation，并只在内存中渲染一次页面树。trace 闭合后才生成 finalized
   ReportExportPlan；Store 写入纯 JSON page payload、最终 text / HTML、资产 bytes 与 proof index。

3. 输出目录包含 `index.html`、页面、`assets/`、`report-plan.json` 与 `evidence/` proof 文件。
   page 深链只指向 Plan 已枚举的 instance；无 JavaScript 时内容仍可读。

4. 将目录交给任意静态托管。
   `RecordEvidenceProofIndexV1` 让读者验证每条交付 event、object、Claim 或 absence evidence 的源 Graph、bytes 与 canonical path，而不是依赖一个可变源 Record。

   之后用 `openReportArtifact(store, ref)` 重开时，只校验内容摘要并读取已经保存的输出；不装载
   ReportDefinition，也不重新执行 plan、Projector、Calculation 或 renderer。

5. source reader 或 proof closure 失败时，本次 export 不留下 partial artifact，而是 reject
   `ReportArtifactError / report-evidence-closure-failed`。`phase` 区分 source 与 proof，`cause`
   完整保留对应的 `RecordSourceFailure` 或 `RecordEvidenceProofFailure`。

## 边界

- 站点是 Report artifact，不是 Record 或 SampleBundle。
- Report artifact Store、SampleBundle Store 和源 Record Store 相互独立。
- 每条源 Record 中已有、但无法复制或验证的 evidence 都会使导出失败；不能写成 `not-recorded`。
- Report 包装 Record owner failure，但不把其 code、operation、issues、retryable 或底层 cause 改写成 message / `unknown`。
- 导出范围由固定 Sample 决定。要改变成员，先 `narrowSample()` 或 `unionSamples()`，再导出。
- 不提供在浏览器中读取计划外 evidence 的旁路。
