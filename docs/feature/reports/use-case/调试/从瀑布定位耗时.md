# 瀑布里全是短节点：哪些值得看，时间去了哪

## 解决什么问题

Traces 页一行一个 attempt，一次五分钟的执行可能有几十个顶层 span，大半是几十毫秒的工具调用。
span 名来自被测 agent 自己的词表（`handle_tool_call_with_source` 这类），读报告的人判不出「这个节点相不相关」。
瀑布用 [显著性折叠](../../components/primitives/waterfall.md#显著性折叠短节点折成摘要) 替你收敛：失败的、测不出时长的、时长占比够大的节点直接列出，其余连续短节点折成一条带计数与合计时长的摘要。时间线数据在 plan 中由 Projector 声明，折叠只改变既有数据的显示。
清单只剩值得看的，分解条仍画全部事实。

## 全流程

1. 打开 view 的 Traces 页（标准报告的第三张导航页，[构成](../../library/built-in.md)）：

   ```bash
   niceeval view
   ```

每行一个 attempt：色带分解条画全部 span；行内清单只列显著节点，连续短节点折成
`tool ×5 · 合计 218ms` 一类摘要，展开即还原逐条。

2. 读法：先看长的 model 节点（采样占大头是常态），再看带失败标记的节点；摘要行的合计时长明显偏大时展开它——短节点多而合计大，多半是工具调用风暴。

3. 挑出可疑的 attempt，从行链接或 locator 下钻：

   ```bash
   niceeval show @01J4C6N8PQRS2TVWXY9ZABCD3M --timing
   ```

attempt 详情显示同一 ReportData 中的时间线投影（[数据源](../../components/attempt-detail/README.md)），瀑布仍是同一套折叠规则。

4. 要逐 span 明细时展开摘要即可；机器消费用 `--timing` 加 `--json`，JSON 恒保留完整树，不受清单折叠影响（[契约](../../show/timing.md)）。

## 边界

- 折叠判据只有可测显著性（失败、缺失、时长占比），niceeval 不按 span 名维护黑白名单。
  觉得某类节点根本不该采，那是被测 agent 采集面的事，见 [Observability](../../../../observability.md)。
- 失败节点与时长缺失的节点恒不折叠，不会因为「短」而被藏起来。
- 行总时长缺失时整行不折叠——没有占比基准，不猜值。
