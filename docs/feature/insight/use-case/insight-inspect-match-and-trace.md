# 在浏览器中审阅 Match 判据结果与 Trace 耗时瀑布图

## 用户目标

开发者在运行评测后发现一条用例被判定为 `failed`。她希望在浏览器中直观复核评测结果，明确：
1. 究竟是哪一项 Match 断言未通过？裁判模型给出的具体理由与打分快照是什么？
2. 整个交互链路中哪一步耗时最长？被测 Agent 发起的 Tool 调用是否传递了错误参数或发生了超时？
3. 被测 Agent 在工作目录内实际修改了哪些代码？

她希望开箱即用使用这些排查视图，不编写任何前端可视化代码。

## 起始状态

- 本机已经完成了一次评估运行，产生了一条失败的 Attempt（定位符 `@1VE05BR7061YN`）；
- 宿主机可用浏览器已就绪，已安装 NiceEval CLI。

## 完整路径

1. 在终端直接根据失败提示打开该 Attempt 的调试页面。 {#open-attempt}

   ```bash
   niceeval view @1VE05BR7061YN
   ```

   预期输出：浏览器自动打开，直接进入 `@1VE05BR7061YN` 的 Attempt debugger 页面。

2. 审阅预设的 Match 结果卡片。 {#inspect-match}

   - 页面顶部展示 Attempt 终态为 `failed`，并按顺序陈列全部 Match 卡片；
   - 发现前两项值断言（`includes`、`matches`）显示为绿色并通过；
   - 第三项 `judge(faithfulness)` 显示为红色且未通过质量门（Gate）；
   - 点击该卡片展开证据抽屉，直接查看已封存的裁判模型打分快照：
     * 模型给出的测量值：`0.3`（低于门禁要求的 `0.7`）；
     * 模型给出的理由文本：清晰指出了被测应用在回答中凭空编造了未经证实的交付日期。

3. 借助调用耗时瀑布图排查执行瓶颈与工具异常。 {#inspect-trace}

   - 切换至 **Trace & Waterfall** 视图，整条 Attempt 的时序树以瀑布流直观展开；
   - 瀑布图横轴为毫秒级时间线，纵向按层级展开 Sandbox 准备、Turn 交互与工具调用；
   - 观察发现：前两轮对话的推理延迟均在 1.2 秒内，但在第三轮中，一次名为 `run_tests` 的 Tool 调用耗时高达 28 秒且节点标红；
   - 单击该红色节点，侧边抽屉滑出该工具执行的详细上下文：
     * 输入参数：`{"cmd": "pytest tests/test_core.py"}`；
     * 标准错误输出：展示了测试执行失败的具体 Python 堆栈与超时信息；
     * 开发者立即明确失败根因是依赖项版本不兼容导致的测试崩溃。

4. 复核工作区文件修改补丁。 {#inspect-diff}

   - 点击 **Diff** 标签页，页面直接展示 Agent 在评测过程中产生的标准代码修改对比；
   - 逐行高亮展示了被修改文件的变更，无需切回终端运行 `git diff`。

## 结果

Match 结果卡片、Trace 耗时瀑布图与 Diff 比对均由 Insight 预设提供，零配置即可使用。
开发者无需自行配置图表或编写数据提取脚本，即可在单一页面中快速定位模型逻辑缺陷与底层工具执行故障。
