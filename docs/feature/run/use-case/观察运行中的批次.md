# 从另一个终端观察正在运行的批次

## 用户目标

一批评估要跑几十分钟。启动它的人，或者替他盯着的 coding agent，想在另一个终端知道每条 Attempt 现在走到哪一步，
卡住的是哪一条，以及怎样进到那台 Sandbox 里看现场。他不想解读滚动的运行日志。

## 起始状态

一个 `niceeval exp` 正在某个终端里运行。用户在同一个项目目录下打开了第二个终端。
本篇是预期用法，输出均为预期结果。

## 完整路径

1. 找到正在运行的 Invocation。 {#list}

   ```sh
   niceeval invocation list
   ```

   预期结果：列出仍在运行的 Invocation、它的进程号、最近一次 heartbeat，以及各 Experiment 的运行与排队数量。

2. 看每条已派发的 Attempt。 {#show}

   ```sh
   niceeval invocation show <invocation-id>
   ```

   预期结果：每条尚未发布的 Attempt 一行，写明 Experiment、Eval、序号、当前阶段与进入时间、Sandbox 的原生实例标识，
   以及最近一条进展和它的时间。排队中尚未派发的只按 Experiment 计数。

3. 判断哪一条不对劲。 {#judge}

   预期结果：阶段停在准备或安装、进入时间远早于其它 Attempt 的那一条值得先看。
   这些行是运行进程写下的观察值；进程被暂停时它们会停止前进，所以读的时候要看时间，不能只看文字。

4. 用 Provider 的原生命令进入现场。 {#attach}

   预期结果：用上一步给出的实例标识，经 Docker 或云 Provider 自己的命令行连进那台 Sandbox。NiceEval 不代理这次连接。

5. 结果发布后改用 locator。 {#after}

   ```sh
   niceeval show @<locator> --timing
   ```

   预期结果：已发布的 Attempt 不再出现在第 2 步的列表里；它的阶段耗时改由这条命令读取，阶段名称与运行中看到的一致。

## 结果

用户不读日志就知道批次的进度和卡点，并能直接进到出问题的现场。观察不会改变运行：它不加锁、不延长寿命、不接管。

| 情形 | 用户看到的结果与下一步 |
|---|---|
| 没有正在运行的 Invocation | 列表为空；加 `--all` 查看已经结束的 |
| Eval 不使用 Sandbox | 实例标识一栏写明没有 |
| 运行进程已经终止但 Run 仍为 `active` | 按[恢复中断运行](恢复中断运行.md)收口 |
| 需要给脚本或 agent 使用 | 加 `--json`，字段与文本输出相同 |
