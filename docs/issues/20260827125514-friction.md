# pr:body apply 改写测试源码中的反斜线 Unicode escape

## Actual observation

测试源码包含字面 `\u001b` 时，远端正文被改写为 `\^[[`；`apply` 返回成功，但每次 remote check 都报告正文 stale。

## Expected behavior

`pnpm pr:body apply --pr <number>` 应保留渲染正文里的测试源码字节，随后 remote check 应通过。

## Impact

受管 PR 创建会在远端 mutation 已发生后返回失败，重复 apply 也无法完成规定的远端验收；作者必须改写等价测试源码才能继续。

## Public entry-point reproduction

在 test directive 展开的源码中保留 `expect(raw).toContain("\u001b[31m")`，运行 `pnpm pr:body apply --pr <number>`，再比较 `pnpm pr:body render` 与 `gh pr view <number> --json body --jq .body`；远端该行成为 `expect(raw).toContain("\^[[31m")`。

## Follow-up evidence

2026-11-28 在 NiceEval `9cd14be3f`、Node 24.22.2 和 `gh` 2.105.0 上复现。完整测试源码包含字面的 `\u001b`。真实 `gh` 连接本地 GitHub API 替身，`pnpm pr:body apply` 写入后报告 `GitHub PR body is stale relative to the rendered draft`。

`gh pr edit --body-file` 发出的正文和替身返回的正文都保留 `\u001b`。`gh pr view --json body` 输出的正文却包含 `\^[[`。对同一替身运行 `gh api repos/fixture/test/pulls/101 --allow-escape-sequences` 得到同样的改写。

go-gh v2.17.0 在解析前对 JSON 响应运行 ASCII sanitizer，连表示字面反斜线的 `\\u001b` 也会被改写。`gh api --allow-escape-sequences` 只影响非 JSON 响应的输出。等待上游修复期间，`pr:body` 保持严格正文比较。把两种文本视为等价会漏报实际正文变化。[go-gh JSON 传输](https://github.com/cli/go-gh/blob/v2.17.0/pkg/api/http_client.go#L259-L273) · [go-gh ASCII sanitizer](https://github.com/cli/go-gh/blob/v2.17.0/pkg/asciisanitizer/sanitizer.go#L69-L95) · [gh API 输出](https://github.com/cli/cli/blob/v2.105.0/pkg/cmd/api/api.go#L541-L551)
