# ClearML schema、兼容与 migration

ClearML 没有一条统一的“产品 schema version”。
公开实现至少有 release、REST API、Mongo migration ledger、Mongo/Elasticsearch engine、index template 与离线 envelope 六条独立轨道。

## 版本轨道总表

| 轨道 | 版本载体 | 当前固定证据 | 是否直接改写已保存数据 |
| --- | --- | --- | --- |
| SDK / Server / Agent release | 各仓库独立 semver tag | SDK `2.1.11`、Server `2.4.0`、Agent `3.0.3` | release 本身不说明；Server 启动可触发 migration |
| REST API | auth token 的 `api_version`，request endpoint version | Server `v2.4` 最大 API `2.35`；SDK生成 `2.9/2.13/2.20/2.23` | 通常不；控制 reader/writer shape |
| Mongo schema | `backend.versions.num` | Server `v2.4.0` migration 文件最高 `1.9.0` | 是；多项脚本原地改 collection |
| Mongo engine / FCV | Mongo server version + featureCompatibilityVersion | compose `mongo:8.0.15`；启动检查 7.0→8.0 FCV | FCV 和外部 engine migration 会改变数据库格式 |
| Elasticsearch | engine version + component/index templates | compose `elasticsearch:8.19.9` | template install通常不重写旧文档；历史 ES migration 会 copy/reindex |
| Task / Event / Artifact / Report object | 公开字段 | 没有发现对象内 `schemaVersion` / revision 字段 | 依赖兼容 API 与全库 migration，而非逐对象升级 |
| offline session | zip 内固定文件名 | `task.json`, `metrics.jsonl`, `log.jsonl`, `data/` | importer 重新发送持久事件并创建或更新 Server 数据；包内无显式版本 |
| Dashboard App | 未公开 | Pro 文档只披露 JSON config import/export | 未公开，无法验证 |

Server release 与 API 对应表由
[`apiserver/documentation/api_versions.md`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/documentation/api_versions.md) 固定。
Server `v2.4.0` commit message 也声明 API `v2.35`。

## SDK 与 REST API compatibility

### 协商

Server签发 token 时写 `api_version`、`server_version`、`server_build` 与 `feature_set`。
SDK `Session` 读取这些值；没有值时最低默认 API 是 `2.9`。

`ApiServiceProxy` 扫描 SDK 内生成目录，选出“不高于 Server 能力的最高本地版本”。
SDK `v2.1.11` 只有 `v2_9`、`v2_13`、`v2_20`、`v2_23`，所以连接 API 2.35 Server 时使用本地 `v2_23` models，而不是凭空生成 2.35 class。

证据：
[`server/apiserver/bll/auth/__init__.py`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/bll/auth/__init__.py)、
[`SDK Session`](https://github.com/clearml/clearml/blob/v2.1.11/clearml/backend_api/session/session.py)、
[`ApiServiceProxy`](https://github.com/clearml/clearml/blob/v2.1.11/clearml/backend_api/api_proxy.py)。

### compatible reader

生成的 API classes 继承 `NonStrictDataModel`。
`from_dict(..., strict=False)` 默认丢弃未知 response keys；这允许旧 SDK 读取带新增字段的 response，而不会把未知字段保存在本地 model。
实现见
[`backend_api/session/datamodel.py :: NonStrictDataModel.from_dict`](https://github.com/clearml/clearml/blob/v2.1.11/clearml/backend_api/session/datamodel.py)。

功能仍需显式 gate：

| 最低 API | SDK 行为 |
| --- | --- |
| `2.9` | multiple configuration 可读；旧版调用 `get_configuration_objects` 抛 `ValueError`；user properties 则写 info 日志后返回 `{}` |
| `2.20` | single-value read；旧版 `get_reported_single_values` 抛 `ValueError` |
| `2.23` | Event request 可带 `model_event` |

这些 gate 在
[`backend_interface/task/task.py`](https://github.com/clearml/clearml/blob/v2.1.11/clearml/backend_interface/task/task.py)、
[`clearml/task.py`](https://github.com/clearml/clearml/blob/v2.1.11/clearml/task.py)
与 [`metrics/interface.py`](https://github.com/clearml/clearml/blob/v2.1.11/clearml/backend_interface/metrics/interface.py) 中可核查。

Server `reports.*` 在 `v2.4.0` 和官方 REST reference 中公开，但 SDK `v2.1.11` 的生成 services 没有 `reports.py`。
这不是 Server schema 不存在，而是 Python SDK surface 未提供同级 proxy / model。
可直接核对 [Reports API](https://clear.ml/docs/latest/docs/references/api/reports/) 与
[`SDK backend_api/services`](https://github.com/clearml/clearml/tree/v2.1.11/clearml/backend_api/services)。

固定 docs commit 中的
[`docs/references/api/reports.md`](https://github.com/clearml/clearml-docs/blob/53782832efce804072879f107ab148218ba07536/docs/references/api/reports.md)
只是 `AutoGenerated PlaceHolder`；live 文档站在构建时生成正文。
因此 placeholder 不能用来推导“没有 Reports API”，Server service source 与 live reference 才是该资源的公开证据。

## Mongo migration runner

Server 启动初始化会调用
[`apiserver/mongo/initialize/migration.py :: _apply_migrations`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/mongo/initialize/migration.py)。
它的真实算法是：

1. 读取 `backend.versions` 中最大的 `num`；没有则视为 `0.0.0`。
2. 扫描 `apiserver/mongo/migrations/*.py`，从文件名提取版本号。
3. 按版本升序，对 auth / backend DB 调用脚本存在的 `migrate_auth` / `migrate_backend`。
4. 每个脚本完成后向 `versions` 写 `num`、`created`、`desc='Applied on server startup'`。
5. migration 失败即 abort，并明确要求 restore backup。

如果数据库被判断为空，runner 跳过脚本内容，但仍为每个版本写 ledger。
它没有公开 dry-run、逐 migration rollback 或全脚本事务；脚本普遍逐文档 `update_one`，中途失败可能留下部分改写，恢复路径是部署前备份。

ledger model 是
[`apiserver/database/model/version.py :: Version`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/database/model/version.py)。
它只保存 migration version 和启动时间，不保存每个 Task 的迁移 receipt。

正式目录是
[`apiserver/mongo/migrations`](https://github.com/clearml/clearml-server/tree/v2.4.0/apiserver/mongo/migrations)。
下表列出除共用函数文件 `utils.py` 外的全部版本文件。

| [`0.12.1`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/mongo/migrations/0_12_1.py) | 对 project/task/model 的 `tags` 重新 partition 为 user `tags` 与 `system_tags` | 是，原地重写 tags |
| [`0.13.0`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/mongo/migrations/0_13_0.py) | backend user `preferences` object JSON-stringify；auth user drop indexes | 是，重写 preferences；另重建索引 |
| [`0.14.0`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/mongo/migrations/0_14_0.py) | 切换 fixed-user IDs，并重写 project/task/model 的 `user` refs | 是，重写身份与引用 |
| [`0.15.0`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/mongo/migrations/0_15_0.py) | 排序 task/model/project/queue 的 tags/system_tags；drop backend/auth indexes | 是，数组顺序改变；另重建索引 |

| [`1.0.2`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/mongo/migrations/1_0_2.py) | 删除符合固定模式的 auto-generated Project descriptions | 是，删除生成内容 |

| [`1.6.0`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/mongo/migrations/1_6_0.py) | 从 Project name 最后一段派生缺失 `basename` | 是，写持久派生值 |
| [`1.7.0`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/mongo/migrations/1_7_0.py) | 把 auth user `created` 复制到缺字段的 backend user | 是，补用户 metadata |
| [`1.9.0`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/mongo/migrations/1_9_0.py) | drop Task text index，使 model 定义重建包含 `report` 的 text index | 否，不改 Task body；改变索引 |

这些脚本说明，ClearML 的 Server migration 不只是内部 metadata 记账。
它会修改用户保存的 Task、Project、Model、Queue 与 user 文档；有些复制兼容字段，有些重排，有些删除旧字段或生成描述。

## Mongo engine 与 FCV

Server `v2.4.0` 的
[`docker/compose.yaml`](https://github.com/clearml/clearml-server/blob/v2.4.0/docker/compose.yaml)
固定 `mongo:8.0.15`。
启动 `_ensure_mongodb_version` 只在检测到 Mongo `8.0.x` 且 FCV 为 `7.0` 时执行：

```text
setFeatureCompatibilityVersion: 8.0, confirm: true
```

若 engine 不是 8.0，runner 只 warning；若 FCV 既不是 7.0 也不是 8.0，也只 warning。
这不是任意旧 Mongo 到 8.0 的通用迁移器。

滚动升级文档仍写“v2.x 从 Mongo 5.x 升到 6.x”，与固定 Server `v2.4.0` compose 和启动代码冲突。
本研究以 tag 源码的 8.0.15 / FCV 8.0 为当前事实，并把滚动页视为未同步的部署说明。

历史上 v1.1 以前到 v1.2 的正式流程是 Mongo 3.6→4.0→4.2→4.4，先备份 / copy 数据目录，再逐 engine 调 FCV。
官方页面：[Mongo 4.4 migration](https://clear.ml/docs/latest/docs/deploying_clearml/clearml_server_mongo44_migration/)。

## Elasticsearch schema 与 migration

Server `v2.4.0` compose 固定 `elasticsearch:8.19.9`。
启动工具
[`apiserver/elastic/apply_mappings.py :: apply_mappings_to_cluster`](https://github.com/clearml/clearml-server/blob/v2.4.0/apiserver/elastic/apply_mappings.py)
安装 component templates 与 index templates，并删除同名 legacy templates。

这条路径没有类似 `backend.versions` 的 Event schema ledger，也不遍历已有 Event 文档做逐对象 rewrite。
Event 本身没有 `schemaVersion`；reader 依赖 index mapping、字段兼容与 Plot 解压逻辑。

历史 Trains Server ≤0.15 的正式 ES 迁移不同：ES 5.6→7.6 脚本备份旧数据，启动 ES5/ES7 migration containers，copy/reindex indices，终止 containers，并重命名旧目录。
完成后旧 Trains Server 不能再读取这些数据。
官方页面：[ES7 migration](https://clear.ml/docs/latest/docs/deploying_clearml/clearml_server_es7_migration/)。

因此“template update”和“engine major migration”不能混为一谈：前者主要约束新 index / mapping，后者会复制并改变用户保存的 Event index。

## 官方 Docker 升级命令与数据影响

[Linux/macOS 升级文档](https://clear.ml/docs/latest/docs/deploying_clearml/upgrade_server_linux_mac/)给出的主流程是：

```bash
docker-compose -f docker-compose.yml down
# 备份 data 与非空 config
# 旧版本先执行适用的 ES / Mongo 前置 migration
curl https://raw.githubusercontent.com/clearml/clearml-server/master/docker/docker-compose.yml \
  -o /opt/clearml/docker-compose.yml
docker-compose -f /opt/clearml/docker-compose.yml pull
docker-compose -f /opt/clearml/docker-compose.yml up -d
```

这是官方滚动命令，不是本研究建议的可复现 pin；它从 `master` 下载最新 compose。
启动新 API Server 会自动跑尚未登记的 Mongo migration，并可能提升 FCV。

官方要求先停服并备份，原因与源码一致：migration 是原地、非全局事务式改写；失败消息要求 restore backup。
Mongo / ES major version前置流程还会 copy、转换或 reindex 数据目录。

## fileserver、Report 与项目迁移

Mongo migration 只改 descriptor / URL 字段，不会自动转换 fileserver 或外部对象存储 bytes。
一般升级保留 `/opt/clearml/data/fileserver` volume；URI 能否继续定位 payload 取决于 host、路径与 storage 配置。

官方 Enterprise project migration 要求把 fileserver 内容复制到目标 company/project 路径。

Open Server 的 source folder 是 `${CLEARML_ROOT}/data/fileserver/<project name>`。
Enterprise source 与目标路径是 `${CLEARML_ROOT}/data/fileserver/<company_id>/<project name>`。

如果 server address 改变，还要求在 Mongo `backend.task` 中对 `report` 和 `report_assets` 做 URL find-and-replace，并更新 `project.description`。
[Importing Projects / Fixing Registered URLs](https://clear.ml/docs/latest/docs/deploying_clearml/enterprise_deploy/import_projects/#fixing-registered-urls)给出正式 `mongosh updateMany`。

这不是普通启动 migration，而是跨 Server 项目迁移的人工步骤。
它证明 Report 保存了可受部署地址影响的 URL，并且迁移会实质重写用户 Report Markdown / assets refs。

## 对象版本与离线 envelope

在固定公开 types 中：

- Mongo `Task`、`Model`、embedded `Artifact` 没有 `schemaVersion`；
- Elasticsearch Event 没有 `schemaVersion`；
- Report 复用 Task，`published` 是编辑锁状态，不是 content schema revision；
- offline zip 没有 manifest 或 package version 字段。

SDK 离线 importer 直接读取固定文件名，用当前 API models 读取其中对象后重新发送。
`NonStrictDataModel` 能忽略未知 Task keys，但没有离线 migration registry；字段被删除、改语义或文件布局变化时，没有公开的版本分派点。
实现见
[`Task.import_offline_session`](https://github.com/clearml/clearml/blob/v2.1.11/clearml/task.py)。

Dataset 的业务 version、Model 的 parent lineage、Task status 或 Report publish 不应被误称为持久 schema version；它们解决的是产品对象生命周期，不是 reader compatibility。

## 持久派生值为何扩大 schema churn

[storage.md](storage.md)列出的 `last_metrics`、`unique_metrics`、`metric_stats`、`active_duration`、Artifact hash/size、Project `basename` 与 Plot 压缩字段都可从更细事实或 payload 计算，却被持久化。

好处是 Task filter、排序、Project Overview 和比较页不必扫描完整 Event。
代价是 shape 或算法改变会要求 migration、summary rebuild 或 index rebuild；`0.17.0`、`1.6.0`、`1.9.0` 已分别展示这种成本。

读取时 smoothing、axis 变换、group / overlay、hide-identical 与 Report dynamic query 没有写回 Task / Event，因而通常不触发用户数据 migration。

## 未公开或不能验证的边界

- ClearML Hosted / Enterprise 后端相对开源 Server 的私有 migrations、回滚和备份自动化未公开。
- Project Dashboard Pro App 的服务端 schema、版本、compat reader 与 migration 未公开。
- 官方没有公开“某次 migration 已逐对象完整完成”的 receipt，也没有 Task/Event 级 downgrade reader。
- 公开 upgrade 文档与 Server `v2.4.0` 对 Mongo major version存在冲突；没有官方说明解释该文档为何仍写 Mongo 6。
- offline archive 没有显式 version；未来版本之间的长期兼容矩阵未公开。

以上边界只列出未公开事实，不推测 SaaS 内部实现。
