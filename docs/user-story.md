# 用户故事地图

本文把 Feature、已裁决 Design 与 Roadmap 中的用户目标整理成 Epic 和普通用户故事。
它回答谁想获得什么结果，以及这个结果为什么有价值。

用户故事不定义 API、CLI、数据形状或内部边界，具体契约仍以每组故事链接的来源文档为准。
每条普通故事都可以独立阅读和验收；编号只用于追踪，不表示执行顺序或依赖关系。

## 角色

| 角色 | 关注点 |
|---|---|
| AI 应用团队 | 让真实 Agent 接受评估，并改进其表现 |
| Eval 作者 | 把领域任务、材料与成功标准写成 Eval |
| Experiment 负责人 | 组织运行条件、范围、成本与可比性 |
| 集成与运行维护者 | 接入 Agent、管理环境，并维护 CI 或长批次运行 |
| 分析与报告作者 | 选择可信数据、解释结果并制作报告 |
| 决策者 | 根据质量、成本与可靠性选择方案 |
| 安全与审计负责人 | 控制运行风险，并复核结论依据 |
| NiceEval 贡献者 | 维护公开行为及其证明 |

## 产品目标故事

本节来自 Feature 契约与 Design 已采纳方案的用户可观察结果。
Design 只补充用户价值，不把候选架构带进故事。

### E1 让真实 AI 系统进入统一评估

**Epic：**作为 AI 应用团队，我希望按真实交互方式评估已有 Agent，从而让结果代表用户实际使用的系统。

- **US-1.1** 作为 AI 应用团队，我希望通过 Agent 正式支持的交互方式参加评估，从而无需为评估改造业务协议。
- **US-1.2** 作为 Eval 作者，我希望同一套 Eval 能评估不同 Agent，从而公平比较替代方案。
- **US-1.3** 作为 Eval 作者，我希望以一致含义观察交互、行为和资源使用，从而复用同一套判据与分析。
- **US-1.4** 作为 Eval 作者，我希望评估多轮交互与人工介入，从而覆盖真实任务中的完整行为。
- **US-1.5** 作为集成与运行维护者，我希望 Agent 无法在目标环境正常运行时提前得到明确说明，从而避免环境缺失造成无效结论。

来源：[Agents 与 Adapters](feature/adapters/README.md)、[Agent Ensure](feature/adapters/architecture/agent-ensure.md)。

### E2 把领域任务写成可信 Eval

**Epic：**作为 Eval 作者，我希望用独立于 Agent 的方式描述任务和成功标准，从而持续复用并审查评估意图。

- **US-2.1** 作为 Eval 作者，我希望 Agent 看到完成任务所需材料但看不到隐藏判据，从而兼顾真实上下文和判分公平。
- **US-2.2** 作为 Eval 作者，我希望一份评估意图覆盖多条稳定可识别的案例，从而扩展测试范围而不产生复制漂移。
- **US-2.3** 作为 Eval 作者，我希望评价最终结果、执行过程和资源使用，从而避免只看答案表面。
- **US-2.4** 作为 Eval 作者，我希望按任务性质评价完成与部分完成，从而让结果表达真实进展。
- **US-2.5** 作为 Eval 作者，我希望开放式结果能依据清楚且可审查的标准获得评价，从而衡量难以用固定规则描述的质量。
- **US-2.6** 作为 Experiment 负责人，我希望任务失败、执行错误、跳过和证据不足彼此可辨，从而正确解释和使用结果。

来源：[Eval](feature/eval/README.md)、[Assertions](feature/assertions/README.md)、[Judge](feature/judge/README.md)、[Verdict](feature/verdict/README.md)。

### E3 在真实且受控的环境中运行

**Epic：**作为 Eval 作者，我希望 Agent 在忠于题目且受控的环境中完成任务，从而兼顾安全、复现与结果公平。

- **US-3.1** 作为安全与审计负责人，我希望 Agent 的命令和文件操作与宿主机隔离，从而限制一次评估的影响范围。
- **US-3.2** 作为 Eval 作者，我希望每道题都在符合题意的环境中运行，从而在迁移和复用时保持任务语义。
- **US-3.3** 作为 Eval 作者，我希望任务原有的多服务条件保持原意，从而避免环境翻译或裁剪改变题目。
- **US-3.4** 作为 Eval 作者，我希望依赖服务就绪后 Agent 才开始，且服务持续到判分完成，从而不把环境故障算成 Agent 表现。
- **US-3.5** 作为 Experiment 负责人，我希望所选 Agent 能进入任务环境，而不必为每种 Agent 制作环境副本，从而低成本迁移真实题目。
- **US-3.6** 作为集成与运行维护者，我希望不受支持的环境组合在执行前说明原因，从而不产生假失败或空跑成功。
- **US-3.7** 作为集成与运行维护者，我希望运行结束后完整回收相关资源，从而不遗留失控环境。
- **US-3.8** 作为集成与运行维护者，我希望在运行环境支持时保留完整失败现场，从而验证落盘证据无法回答的假设。

来源：[Sandbox](feature/sandbox/README.md)、[Environment Model 决策](design/environment-model/DECISION.md)、[Agent 安装配方决策](design/agent-install-recipe/DECISION.md)、[多容器环境决策](design/multi-container-environments/DECISION.md)。

### E4 运行可比且经济的 Experiment

**Epic：**作为 Experiment 负责人，我希望在明确的成本和时间内比较不同条件，从而更快得到仍然可信的结论。

- **US-4.1** 作为 Experiment 负责人，我希望用同一批 Eval 比较不同运行条件，从而把表现差异归因到有意改变的变量。
- **US-4.2** 作为 Experiment 负责人，我希望在执行前确认并收窄范围，从而避免误跑和无谓消耗。
- **US-4.3** 作为 Experiment 负责人，我希望一次运行遵守团队的资源约束，从而在可接受成本内获得足够证据。
- **US-4.4** 作为 Experiment 负责人，我希望可信且未受变化影响的历史结果可以继续使用，从而把资源留给真正变化的部分。
- **US-4.5** 作为 Experiment 负责人，我希望相互独立的任务安全并行，从而缩短等待时间而不互相污染。
- **US-4.6** 作为 Experiment 负责人，我希望减少重复准备，同时让每道题从可接受的干净状态开始，从而安全缩短运行时间。
- **US-4.7** 作为集成与运行维护者，我希望长批次任务不进入即将失效的环境，从而避免可预见的中途失败。
- **US-4.8** 作为集成与运行维护者，我希望自动化稳定读取计划、进度和结果，从而维护 CI 与自动修复循环。

来源：[Experiments](feature/experiments/README.md)、[实验加速决策](design/experiment-speed/DECISION.md)、[提高评估速度](feature/use-case/提高评估速度/README.md)。

### E5 在故障时恢复并止损

**Epic：**作为集成与运行维护者，我希望不同故障得到恰当处理，从而恢复可恢复工作并停止重复撞上同一问题。

- **US-5.1** 作为集成与运行维护者，我希望瞬时外部故障得到有限恢复机会，从而减少偶发基础设施问题造成的整批失败。
- **US-5.2** 作为 Experiment 负责人，我希望已知致命问题出现后停止受影响的后续工作，从而避免重复消耗。
- **US-5.3** 作为集成与运行维护者，我希望看见恢复、耗尽与停止的原因，从而知道下一步修复什么。
- **US-5.4** 作为分析与报告作者，我希望基础设施故障不被计入 Agent 的任务表现，从而保持质量结论公平。

来源：[执行失败分类](feature/error-classification/README.md)。

### E6 保留可审计结果并选出可信 Sample

**Epic：**作为分析与报告作者，我希望知道结论来自哪些运行事实和选择口径，从而能够复核、交换和重新分析。

- **US-6.1** 作为安全与审计负责人，我希望每次运行的条件、判定、诊断与证据完整保存，从而能够复核历史结论。
- **US-6.2** 作为集成与运行维护者，我希望评估结果搬到另一处后仍可独立读取和复核，从而与第三方系统交换结果。
- **US-6.3** 作为分析与报告作者，我希望选择数据时同时看到范围、覆盖和问题，从而避免误用不完整数据。
- **US-6.4** 作为分析与报告作者，我希望区分真实执行、结果沿用、未完成与跳过，从而准确理解一次运行做了什么。
- **US-6.5** 作为安全与审计负责人，我希望每个汇总数字都能追溯到具体 Attempt，从而验证指标背后的证据。

来源：[Record](feature/record/README.md)、[Sample](feature/sample/README.md)、[Reading](feature/reading/README.md)。

### E7 快速定位、修复并复验问题

**Epic：**作为 AI 应用团队，我希望从失败结论快速到达可行动证据，从而缩短修复与复验循环。

- **US-7.1** 作为 AI 应用团队，我希望从失败摘要到达源码、执行过程、耗时和文件变化，从而定位根因。
- **US-7.2** 作为分析与报告作者，我希望查看同一任务的历史表现，从而区分偶发问题与稳定回归。
- **US-7.3** 作为集成与运行维护者，我希望在失败现场反复验证假设，从而避免为每次检查重新运行昂贵任务。
- **US-7.4** 作为 AI 应用团队，我希望自动完成运行、读取失败、修改和复验，从而缩短 Agent 改进循环。

来源：[调试评估](feature/use-case/调试评估/README.md)、[报告调试用例](feature/reports/use-case/调试/README.md)、[机器输出用例](feature/experiments/use-case/机器输出/README.md)。

### E8 把结果转化为可分享的决策

**Epic：**作为决策者，我希望从可信结果中看见方案取舍，从而选择方向并把依据交付给不同受众。

- **US-8.1** 作为决策者，我希望比较不同方案的质量、成本与可靠性，从而选择更合适的方案。
- **US-8.2** 作为分析与报告作者，我希望识别运行条件与结果差异的关系，从而解释方案表现为何不同。
- **US-8.3** 作为分析与报告作者，我希望每道题在汇总中获得公平权重，并区分无法测量与未覆盖，从而避免缺口或重复次数扭曲结论。
- **US-8.4** 作为分析与报告作者，我希望按团队问题组织分析并加入必要的业务上下文，从而制作有针对性的报告。
- **US-8.5** 作为决策者，我希望不同阅读方式表达相同的数据和口径，从而得到一致结论。
- **US-8.6** 作为分析与报告作者，我希望以适合受众的形式交付结果，从而让结论进入团队的决策流程。

来源：[Reports](feature/reports/README.md)、[Report Authoring 决策](design/report-authoring/DECISION.md)、[Reading 用例](feature/reading/use-case/README.md)。

## 贡献者目标故事

这一节面向 NiceEval 仓库贡献者，不属于产品终端用户能力。

### C1 让用户可见行为容易理解和验证

**Epic：**作为 NiceEval 贡献者，我希望测试直接说明用户任务和可观察结果，从而判断改动是否破坏公开行为。

- **CS-1.1** 作为 NiceEval 贡献者，我希望从用户动作、目标对象与预期结果读懂测试，从而无需先阅读生产实现。
- **CS-1.2** 作为 NiceEval 贡献者，我希望公开行为与内部机制各自得到准确证明，从而让内部重构不扰动用户故事。
- **CS-1.3** 作为 NiceEval 贡献者，我希望每个用户行为都有清楚的证明范围，从而知道一次通过能够支持什么结论。
- **CS-1.4** 作为 NiceEval 贡献者，我希望失败指出行为身份、观察来源和证据位置，从而准确定位并单独复验。

来源：[用户可读测试决策](design/user-readable-testing/DECISION.md)。

## 产品 Roadmap 候选故事

本节只保留尚未定稿方向中的稳定用户问题。
它们不是产品承诺；开放分歧与候选形状仍以 Roadmap 原文为准。

### R1 让新的 Agent 平台成为可信被测对象

**Epic：**作为 AI 应用团队，我希望具备稳定且受支持官方编程接口的平台可以接入评估，从而延续已有 Eval 和分析资产。

- **US-R1.1** 作为 Eval 作者，我希望接入后仍能观察会话延续、人工介入、行为和资源使用，从而评估真实连续交互。
- **US-R1.2** 作为 AI 应用团队，我希望能力不足的平台明确保持不支持，从而避免脆弱接口制造不可信结论。

来源：[Adapter Roadmap](roadmap/adapters/README.md)。

### R2 让 Agent 进程拥有公平的生命周期

**Epic：**作为 Eval 作者，我希望进程寿命与退出含义保持一致，从而不把运行环境行为误算成 Agent 表现。

- **US-R2.1** 作为 Eval 作者，我希望 Agent 正常结束后启动的服务仍能活到判分完成，从而避免执行会话关闭造成假失败。
- **US-R2.2** 作为集成与运行维护者，我希望超时、中断或保留现场前停止失控进程，从而停止额外消耗并保护证据一致性。
- **US-R2.3** 作为分析与报告作者，我希望异常退出被视为执行问题，并在可恢复时获得有限重试，从而不污染任务失败率。

来源：[Agent 进程契约](roadmap/agent-process-contract/README.md)。

### R3 评估多 Agent 系统的归属与互动

**Epic：**作为 Eval 作者，我希望看清每个 Agent 的职责、交接和互动，从而判断团队协作是否正确。

- **US-R3.1** 作为 Eval 作者，我希望在归属证据完整时按 Agent 检查做过和没有做过的行为，从而可信验证职责分工与越权行为。
- **US-R3.2** 作为 Eval 作者，我希望区分委派与控制权交接，从而判断实际协作路径是否符合预期。
- **US-R3.3** 作为 Eval 作者，我希望主被测 Agent 能与角色明确的模拟对手多轮互动，从而评估客服或谈判等任务。
- **US-R3.4** 作为分析与报告作者，我希望主被测与模拟对手的成本分开呈现，从而不把评估开销算成被测成本。

开放边界：模拟对手是否随 Experiment 条件变化、循环交接是否支持完整轨迹、嵌套多 Agent 的归属范围仍待裁决。

来源：[Multi-Agent Evals](roadmap/multi-agent/README.md)。

### R4 解释结果沿用与 Sandbox 复用

**Epic：**作为 Experiment 负责人，我希望知道哪些结果没有执行、哪些 Attempt 复用了 Sandbox，从而正确理解速度与风险。

- **US-R4.1** 作为分析与报告作者，我希望明确区分结果沿用与 Sandbox 复用，从而知道哪些 Attempt 真实执行过。
- **US-R4.2** 作为集成与运行维护者，我希望看见复用 Sandbox 的规模与更换情况，从而发现异常轮换。
- **US-R4.3** 作为集成与运行维护者，我希望人读反馈与机器输出使用相同语义，从而让自动化和人工判断一致。
- **US-R4.4** 作为集成与运行维护者，我希望术语变化不会静默改变计数含义，从而及时迁移既有自动化。

开放边界：是否单列环境准备失败，仍会影响用户能否区分容量、创建与正常更换问题。

来源：[结果携带与 Sandbox 复用反馈](roadmap/reuse-feedback/README.md)。

## 贡献者 Roadmap 候选故事

这一节只细化 C1 在 Report E2E 观察面上的候选需求，不属于产品承诺。

### CR1 让 Report 验收关注用户结果

**Epic：**作为 NiceEval 贡献者，我希望按公开对象和用户结果表达 Report 预期，从而让外观调整不制造无关回归。

- **CS-R1.1** 作为 NiceEval 贡献者，我希望按对象身份、状态和关系表达预期，从而不依赖文案、排版或内部结构。
- **CS-R1.2** 作为 NiceEval 贡献者，我希望从真实公开入口和独立预期验证结果，从而避免候选实现自己证明自己正确。
- **CS-R1.3** 作为 NiceEval 贡献者，我希望复用同一次真实运行验证多个观察面，从而减少昂贵运行并保持证据一致。
- **CS-R1.4** 作为 NiceEval 贡献者，我希望失败指出目标对象和证据位置，从而快速定位并单独复验。

这一方向需要按用户可读测试决策重定基线，只保留 Report 观察面的候选需求。

来源：[E2E 验收断言 Roadmap](roadmap/e2e-acceptance-dsl/README.md)、[用户可读测试决策](design/user-readable-testing/DECISION.md)。
