# 用户故事地图

本文记录具体人物在真实工作中想完成什么、希望怎样完成，以及这样做对他们有什么价值。
它不描述由谁提供能力，也不规定实现方式。

人物姓名、公司与业务产品是具名的代表性设定，不表示这些公司是实际客户。
MemoryBench 与 TerminalBench 的场景来自真实项目；两者面对的工作不同，因此分别叙述。

## 林书雅：回答 memory 是否真的改善 coding agent

MemoryBench 的重点是比较实验条件，而不是让每道题各自配置一套 memory。
林书雅希望任务本身保持轻量和稳定，把 memory、模型、Agent、状态延续方式与运行顺序放在不同的对比组中管理。

- **MB-1 只改变 memory 条件。** 林书雅希望同一轮比较固定任务、模型、Agent、判分和起始环境，只替换无 memory、RecallKit 或其它 memory 条件，这样她才能把结果差异归因给 memory。
- **MB-2 让任务独立于 memory 产品。** 林书雅希望每道题只说明要修改哪个固定版本的仓库、要完成什么工作以及怎样算完成，不引用 RecallKit 或其它 memory 产品，这样新增对比条件时不必复制和改写题目。
- **MB-3 为每个对比组准备合适的起点。** 林书雅希望无 memory 组从普通环境开始，RecallKit 组从已准备好对应工具的环境开始，同时让两组看到完全相同的任务材料，这样环境准备不会偷偷改变题意。
- **MB-4 按条件延续状态。** 林书雅希望需要累积 memory 的对比组按固定顺序载入、使用和保存状态，不需要累积状态的对比组仍可并行，这样共享状态不会被交错运行污染。
- **MB-5 单独处理少数重环境任务。** 某道题需要数据库或多个服务时，林书雅希望只为这道题提供完整环境；如果某个 memory 条件无法进入该环境，就在运行前明确排除这个组合，而不是换成一个不等价的简化环境。
- **MB-6 对所有条件使用同一判分。** 林书雅希望 Agent 在工作时看不到隐藏判据，并让每个 memory 条件接受相同的最终检查，这样 memory 产品无法通过接触额外信息获得优势。
- **MB-7 不把服务故障算成 Agent 失败。** memory 服务暂时断连时，林书雅希望先做有限恢复；确认共享服务不可用后，她希望停止继续消耗剩余任务，同时把这些结果与真正的任务失败分开。
- **MB-8 同时看收益与代价。** 林书雅希望按 memory 条件比较完成率、耗时、对话轮次、工具调用、token、成本和重复试错，并能回到异常任务查看过程，这样团队能判断收益是否值得额外开销。
- **MB-9 只重做受变化影响的部分。** 林书雅修改一道题或一个 memory 条件后，希望重新运行受影响的组合，继续使用其它仍然可比的历史结果，这样一次小改动不会触发整套昂贵实验。

## 陈砚舟：忠实运行 TerminalBench，而不是重写相似题

TerminalBench 的重点在每道题自己的运行环境。
不同题目依赖不同镜像、服务、起始文件、隐藏测试和时间预算；把它们压成一套公共环境会改变题目。

- **TB-1 从原始题库持续更新。** 陈砚舟希望直接从锁定版本的 TerminalBench 题库读取题面、标签、时间预算、环境材料、官方测试和参考答案，这样题库升级时不用人工维护数百份容易漂移的副本。
- **TB-2 让每道题带着自己的环境。** 陈砚舟希望数据库题、Python 题和多服务题各自使用原题要求的完整环境，这样 Agent 面对的困难与官方题目一致。
- **TB-3 更换 Agent 时不改题目。** 陈砚舟希望把 PatchPilot、Codex 或 Claude Code 分别放进同一批题目的环境，而不是为每个 Agent 复制题库，这样差异来自 Agent，而不是迁移出来的环境副本。
- **TB-4 把隐藏测试留到最后。** 陈砚舟希望 Agent 完成工作后才出现官方测试，并让参考答案始终不可见，这样 Agent 只能根据题面解题，不能针对判分脚本投机。
- **TB-5 保留官方判分。** 陈砚舟希望最终结果由原题的官方测试决定，而不是由 Agent 是否正常退出决定，这样“顺利结束但答案错误”仍然算任务未完成。
- **TB-6 在花费模型额度前确认可运行。** 陈砚舟希望先看清哪些题能够运行、哪些题缺少环境、哪些 Agent 无法进入目标环境以及具体原因，这样不会在批次中途才发现前面的投入无效。
- **TB-7 尊重每道题的时间预算。** 陈砚舟希望普通运行沿用原题给 Agent 和测试的时间，临时排查时再统一缩短上限，这样长任务不会被误杀，快速检查也不会无限等待。
- **TB-8 先用官方答案验证评测链。** 陈砚舟希望在花钱测试 Agent 前，用官方参考答案走一遍相同环境和判分过程，这样可以先发现环境、起始文件或测试挂载本身的问题。
- **TB-9 用同一口径比较 Agent。** 陈砚舟希望不同 Agent 跑相同题目后，按任务完成、耗时、成本和执行过程比较，并能回到具体失败查看证据，这样团队可以解释谁更好以及为什么。

## 唐诗涵：评价开放式对话，而不是强行匹配文字

小问既要答对，也要用适龄方式引导学生思考。
唐诗涵希望不同要求使用与证据相称的评价方式，而不是把所有质量都压成一个模糊分数。

- **TUT-1 按真实教学过程测试。** 唐诗涵希望覆盖单轮问答、多轮追问、并行学生会话和等待教师批准后继续的流程，并把评价对应到具体一轮或整段辅导，这样不同学生的上下文不会混在一起。
- **TUT-2 确定事实用确定规则。** 唐诗涵希望用明确规则检查计算答案、资料引用、工具顺序、禁止行为、最终产物和成本上限，这样失败时可以直接指出哪项事实不符合要求。
- **TUT-3 有意义的进展给部分分。** 一道五步教学任务完成三步时，唐诗涵希望记录已经完成的三步；只有完整完成才有意义的任务仍按通过或未通过计算，这样结果能反映真实进展，而不是掩盖在一个总状态里。
- **TUT-4 开放式质量交给独立裁判。** 唐诗涵希望用独立裁判模型评价讲解是否适龄、是否切题和是否泄露答案，并让裁判只看到指定的回复或对话，这样评价材料和标准都能被复核。
- **TUT-5 分开安全底线与体验目标。** 唐诗涵希望危险建议和泄露答案始终阻止发布，语言亲切或表达简洁作为可逐步提高的质量目标，探索性评价缺失时也不应伪装成通过或失败。
- **TUT-6 裁判不可用时保留其它结果。** 判分服务不可用时，唐诗涵希望在运行开放式讲解题前得到提示，同时继续完成只依赖确定规则的数学题，这样一个外部服务故障不会没收整批证据。

## 周芷宁：在发布前选出更合适的 Agent 配置

周芷宁每周要决定 CodeMate 使用哪个 Agent、模型和推理强度。
她不能只看一次通过率，因为更好的配置可能成本翻倍、尾部耗时过长，或只在重复运行中偶然成功。

- **REL-1 固定每次发布要过的题。** 周芷宁希望把内部回归任务、关键客户场景和外部 benchmark 组成一份版本化的发布题集，并固定本轮使用的 Agent、模型、推理方式、重复次数和预算，这样本地与自动流程能够重现同一次发布判断。
- **REL-2 先确认范围和花费。** 周芷宁希望在正式开始前看到题目数量、总运行次数、并行规模和预算，并能先缩小到一个回归切片，这样不会因为选错范围产生意外费用。
- **REL-3 用重复运行判断可靠性。** 周芷宁希望同一道题重复执行并保留每次结果，这样可以区分稳定能力与偶然成功，同时知道还有哪些题没有得到足够观测。
- **REL-4 同时比较质量、成本和速度。** 周芷宁希望并排查看完成率、估算成本和耗时分布，并回到造成取舍的具体任务，这样不会被一个混合总分掩盖真正的产品代价。
- **REL-5 把回归交给自动修复循环。** 周芷宁希望自动流程能稳定读取计划、进度、结果和失败证据，再交给 coding agent 修改并复验，这样团队不必人工复制终端内容来回传递问题。

## 周芷宁：修复后只重跑真正需要复验的部分

CodeMate 的一次完整回归需要数小时和真实模型费用。
周芷宁希望根据变化原因选择沿用、局部重跑或全量重验，而不是每次都从零开始。

- **RUN-1 沿用未受影响的确定结果。** 周芷宁只修改报告标题或分组名称时，希望继续使用原来的通过与未通过结果，同时重新处理上次因环境或执行问题没有得到结论的任务，这样展示变化不会浪费模型费用。
- **RUN-2 让真实变化自动触发复验。** 周芷宁修改题目、公共材料、模型、判分标准、Agent 或运行环境时，希望受影响的旧结果不再进入新结论；只改变备注或一次运行产生的临时地址时，则不希望整批失效。
- **RUN-3 修复产品后只复验旧失败。** CodeMate 修复一个缺陷后，周芷宁希望重新运行上次未通过的任务，保留仍然可信的旧通过结果，同时补做上次没有成功执行的任务，这样最快确认修复是否关闭回归。
- **RUN-4 外部事实变化时全量重验。** 模型供应商更新服务或外部依赖改变，而本地文件没有变化时，周芷宁希望主动忽略所有旧结果重新运行一次，这样发布结论不会建立在无法观察的旧行为上。
- **RUN-5 区分沿用结果与复用环境。** 本地冒烟时，周芷宁希望多道题共用已经装好依赖的运行环境，但每道题仍然真实执行并产生新证据，这样可以节省准备时间，又不会把旧结果冒充为本次结果。
- **RUN-6 每道题开始前恢复干净状态。** 共用环境中的前一道题可能修改代码、启动进程或写入缓存。周芷宁希望下一道题开始前清除这些影响，不同环境要求的题分开运行，环境寿命不足时提前更换，这样提速不会破坏公平性。
- **RUN-7 按问题选择是否跑满。** 周芷宁只想确认“至少能成功一次”时，希望首次成功后停止多余重复；需要测稳定性时则跑满所有次数，只有相互独立的任务才并行，这样速度优化不会伪装成完整可靠性数据。

## 孟启航：让长批次运行可恢复、可止损

孟启航替多个团队运行 EvalCloud。
被测 Agent 会执行命令和修改文件，长批次还会遇到限流、网络中断、无效凭据、损坏的起始材料和共享服务失效。

- **OPS-1 隔离并清理每次运行。** 孟启航希望不可信 Agent 无法修改宿主机或其它任务，并在成功、失败或中断后释放相关进程和资源，这样一次评估不会影响下一次工作。
- **OPS-2 只恢复确定安全的瞬时故障。** 请求在被 Agent 接收前遇到限流或连接失败时，孟启航希望有限重试；无法确认 Agent 是否已经产生副作用时，他宁可保留诚实的执行错误，也不重复发送同一任务。
- **OPS-3 确认共享故障后立即止损。** 凭据失效或共享服务死亡时，孟启航希望停止尚未开始的相关任务，让正在运行的任务自然结束，并保留停止原因，这样同一故障不会把剩余预算消耗完。
- **OPS-4 保护长任务和失败现场。** 孟启航希望长任务开始前确认环境还会存活足够时间；遇到难以解释的启动或状态问题时，他希望保留现场进入检查，这样不必为每个假设重新支付一次完整运行成本。
- **OPS-5 修复外部服务后从断点继续。** 孟启航修好共享服务后，希望保留仍可信的已完成结果，只补做执行失败和未开始的任务，并清楚说明哪些结果来自本次运行，这样恢复不等于整批重来。

## 苏曼青：让发布结论经得起复核

苏曼青不能只接受“CodeMate 平均完成率提高了 4%”。
她需要知道这 4%来自哪些题、哪些运行、怎样的条件，以及是否排除了未覆盖和基础设施错误。

- **AUD-1 保存能够独立复核的运行事实。** 苏曼青希望每次运行都保留配置、交互、文件变化、判定、诊断、耗时和用量，并让一次具体运行拥有稳定引用，这样她不用从终端文案猜测发生了什么。
- **AUD-2 先审数据范围再看指标。** 苏曼青希望知道结果包含哪些实验和题目、哪些是真实执行、哪些沿用历史、哪些跳过或未完成，以及数据存在哪些缺口，这样缺失数据不会被当作失败、零值或成功。
- **AUD-3 按问题选择历史范围。** 复核发布水位时，苏曼青希望看每道题的当前结论；调查事故时，她希望只看相关批次；核算本次成本时，她只看本次真实执行，这样每个数字都有明确时间和范围口径。
- **AUD-4 从汇总数字回到原始证据。** 苏曼青希望从完成率、成本或耗时读数追到组成它的具体运行，并看清纳入和排除规则，这样她可以独立重算并挑战结论。
- **AUD-5 在不同入口使用同一口径。** 苏曼青希望在终端、浏览器和内部脚本中收窄同一批实验、题目或运行，并在长批次进行时看到结果逐步出现，这样不同入口不会给出相互冲突的数字。
- **AUD-6 交付自包含的结果子集。** 苏曼青向审计委员会交付材料时，希望只带选中的结果和所需证据，不留下指向内部机器的路径，并能在离线环境独立打开。
- **AUD-7 把技术结果转成业务报告。** 苏曼青希望把完成率、成本、风险等级和业务分组放进同一份报告，并从异常点回到具体运行，这样管理者看到取舍，审计人员也能继续追证据。
- **AUD-8 为不同受众保持同一结论。** 苏曼青希望终端摘要、浏览器报告、静态站点和 Harbor 产品页共享相同的数据范围、数字、警告和证据指向，这样展示形式变化不会改变结论。

## 方以宁：看清多 Agent 客服系统怎样协作

Relay 由协调 Agent、退款 Agent 和技术支持 Agent 共同完成一次客户请求。
只看最终答复，方以宁无法判断谁做了什么、是否越权，以及成本主要花在哪个角色上。

- **MA-1 按 Agent 复核行为。** 方以宁希望每次交互、工具调用和外部操作都能归到实际执行它的 Agent；证据不足时明确说不知道，这样不会靠猜测判断职责是否履行。
- **MA-2 区分征求建议与交出控制权。** 方以宁希望看出协调 Agent 只是向专业 Agent 咨询，还是把后续对话交给它处理，并能沿着多轮交接查看上下文，这样她可以判断协作路径是否符合设计。
- **MA-3 分开各角色成本。** 方以宁使用模拟客户或谈判对手时，希望主被测系统、专业 Agent 和模拟侧分别计算用量，这样评估成本不会被误算成 Relay 的服务成本。
- **MA-4 比较不同协作方案。** 方以宁希望在同一批客户请求上比较不同分工与交接策略，同时保持客户脚本和结果标准不变，这样差异才能归因到协作设计。
