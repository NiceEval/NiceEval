# 读入数据文件

## 场景

题面、断言的期望值、一整张 case 表常常放在数据文件里,不写死在 `.eval.ts` 中。
这些文件的内容改了,判定就变了,该作废读它的那些 eval。

用 `fs.readFileSync` 读进来的文件无法进入 source manifest。
系统不知道那次读取依赖哪个文件，因此不能证明历史 Evidence 仍有效。

## 怎么写

用 loader 读,四个覆盖常见格式:

```typescript
import { loadYaml, loadJson, loadText, loadBytes } from "niceeval/loaders";

const cases = await loadYaml("evals/data/recall-cases.yaml");
const template = await loadText("evals/data/recall-prompt.md");
```

四个 loader 都在发现阶段读取文件。
路径与内容 digest 进入引用它的 Requirement；改一行数据后，两套默认政策都只派发这些 Eval。

```text
memory/recall-01..30
  invalid  loader input changed
    evals/data/recall-cases.yaml  2a8e… → 71cc…
```

## 边界

内容 digest 按**整份文件**算，不逐行算。
从输入数组生成多条 eval写法因此有一条性质：一个文件生成的全部 eval 共享同一份数据哈希与同一份源码字节, 所以三十行 case 表改任意一行，三十条一起失效。

这让从输入数组生成多条 eval写法的作废面比手写差:三十个 `.eval.ts` 文件里改一个 case 只烧一条, 从输入数组生成多条 eval成「一个文件加一张表」之后改一个 case 烧三十条。
从输入数组生成多条 eval仍然是[推荐写法](../../../feature/eval/use-case/dataset-fanout.md)——薄 wrapper 难维护且容易漂移——但 case 集大且经常单独调时, 按变更频率拆数据文件:

```text
evals/data/
├── recall-cases-stable.yaml     定稿的 25 条,几乎不动
└── recall-cases-wip.yaml        在调的 5 条,改它只烧 5 条
```

判据与拆 `share/` 同一条:稳定的和天天调的不放同一个文件。

直接 `fs.readFileSync`、`node_modules` 里的包与动态 `import()` 无法进入完整 manifest 时，相关 Requirement 为 `opaque`。
证明优先默认派发，复用优先默认沿用并标 unverified。
用户可以用 `--accept opaque:source.dynamic-import` 或 `--rerun source:<path>` 覆盖当前政策，但长期修法仍是改用 loader 或把依赖纳入 manifest。
