# 归零被测服务状态

## 场景

被测对象是一个有累积状态的服务:记忆库、向量库、一个跑着的知识后端。
它跑过一批 eval 之后库里就有东西了,而「空库跑出来的通过率」
和「积累了两百条记忆之后跑出来的通过率」是两批不可比的数。

这个状态在服务端,不在任何源码或配置里,指纹永远观测不到它。
清库、换实例、导入一批种子数据都改变它,而 niceeval 一个字都看不见。

## 怎么写

优先让服务提供只读版本接口，由 Experiment observer 在对账前读取。
没有版本接口时，给状态一个静态 epoch：

```typescript
export default defineExperiment({
  flags: {
    corpusEpoch: "2026-07-20-empty",
  },
  resources: [
    observeResource.fromFlag({
      id: "memory-corpus",
      flag: "corpusEpoch",
      appliesTo: (e) => e.tags.includes("memory"),
    }),
  ],
});
```

清库、换实例或导入种子数据时修改这个值，并在同一批改动里提交。
依赖 `memory-corpus` 的 Requirement 随之变化，只派发相关证据槽位。

值只要求每次状态变化都不同。
带日期与状态描述的字符串比递增序号更适合审计。

## 边界

静态 epoch 仍需要操作者在状态变化时更新一次。
它解决的是「在状态变更事件上判断」，不是自动发现服务端变化。

忘记更新 epoch 后直接运行时，系统无法证明资源没变。
如果资源只声明了静态 epoch，当前 Requirement 仍会匹配历史 Evidence；
这条人工承诺不能被包装成「错误最终一定会暴露」。

高风险服务应提供自动 observer。
无法提供时，用户可以在清库后用 `--rerun all` 收紧本次采信，
同时补改 epoch，避免后续 Invocation 继续依赖手工重跑。

`corpusEpoch` 是实验条件，也可以作为报告维度比较空库与积累库。
不要用时间戳无条件变化来关闭全部沿用；无法声明身份的资源应明确标成 `opaque`。
