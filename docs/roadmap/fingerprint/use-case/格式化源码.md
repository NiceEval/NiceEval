# 格式化源码

## 场景

eval 文件与源码闭包按整份内容进入 source manifest。
所以格式化一次 `evals/`，或改一个共享文件里的注释，
默认会让引用它的 Requirement 失效。

改的人知道题面、执行与判定语义没有变化，系统只能看到 digest 不同。

## 怎么写

先看计划：

```bash
niceeval exp compare/codex --dry
```

```text
memory/recall-01..30
  source changed
    evals/share/prompts.ts  80d1… → b91a…
  decision  dispatch
```

确认这份精确变化不影响证据含义后认账：

```bash
niceeval exp compare/codex --accept-change evals/share/prompts.ts
```

系统只在其它 manifest 输入完全相等时沿用历史 Evidence。
落盘的 `ReuseAttestation` 记录 old digest、new digest 与两侧 requirement key。
原 Evidence 的执行身份不改写。

## 边界

它接受的是一次 old → new 状态转换，不是长期忽略某个路径。
下一轮仍是相同 new digest 时可以沿用已有 attestation；
文件再次变化时产生新的 digest，必须重新判断。

同时改了另一份断言文件时，只接受 prompt 文件不会放行：

```text
cannot accept change
  accepted:
    evals/share/prompts.ts  80d1… → b91a…
  remaining semantic input changes:
    evals/share/assert-memory.ts  12aa… → 43bf…
```

文件重命名或拆分可以把 delete 与 add 的路径一起接受。
Agent、Sandbox 与外部资源变化不开放这个出口。

更稳的日常做法仍是按变更频率拆文件：
稳定断言与频繁调整的 prompt 模板不放同一个文件。
