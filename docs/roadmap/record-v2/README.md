# Record v2 —— 可演进的持久化契约

Record 的第一版选择了一个全局 `schemaVersion`：Run 内任意持久化形状发生破坏性变化，整个 Run 就只能由同版本 CLI 读取。
这保证了消费方不会静默误读事实，却把导航、报告、证据读取与结果携带绑在同一个兼容性开关上。

从 2026-07-02 到 2026-08-02，格式在一个月内走过 14 个版本。
其中既有修复并发覆盖和身份碰撞的必要重构，也有字段命名与呈现需求引起的局部变化。
全局拒读让这些不同风险承担了同一代价：旧 Run 从全部读取面消失，携带规划也只能把它们整批判为不兼容。

## v1–v14 为什么变化

下表按实际 commit 复核版本台账。
`v7` 与 `v10` 是设计上的版本边界，但没有成为可单独读取的发布版本：代码分别从 6 跳到 8、从 9 跳到 11。

| 版本 | 主要 commit | 触发原因 | 变化性质 |
|---|---|---|---|
| 1 | `6b197dda` | 给 `summary.json` 增加稳定识别头，拒绝由不兼容 reader 猜读 | 建立版本机制 |
| 2 | `03b2d30b` | `flags` 改名 `params`，试图区分实验条件与 CLI flag | 命名裁决 |
| 3 | `3265d4f0` | 明确该字段就是 A/B feature flag，撤回 `params` | 命名翻案 |
| 4 | `d0b67181` | 同毫秒并发 Run 共写 `summary.json` 会覆盖判定，改成每个 Experiment 独占快照目录 | 数据安全与布局 |
| 5 | `b5b8ca92` | 增加可下钻的 Attempt locator，并把重复源码改成内容寻址存储 | 身份与去重 |
| 6 | `fef6adcd` | 自由字符串错误无法表达阶段、代码、原因和收尾诊断 | 事实结构化 |
| 7 | `d55d3c3b`、`5e7549eb` | 三套生命周期词表已发生漂移，错误和诊断统一使用 `LifecyclePhase` | 词表统一；随 v8 发布 |
| 8 | `c215076e`、`5e7549eb` | 外部契约评审要求断言三态、证据覆盖、窗口 diff、解析后配置投影与发布标记 | 多项语义重构打包 |
| 9 | `be3ebdb3` | 新增证据时要同步多份隐式清单，`has*` 布尔族改成 registry 驱动的 `artifacts`；`o11y` 去掉重复权威值 | 扩展性与单源化 |
| 10 | `b0cb68f6`、`d79be370` | 多文件源码需要入口角色与完整调用路径，否则无法装配源码调用树 | 证据语义；随 v11 发布 |
| 11 | `d79be370` | Results 拆成 Record / Sample / Reports；快照正名 Run，引入 `runId`、可逆目录编码与更安全的 locator | 领域边界与身份重构 |
| 12 | `3dd6419e` | `diff.json` 把二进制和超大文本统一表达为 `elided`，避免旧 reader 把二进制误作空文本 | 局部 artifact 形状 |
| 13 | `63877700`、`bf0b0c48` | 封闭计时节点无法容纳 Sandbox Build 等开放 activity；错误归因需要同时引用 Attempt 锚点与 Run timing | 时间模型重构 |
| 14 | `c9e7d21f` | `coverage` 不能明确表达“证据覆盖”，改名 `evidenceCoverage`，并把六通道声明收紧为必填 | 命名与必填约束 |

这些变化不能简单归结为“旧 schema 设计错了”。
v1 的严格拒读避免了隐式兼容造成的静默误判；v4、v5 与 v11 修复了会丢数据或指错 Attempt 的身份问题；v6、v8 与 v13 让错误、断言和计时成为可验证事实。
NiceEval 仍处于 beta，快速纠正领域模型也比长期背负错误兼容层更合理。

真正需要改变的是兼容性的粒度。
v2、v3 与 v14 的局部命名变化不应让源码、events、trace 和 Run 身份一起失效；v12 只改变 diff，也不应阻止用户读取判定或携带不依赖 diff 的结果。
`v7`、`v10` 没有独立发布，以及 v8 一次打包多种变化，也说明全局整数同时承担“契约边界”和“发布批次”后很难保持准确。

## 候选核心心智

Record v2 把一份记录分成三个兼容层：

1. **容器与身份**负责发现 Run、Attempt 和文档引用。只有这一层无法安全识别时，整份 Run 才不可读。
2. **事实文档**各自声明 schema。结果、events、diff、源码和计时可以独立演进，reader 只降级自己不认识的切面。
3. **消费能力**声明某个任务需要哪些事实与语义版本。查看、比较、报告和携带分别判断，不再共用“整个 Run 能否读取”这一问。

Reader 先把磁盘文档转换成当前的中性 Record 模型。
转换只发生在读取边界，不重写原始记录；报告和 Sample 不直接处理历史字段名。
Writer 只写最新 schema，避免兼容分支进入执行热路径。

完整候选形状见 [Architecture](architecture.md)。

## 范围

本候选包含：

- 稳定容器头、Run / Attempt 身份与文档目录。
- 每类事实独立版本、读取转换与结构化降级。
- 查看、比较、报告和携带的能力判定。
- 从当前 v14 进入新格式的过渡边界。
- 第三方 `createWriter()` 如何声明 core 文档与扩展文档。

本候选不改变 Record / Sample / Reports 三层分工，不把聚合写回磁盘，也不把报告组件协议写入 Record。
内容寻址源码、按需 artifact、自包含发布和原始事实不可变继续保留。

## 待裁决

1. 文档描述符集中放在 `attempt.json`，还是允许每个对象文档自带识别头、数组文档由描述符补充。
2. 新 reader 只内置 v14 到 v2 的桥接，还是提供独立转换命令读取更早的 v1–v13。
3. 第三方扩展只允许命名空间文档，还是允许注册可参与携带资格的扩展能力。
4. 文档摘要是否从第一版就必填；它能验证复制与借用完整性，但会增加第三方 writer 的实现成本。
5. 一个旧结果能读取判定却缺少当前携带所需的证据语义时，应统一标记 `incompatible`，还是细分为可展示但不可携带的原因。
