# 评估环境较重

## 项目形态

每道 Eval 自带 Dockerfile 或 Compose,环境本身是题意的一部分。
terminal-bench 就是这种形态:重的是每道题的系统包、服务和构建过程,Experiment 没有额外实验工具。

## Eval 声明题目环境

```typescript
// evals/terminal-bench/debug-long-program/eval.ts
const environment = composeSandbox({
  file: new URL("docker-compose.yaml", import.meta.url),
  mainService: "client",
  build: "on-demand",
});

export default defineEval({
  environment,
  async test(t) {
    await t.send("修好 /app/solver 里的死循环。");
    await t.sandbox.uploadDirectory("./tests", ".tbench-testing");
    const verify = await t.sandbox.runShell("bash .tbench-testing/run-tests.sh");
    t.check(verify, commandSucceeded());
  },
});
```

另一道 Eval 可以声明不同的 Compose、Dockerfile 或 environment profile。
这些内容进入各自的 BuildKey 与 CaseKey,只作废受影响 Eval 的旧结果。

## Experiment 只选择运行方式

```typescript
// experiments/claude-docker.ts
export default defineExperiment({
  agent: claudeCodeAgent(),
  sandbox: dockerSandbox({
    materializers: { compose: dockerComposeMaterializer() },
  }),
});
```

Adapter 自动确保 Agent CLI 在每道题的主 Sandbox 中就位。
Experiment 不需要知道题目目录、Compose 服务或构建内容,也不需要声明 experiment Layer。

## 重成本怎样复用

Dockerfile 与 build context 按 BuildKey 做 Run 级构建协调;同一构建输入只构建一次,命中 provider 原生 cache 时只做增量工作。
这是评估环境重时的主要复用机制,不需要打开 `sandboxReuse`。

不同 sandbox case 不能共用一个 Sandbox。
`sandboxReuse` 只能让同一解析后 sandbox case 分组内的 Attempt 复用实例,不能让 241 份不同 Compose 共享运行环境。
只有同一个 case 有多次 Attempt、并且题目允许 workdir 外残留时,才单独评估是否开启复用。

Agent 安装仍由 Adapter 的 Agent Layer 逐 Sandbox 检查和补齐。
如果每道任务镜像都缺 Agent、安装成本成为瓶颈,应优先给任务环境共享一个预装 Agent 的基础镜像,而不是把 Agent 写进每道 Eval。
