# 主用例二：用户扩展 GPU 能耗领域 SDK

这个 Use Case 回答三种不同身份的问题：

- 普通 Eval 作者怎样启用 GPU 能耗，而不看见 Record；
- 领域 SDK 作者怎样定义值、版本、migration、producer lifecycle 与 projection；
- application／Analysis／Report host 怎样安装、读取、迁移与呈现。

通用语法以 [RecordAttachment adapter SPI](../../record-attachment-authoring/library.md)、
[Record → Analysis → Report Library](../library.md) 与 [Reports Library](../../../feature/reports/library.md) 为单源。

```text
ordinary Eval: gpuEnergy({ meter })
  → occurrence-local meter session
  → sealed GpuEnergy
  → SDK-private RecordAttachment adapter
  → canonical Record command
  → domain Projection / Derivation
  → Report
```

这套用例由两个作者共同完成：领域 SDK 作者提供采集、持久化与 Analysis 消费面；application 的 Report 作者再用这些
领域 export 写自己的 Report 组件。adapter 不是“组件”，Report 的 Calculation 与 Page 才是组件。

## SDK 与 application 各自写什么

| 文件／模块 | owner | 导出 | consumer |
|---|---|---|---|
| `plugin.ts` | 领域 SDK | `gpuEnergy()`、`nvmlEnergyMeter()` | 普通 Eval |
| `record.ts` | 领域 SDK | 只导出 `gpuEnergyRecordInstallation` | application／maintenance host |
| `analysis.ts` | 领域 SDK | `gpuEnergyByAttempt`、`projectGpuEnergy()`、`deriveGpuEnergy()` | Analysis script 与 Report |
| `reports/gpu-energy.ts` | application 或另一个 UI package | `gpuEnergySummary` Calculation、`gpuEnergyPage` Page | application 的 `defineReport()` |

SDK-private adapter、binding、schema 与 raw projector 都不从这些公共模块泄漏。Report package 也不能因为需要画图就反向
取得 Record reader。

## 1. SDK 先定义 sealed domain value

领域值不是 versioned document。它表达一次 Attempt 区间测量已经封口后的业务语义：

```ts
export type GpuEnergy =
  | {
      readonly state: "observed";
      readonly joules: number;
      readonly source: "device-estimate";
      readonly uncertaintyJoules: number | null;
    }
  | {
      readonly state: "unavailable";
      readonly reason: "not-supported" | "not-readable";
    };
```

`unavailable` 是正常领域结果。meter 不支持累计能耗，或设备拒绝读取时，producer 仍形成这个 sealed value；它不 throw，
也不靠 Attachment 缺席表示。

SDK 的公开 meter definition 是 immutable、opaque 配置，不是 live session：

```ts
import {
  nvmlEnergyMeter,
  type GpuEnergyMeter,
} from "@example/niceeval-gpu";

const meter: GpuEnergyMeter = nvmlEnergyMeter({ device: 0 });
```

meter 自带稳定 `behaviorIdentity`。设备选择、采样算法、counter wrap 与 unsupported policy 改变时，SDK 提升 identity；
schema identity 不能替代 producer behavior identity。

## 2. SDK 定义 v1／v2 adapter

versioned payload 只在 `@example/niceeval-gpu/record` 内部出现：

```ts
import { Effect, Schema } from "effect";
import {
  defineRecordAttachmentAdapter,
} from "niceeval/record/adapter";

const finiteNonNegative = Schema.Number.pipe(
  Schema.finite(),
  Schema.nonNegative(),
);

const gpuEnergyPayloadV1Schema = Schema.Union(
  Schema.Struct({
    state: Schema.Literal("observed"),
    joules: finiteNonNegative,
  }),
  Schema.Struct({
    state: Schema.Literal("unavailable"),
    reason: Schema.Literal("not-supported", "not-readable"),
  }),
);

const gpuEnergyPayloadV2Schema = Schema.Union(
  Schema.Struct({
    state: Schema.Literal("observed"),
    joules: finiteNonNegative,
    source: Schema.Literal("device-estimate"),
    uncertaintyJoules: Schema.NullOr(finiteNonNegative),
  }),
  Schema.Struct({
    state: Schema.Literal("unavailable"),
    reason: Schema.Literal("not-supported", "not-readable"),
  }),
);

type GpuEnergyPayloadV1 = Schema.Schema.Type<
  typeof gpuEnergyPayloadV1Schema
>;
type GpuEnergyPayloadV2 = Schema.Schema.Type<
  typeof gpuEnergyPayloadV2Schema
>;

const gpuEnergyRecord = defineRecordAttachmentAdapter({
  owner: "attempt",
  name: "com.example.gpu-energy",
  versions: {
    v1: {
      schema: gpuEnergyPayloadV1Schema,
      blobRefs: () => [] as const,
    },
    v2: {
      schema: gpuEnergyPayloadV2Schema,
      blobRefs: () => [] as const,
    },
  },
  current: "v2",
  migrations: ({ v1, v2 }) => ({
    v1: {
      to: v2,
      migrate: (source, target) =>
        Effect.succeed(
          target.value(
            source.payload.state === "observed"
              ? {
                  state: "observed",
                  joules: source.payload.joules,
                  source: "device-estimate",
                  uncertaintyJoules: null,
                }
              : source.payload,
          ),
        ),
    },
  }),
  adapt: (value: GpuEnergy, target) =>
    Effect.succeed(target.value(value)),
  project: ({ payload }) => payload,
});
```

v1 的版本语义明确规定：每个 `observed` payload 都来自 `device-estimate`，但没有保存 source 字段或不确定度。因此
converter 可以无损补出 `source: "device-estimate"`；`uncertaintyJoules: null` 表示“v1 未持久化”，不表示 `0`。

`adapt` 只接收 sealed `GpuEnergy` 与 current target。它不读取设备、clock、Attempt session 或 Record path。若 v1 没有
保证 source，或者 v2 要求真实 uncertainty，SDK 必须把 edge 声明为 `unavailable`，不能在 converter 中重新测量或猜值：

```ts
v1: {
  to: v2,
  unavailable: {
    reason: "v1 did not record a source that can be derived losslessly",
  },
}
```

SDK 只向 application host 导出 opaque installation：

```ts
export const gpuEnergyRecordInstallation =
  gpuEnergyRecord.installation;
```

adapter 与 writable definition 都不导出。

## 3. SDK 把 meter 绑定到 Attempt

GPU 能耗是区间差值。SDK 不假设 after-Attempt 时还能从 ambient device state 准确还原整个 Attempt，而是在每个 actual
Attempt 的独立 Scope 中 bracket 一次 meter session：

```ts
import { definePlugin } from "niceeval/plugin";
import {
  defineAttemptRecordAdapterBinding,
} from "niceeval/record/adapter";

export const gpuEnergy = definePlugin<{
  readonly meter: GpuEnergyMeter;
}>({
  name: "com.example.gpu-energy",
  behaviorRevision: "2",

  eval({ meter }) {
    return {
      recordAdapters: {
        attempt: [
          defineAttemptRecordAdapterBinding({
            adapter: gpuEnergyRecord,
            behaviorIdentity: meter.behaviorIdentity,
            open: ({ attempt, signal }) =>
              meter.open({ attempt, signal }),
            seal: (session, { attempt, exit, signal }) =>
              meter.seal(session, { attempt, exit, signal }),
            release: (session, { attempt, exit }) =>
              meter.release(session, { attempt, exit }),
          }),
        ],
      },
    };
  },
});
```

`attempt` 是领域可见的 nominal execution identity，不是 `RecordAttemptRef`、writer 或 lease。live session 只住在
binding child Scope，不进 Plugin blueprint、module-level map、`TestContext` 或另一个并发 Attempt。

三项 meter 方法是 Effect-native，requirement 为 `never`。NVML Promise／callback 只在 meter boundary 用
`Effect.tryPromise` 适配一次。expected failure、defect 与 interruption保持原通道；正常 unsupported／unreadable 返回
`GpuEnergy.unavailable`。

## 4. 普通 Eval 只使用领域 API

```ts
// evals/gpu-energy.eval.ts
import { defineEval } from "niceeval";
import {
  gpuEnergy,
  nvmlEnergyMeter,
} from "@example/niceeval-gpu";

export default defineEval({
  plugins: [
    gpuEnergy({
      meter: nvmlEnergyMeter({ device: 0 }),
    }),
  ],

  async test(t) {
    const turn = await t.send("完成 GPU 推理任务");
    turn.succeeded().label("任务完成");
  },
});
```

Eval 作者不 import `niceeval/record`，不声明 definition／grant，不构造 versioned payload，也不提交 Record command。

一个 actual gap Attempt 的固定顺序是：

```text
owner open
  → reserve com.example.gpu-energy + pending obligation
  → Agent ready
  → meter.open
  → beforeAttempt hooks
  → Eval body / sends
  → afterAttempt hooks
  → meter.seal → one sealed GpuEnergy
  → meter.release
  → adapter.adapt
  → canonical command accepted once
```

carry／reuse 不打开 meter。seal 成功但 release 失败时不执行 adaptation，owner 失败。未产值、重复值、adaptation／schema／
closure／durable failure 也阻止 publication。

## 6. 历史 v1 与显式 migration

### 6.1 先读，得到迁移要求

application 已安装 v2 installation，但 Record 中某个 owner 仍是 v1。普通用户先执行 Report：

```sh
niceeval show \
  --run 01H... \
  --report ./reports/gpu-energy.ts
```

领域 projection 不调用 converter，而是保留 host state：

```ts
{
  state: "migration-required",
  from: "com.example.gpu-energy/v1",
  to: "com.example.gpu-energy/v2",
  command: "niceeval migrate",
}
```

本用例的 Calculation 使用 `allow-partial`，所以它仍收到完整 `ProjectedSample`。`deriveGpuEnergy()` 为该 slot 形成
`migration-required` row，summary 保持 partial，`totalJoules` 为 `null`。host-owned problems surface 同时给出迁移命令。

若 Calculation 选择 `require-complete`，host 不调用它，而是形成 `data-unavailable`。两种策略都不能把 v1 当成 v2，
也不能从 available slots 重算一个更小的分母。

### 6.2 Programmatic migrate SDK

application maintainer 从 host-only `niceeval/record/host` 取得同一个 scoped runtime。installation 仍使用 config 的同一
份 `recordAttachments`；SDK 不从 Plugin mount、Record bytes 或 Layer 猜 registry：

```ts
import { Console, Effect, Either } from "effect";
import {
  NodeRecordHostLive,
  makeRecordRoot,
  openRecordAccessRuntime,
  type RecordMigrationAuthorizationDecision,
} from "niceeval/record/host";
import { recordAttachments } from "./record-attachments.js";

export const migrateGpuEnergyHistory = (
  decision: RecordMigrationAuthorizationDecision,
) =>
  Effect.scoped(
    Effect.gen(function* () {
      const rootResult = makeRecordRoot("/project/.niceeval/record");
      if (Either.isLeft(rootResult)) {
        return yield* Effect.fail(rootResult.left);
      }
      const access = yield* openRecordAccessRuntime({
        root: rootResult.right,
        recordAttachments,
      });

      const plan = yield* access.maintenance.planMigration();
      yield* Console.log(JSON.stringify(plan.summary, null, 2));

      if (plan.state === "not-needed") {
        return yield* access.maintenance.migrate({ plan });
      }

      const authorizationResult =
        access.maintenance.authorizeMigration({ plan, decision });
      if (Either.isLeft(authorizationResult)) {
        return yield* Effect.fail(authorizationResult.left);
      }
      const receipt = yield* access.maintenance.migrate({
        plan,
        authorization: authorizationResult.right,
      });
      yield* Console.log(JSON.stringify(receipt, null, 2));
      return receipt;
    }),
  ).pipe(Effect.provide(NodeRecordHostLive));
```

调用方必须显式传入 `{ state: "use-git-restore-point" }`，或者在自己确认备份责任后传入
`{ state: "accept-data-loss" }`。`authorizeMigration()` 针对 exact plan mint nominal authorization；不能伪造、保存到
下一进程，或拿去执行另一个 runtime 的 plan。

本例的 plan summary 明确显示具体内容：

```ts
{
  state: "needed",
  root: "/project/.niceeval/record",
  git: { state: "git-restore-point", commit: "9f31d2a..." },
  core: { state: "current", format: "niceeval.record/v1" },
  attachments: [{
    state: "migrate",
    owner: "attempt",
    name: "com.example.gpu-energy",
    from: "com.example.gpu-energy/v1",
    to: "com.example.gpu-energy/v2",
    edges: [{
      from: "com.example.gpu-energy/v1",
      to: "com.example.gpu-energy/v2",
    }],
    count: 12,
  }],
}
```

成功 receipt 逐 family 说明实际结果：

```ts
{
  state: "migrated",
  plan: plan.summary,
  authorization: {
    state: "git-restore-point",
    commit: "9f31d2a...",
  },
  attachments: [{
    state: "migrated",
    owner: "attempt",
    name: "com.example.gpu-energy",
    from: "com.example.gpu-energy/v1",
    to: "com.example.gpu-energy/v2",
    edges: [{
      from: "com.example.gpu-energy/v1",
      to: "com.example.gpu-energy/v2",
    }],
    count: 12,
  }],
}
```

`current`、`migration-unavailable` 与 `unsupported` 分别在 receipt 中成为 `already-current`、
`preserved-migration-unavailable` 与 `preserved-unsupported`，不会伪装成 migrated。

### 6.3 CLI 使用同一 maintenance facet

用户确认 preflight 后执行：

```sh
niceeval migrate \
  --record /project/.niceeval/record \
  --config /project/niceeval.config.ts
```

`--config` 决定可信 installation registry。preflight 在任何 portable write 前显示 exact owner、family 与 edge：

```text
RecordAttachments
  attempt/com.example.gpu-energy: v1 -> v2
```

执行顺序固定为：

```text
validate installed graph + exact source
  → verify Git restore point or explicit --yes authorization
  → acquire exclusive maintenance lock
  → create and sync migration.in-progress
  → run v1 → v2 converter
  → schema / plain-data / closure validation
  → durable commit
  → remove and sync sentinel
```

CLI 对 `--config` 做配置求值，得到同一份 `recordAttachments`，再调用 `planMigration()`、交互获取 decision、
`authorizeMigration()` 与 `migrate()`。`--yes` 只形成 `accept-data-loss` decision，不是能脱离 plan 重用的 authorization，
也不创建 rollback、shadow copy 或 migration history。Plugin mount、Analysis、Report 与 ordinary read 都没有这项
maintenance authority。

### 6.4 成功与失败之后

成功后重新运行同一条 `niceeval show`。新的 snapshot 才读到 v2；迁移前的 `ReportExecution` 不会原地刷新。历史
observed 值的 `uncertaintyJoules` 为 `null`，unavailable 原因原样保留。

converter 不读取当前 GPU、network、clock、environment 或另一个 Attachment。target 仍经过同一 schema、plain-data 与
closure validators。

converter、blob、durable I/O、defect 或 interruption 失败时，CLI 保留 sentinel。后续 read 与 migrate 都以
`record-migration-interrupted` fail closed；用户必须从 preflight 指出的 Git commit 或自己的备份恢复。若 edge 是
`migration-unavailable`，CLI 原样保留旧 bytes，只显示 reason，不反复建议运行 migration。

## 7. SDK 写 Analysis 消费面

SDK 的 `analysis.ts` 用 private projector 构造领域 declaration，并把 direct call 与纯 Derivation 一起导出：

```ts
import {
  attemptSlotProjection,
  projectAnalysisSample,
} from "niceeval/projection";

export const gpuEnergyByAttempt = attemptSlotProjection(
  gpuEnergyRecord.projector,
);

export const projectGpuEnergy = (
  sampleHandle: AnalysisSampleHandle,
) =>
  projectAnalysisSample({
    sampleHandle,
    projection: gpuEnergyByAttempt,
  });
```

普通 Analysis script 不写 Report component，也不 import Record。它只调用 SDK 的领域函数：

```ts
import {
  deriveGpuEnergy,
  projectGpuEnergy,
} from "@example/niceeval-gpu/analysis";

const projected = yield* projectGpuEnergy(sampleHandle);
const summary = deriveGpuEnergy(projected);
```

`projected.entries` 与 Sample logical slots 一一对应。excluded、not-recorded、core-invalid、unavailable、
migration-required、migration-unavailable、unsupported、invalid 与 available domain value 都不能消失。

## 8. SDK 的纯 Derivation 保留口径

一个最小结果形状是：

```ts
export type GpuEnergyProjectedSample =
  ProjectedSample<"attempt-slot", GpuEnergy>;

interface GpuEnergyRow {
  readonly slot: AnalysisSlotRef;
  readonly attempt: RecordAttemptRef | null;
  readonly state:
    | "excluded"
    | "not-recorded"
    | "core-invalid"
    | "attachment-unavailable"
    | "migration-required"
    | "migration-unavailable"
    | "unsupported"
    | "invalid"
    | "domain-unavailable"
    | "observed";
  readonly joules: number | null;
  readonly uncertaintyJoules: number | null;
  readonly issues: readonly GpuEnergyIssue[];
  readonly refs: readonly GpuEnergyRef[];
}

interface GpuEnergySummary {
  readonly rows: readonly GpuEnergyRow[];
  readonly observed: number;
  readonly denominator: number;
  readonly totalJoules: number | null;
  readonly state: "complete" | "partial";
  readonly issues: readonly GpuEnergyIssue[];
  readonly refs: readonly GpuEnergyRef[];
}

export declare const deriveGpuEnergy: (
  projected: GpuEnergyProjectedSample,
) => GpuEnergySummary;
```

规则固定为：

- 每个 Sample logical slot 恰好一行；
- `denominator` 直接来自 Sample，不从 available 数量反推；
- `observed` 只数 domain `observed`；
- `totalJoules` 只在 denominator 大于零、所有 denominator slots 都 observed 且 checked sum finite 时形成；
- domain unavailable、Attachment read state 与 Core 缺口进入 issues，并令 summary partial；
- 每个参与数值的 row 保留 slot、exact Attempt 与领域 refs。

这是 GPU SDK 的 completeness policy。另一个领域可以提供 observed subtotal，但必须明确命名并保留分母与缺口。

## 9. 用户写 Report Calculation 与 Page 组件

Report 作者不重新定义 GPU schema、reader 或统计公式。application 在 `reports/gpu-energy.ts` 中用 SDK 的领域 declaration
与 Derivation 编写 Calculation 和 Page：

```ts
import { Either } from "effect";
import {
  defineCalculation,
  definePage,
  defineReport,
  reportComponentId,
  reportDocument,
  reportId,
  reportInputs,
  reportMetric,
  reportRoute,
} from "niceeval/report";
import {
  deriveGpuEnergy,
  gpuEnergyByAttempt,
} from "@example/niceeval-gpu/analysis";

const inputs = reportInputs({ energy: gpuEnergyByAttempt });

export const gpuEnergySummary = defineCalculation({
  id: Either.getOrThrow(
    reportComponentId("gpu-energy-summary"),
  ),
  inputs,
  completeness: "allow-partial",
  calculate: ({ inputs }) => deriveGpuEnergy(inputs.energy),
});

export const gpuEnergyPage = definePage({
  id: Either.getOrThrow(reportComponentId("gpu-energy")),
  route: Either.getOrThrow(reportRoute("/gpu-energy")),
  calculations: { gpuEnergySummary },
  render: ({ calculations }) => {
    const result = calculations.gpuEnergySummary;

    if (result.state !== "available") {
      return reportDocument({
        title: "GPU energy",
        children: [{
          type: "status",
          tone: "negative",
          label: "GPU energy calculation unavailable",
        }],
      });
    }

    const value = result.value;
    return reportDocument({
      title: "GPU energy",
      children: [
        reportMetric({
          label: "Observed slots",
          value: `${value.observed}/${value.denominator}`,
        }),
        reportMetric({
          label: "Total energy",
          value: value.totalJoules,
          unit: "J",
        }),
        {
          type: "table",
          caption: "GPU energy by logical slot",
          columns: [
            { key: "slot", label: "Slot" },
            { key: "state", label: "State" },
            { key: "joules", label: "Energy (J)", align: "end" },
          ],
          rows: value.rows.map((row) => ({
            slot: `${row.slot.runId}/${row.slot.slotId}`,
            state: row.state,
            joules: row.joules,
          })),
        },
      ],
    });
  },
});

export default defineReport({
  id: Either.getOrThrow(reportId("gpu-energy")),
  calculations: { gpuEnergySummary },
  pages: [gpuEnergyPage],
});
```

application 可以直接把这两个组件放进一个 Report，也可以由 `@example/niceeval-gpu/report` 另行封装后复用。无论怎样
打包，Calculation 都调用 SDK 唯一的 `deriveGpuEnergy()`；Page 只消费 closed `GpuEnergySummary`。

Report 作者只看到 `gpuEnergyByAttempt` 与 closed `GpuEnergySummary`。Page 没有 adapter、reader、schema、converter、Sample
handle 或 maintenance capability。host problems 仍保留 migration、unsupported、invalid 与 callback failure，页面不能
删除。

## 10. Report host 到底怎样读取 GPU Attachment

`reportInputs({ energy: gpuEnergyByAttempt })` 只声明依赖，不执行读取。普通用户从 CLI 触发 host：

```sh
niceeval show --run 01H... --report ./reports/gpu-energy.ts
```

application host 的等价 Effect 入口是：

```ts
import {
  executeReportFromRecord,
  showReport,
} from "niceeval/report/host";
import { recordAttachments } from "./record-attachments.js";
import gpuEnergyReport from "./reports/gpu-energy.js";

const execution = yield* executeReportFromRecord({
  root,
  recordAttachments,
  selection: {
    policy: "explicit-runs",
    input: { runIds: [runId] },
  },
  report: gpuEnergyReport,
});

yield* showReport({ execution });
```

host 内部固定执行：

```text
open scoped RecordReader
  → selectAnalysisSample(reader, selection)
  → executeReport({ sampleHandle, report })
      → collect finite reportInputs
      → project gpuEnergyByAttempt at most once
      → deriveGpuEnergy() Calculation
      → gpuEnergyPage
  → close reader
  → immutable ReportExecution
```

Report 作者不会调用 `projectGpuEnergy()`；那个函数属于普通 Analysis script。Report 作者交出
`gpuEnergyByAttempt` declaration，host 才在 live handle 上执行它。Projection 的六态、Sample denominator 与 coverage
进入 closed input；Calculation 和 Page 都不能追加 Attachment I/O。

`show`、浏览器请求与 static export 只消费 `ReportExecution`。`view` 每次 rebuild 创建新 snapshot；HTTP refresh 不读
Record。迁移完成后也必须 rebuild，旧 execution 仍显示迁移前状态。

## 11. 自定义能力被哪些上层消费

| 上层 | 调用形状 | 得到什么 |
|---|---|---|
| Analysis script | `projectGpuEnergy()` → `deriveGpuEnergy()` | closed `GpuEnergySummary`，含 denominator、issues 与 refs |
| Relations | `gpuEnergyByAttempt` 与同一 Sample 的其它 projection | 按 exact owner／anchor 对齐的 exhaustive relation cells |
| Report Calculation | `reportInputs({ energy: gpuEnergyByAttempt })` | host 预取的 closed projection |
| Report Page | `calculations.gpuEnergySummary` | closed summary 与不可删除的 host problems |
| `show`／`view`／static export | application 的 `ReportExecution` | 同一组件树的终端、网页与静态结果，不重新读取 Record |

## 官方与第三方的中立性

| 环节 | third-party GPU | official Timing／Assertions／Diff |
|---|---|---|
| adapter compiler | public reverse-domain input | 同一 compiler + private namespace token |
| producer lifecycle | SDK binding | package-private binding |
| total obligation | mounted owner open 时登记 | 相同 |
| Scope／seal／release | owner child Scope | 相同 |
| target／validators | generic | 相同 |
| tracked command／poison／sink | canonical | 相同 |
| reader／projection／migration | installed registry 与同一 runtime | 相同 |

authority 差异止于 namespace、导出边界与 installation package owner。第三方不能冒充 official family；official 也不能
绕过 binding 或 generic kernel。
