# 宿主写后读取与显式迁移

这个 Use Case 说明 application / CLI host 怎样用一套 Record 子系统完成三类动作：Invocation 写入、fresh snapshot
读取、maintenance migration。它们共享一个 `RecordAccessRuntime`，但不会共用同一把万能 capability 或让锁的生命周期
泄漏给 producer、Analysis、Report。

```text
open one RecordAccessRuntime(root, recordAttachments)
  → withWriteSession: reuse planning + execute + publish
  → close writer
  → withSnapshot: fresh Analysis + ReportExecution
  → close snapshot
  → planMigration + authorizeMigration + migrate under exclusive maintenance
  → withSnapshot: read migrated current values
```

公共签名以 [Library](../library.md) 为单源。`runInvocationInSession()` 是 host 自己的 Invocation 领域函数。
Report 读取使用现有的 `selectAnalysisSample()` 与 `executeReport()`，不再引入含糊的适配函数。

## 一次 application main 的语法

```ts
import { Effect, Either } from "effect";
import { selectAnalysisSample } from "niceeval/analysis";
import {
  NodeRecordHostLive,
  openRecordAccessRuntime,
  type RecordMigrationAuthorizationDecision,
} from "niceeval/record/host";
import { executeReport } from "niceeval/report/host";
import { recordAttachments } from "./record-attachments.js";

const program = (
  migrationDecision: RecordMigrationAuthorizationDecision,
) => Effect.scoped(
  Effect.gen(function* () {
    const access = yield* openRecordAccessRuntime({
      root,
      recordAttachments,
    });

    const executeSnapshotReport = (reader) =>
      Effect.gen(function* () {
        const sampleHandle = yield* selectAnalysisSample(
          reader,
          selection,
        );
        return yield* executeReport({ sampleHandle, report });
      });

    const invocationReceipt = yield* access.invocation.withWriteSession(
      (session) => {
        const reusePlan = planReuse({
          view: session.view,
          executionTarget,
        });

        return runInvocationInSession({
          session,
          reusePlan,
          executionTarget,
        });
      },
    );

    const beforeMigration = yield*
      access.invocation.withSnapshot(executeSnapshotReport);

    const plan = yield* access.maintenance.planMigration();
    let migrationReceipt;
    if (plan.state === "not-needed") {
      migrationReceipt = yield* access.maintenance.migrate({ plan });
    } else {
      const authorizationResult =
        access.maintenance.authorizeMigration({
          plan,
          decision: migrationDecision,
        });
      if (Either.isLeft(authorizationResult)) {
        return yield* Effect.fail(authorizationResult.left);
      }
      migrationReceipt = yield* access.maintenance.migrate({
        plan,
        authorization: authorizationResult.right,
      });
    }

    const afterMigration = yield*
      access.snapshots.withSnapshot(executeSnapshotReport);

    return {
      invocationReceipt,
      beforeMigration,
      migrationReceipt,
      afterMigration,
    };
  }),
).pipe(Effect.provide(NodeRecordHostLive));
```

`Effect.scoped()` 持有 outer runtime 的资源。真正的 lease 都由四个 child operation 自己 acquire/release；代码没有在
内部调用 `Effect.runPromise`。CLI / application main 在提供 Layers 后只启动一次 runtime。

## 写侧到底发生什么

`withWriteSession()` 固定按 shared maintenance → exclusive writer 的顺序取锁，并 mint `session.view` generation。
这个 view 只供本次 reuse planning 使用：

```text
session.view
  → inspect published history
  → plan every target slot as reuse or gap
  → execute gaps
  → run mounted owner-specific producer bindings
  → sealed domain values → adapters → canonical commands
  → validate domain aggregate
  → publish complete Run
```

领域 producer 只拿自己的 Attempt／Run identity、signal 与 SDK session。它看不到 Record owner ref、root、writer lock、
generation、verified-read cache、maintenance facet 或 command kernel。host 根据 linked binding 建立 total producer
obligation；producer 封口为领域值后，才由 package-private adapter 适配并向同一个 command kernel 提交 tracked command。

普通 Eval、Experiment 与 Hook context 没有 Record 方法。官方 OTel、Assertions、File Diff 与第三方 GPU SDK 都走同一条
binding／adapter 路径；区别只在领域 API 与 sealed value，不在持久化旁路。

`publish` 不刷新 `session.view`。即使 portable bytes 已经写完，当前 generation 仍保持创建时的 membership；这避免 reuse
planner 在一次 Invocation 中途看到自己刚发布的 Run。

## 为什么必须关闭 writer 后再读

第一个 `withSnapshot()` 在 write callback 已返回之后才执行，因此 writer 与 shared maintenance lease 都已释放。它重新：

1. 取得 shared maintenance lease；
2. 检查 current format 与 migration sentinel；
3. mint 一个 fresh generation；
4. 冻结已发布 Run membership；
5. 在 callback 结束时关闭 generation 并释放 lease。

`selectAnalysisSample()` 把 callback 内的 fresh `RecordReader` 变成 reader-bound `AnalysisSampleHandle`。
`executeReport()` 必须在同一 callback 内完成 dependency compile、Projection、Analysis materialization 与 Page。返回的 `ReportExecution` 是
self-contained value，不持有 reader、handle、path 或 Scope，所以 `beforeMigration` 能活到 snapshot 关闭以后。

这条边界给出明确的可见性规则：

| 时刻 | 能看见刚发布 Run 吗 |
|---|---|
| `session.view` 创建后、publish 前 | 不能 |
| 同一个 `session.view` 中、publish 后 | 仍不能 |
| write session 关闭后的 fresh snapshot | 能；前提是 Run 有 complete marker |

## Report 到底怎样读

普通用户从 CLI 触发同一条一次性管线：

```sh
niceeval show --run 01H... --report ./reports/gpu-energy.ts
niceeval view --run 01H... --report ./reports/gpu-energy.ts
```

application host 也可以使用精确组合入口：

```ts
import { executeReportFromRecord } from "niceeval/report/host";

const execution = yield* executeReportFromRecord({
  root,
  recordAttachments,
  selection: {
    policy: "explicit-runs",
    input: { runIds: [runId] },
  },
  report,
});
```

`executeReportFromRecord()` 内部执行固定顺序：

```text
open scoped RecordReader
  → selectAnalysisSample(reader, selection)
  → reader-bound AnalysisSampleHandle
  → collect finite ReportData field declarations
  → compile dependencies; reject cycle / population mismatch
  → execute each unique Projection and field materializer at most once
  → closed rows → Page / PageFamily / Download
  → close reader
  → immutable ReportExecution
```

只有 field closure 请求的 Attachment 会被读取。六态结果留在 `ProjectedSample` 与 host-owned problem table；Record I/O
failure 留在 Effect error channel。`show`、HTTP 页面请求和 static renderer 只消费已经关闭的 execution，不再打开
Record。`view` 只有在 rebuild 时创建下一份 snapshot 与 execution。

## migration 为什么是第三个 facet

普通 read 遇到 known old Attachment 只返回 `migration-required`；普通 write 只写 adapter 的 current payload。两条路径
都不调用 converter。

`planMigration()` 在 runtime 已绑定的 canonical root 上检查 installed installations、完整相邻 graph、source identity、
Git restore point 与 sentinel，然后返回 opaque plan。`plan.summary` 可呈现；plan 的 private state 绑定 exact runtime、
source snapshot、registry identities 与 Git inspection，不能从 JSON 重建。

needed plan 先由 `authorizeMigration({ plan, decision })` mint plan-bound nominal authorization；结构相同的对象、另一个
plan 或另一个 runtime 都无效。`migrate({ plan, authorization })` 要求所有 write/snapshot child Scope 已关闭，然后取得
exclusive maintenance lock。

它创建并 sync `migration.in-progress`，执行 adjacent converters，复用 generic schema / plain-data / closure validators，
durable commit 后最后删除并 sync sentinel。

迁移期间不能有 live snapshot；反过来，outer `RecordAccessRuntime` 仍活着、verified-read cache 仍有 material，都不能成为
exclusive maintenance 的 busy 原因。迁移成功后必须打开第二个 fresh snapshot：旧 generation 与旧
`ReportExecution` 不会被原地刷新。

## 同一 runtime 共享什么，又不共享什么

| 机制 | write / read / migrate 是否复用 | 是否让调用者观察 |
|---|---|---|
| canonical root identity | 复用 | facet 不能换 root |
| runtime registry 与 installed installations | 复用 | 只通过 typed states / plan 体现 |
| maintenance / writer lock authority | 复用 | acquire 顺序与锁对象隐藏 |
| snapshot generation allocator | 复用 | 只能通过 fresh/closed 行为观察，不能比较数字 |
| schema、plain-data、blob closure validators | 复用 | typed read/write/migration error 可见 |
| exact-content verified-read cache | 复用 | hit、miss、size、eviction 全部不可观察 |
| owner-specific binding | 每个 occurrence 独立 link | callback 看不到；host 只推导内部 exact adapter grant |
| migration authorization | 不复用；仅 maintenance host | producer、Analysis、Report 都拿不到 |

verified-read cache 只复用已经证明过的 exact envelope、payload bytes 与完整 closure material。它不能缓存 Run enumeration、
path 到 current content 的映射、owner handle、draft、read state、lease 或 migration 中间态。reuse planning 则是可见的
Experiment domain policy；cache hit 绝不是“这个 Attempt 可以复用”的业务理由。

## 顺序反例

| 反例 | 为什么不成立 |
|---|---|
| 在 `withWriteSession()` callback 内分析刚 publish 的 Run | `session.view` 不刷新；会得到旧 membership |
| 让 `FrozenRecordView` 或 `AnalysisSampleHandle` 逃出 callback | generation 关闭后 capability 拒绝使用 |
| 保持一个 live snapshot，同时调用 `migrate()` | shared maintenance lease 阻止 exclusive maintenance |
| 让 read 在遇到 v1 时顺手执行 converter | read 不写磁盘；只返回 `migration-required` |
| migration 后继续使用旧 `ReportExecution` 当作新结果 | execution 是旧 snapshot 的 closed value，不会自动刷新 |
| 为 write、view、migrate 各建一个 root client 与 cache | 会重开 root identity、lock 与 generation 语义；目标契约只有一个 substrate |

## 这套心智模型屏蔽了什么

普通用户只需要记三句话：

1. Eval 只配置领域 Plugin；领域 SDK 对每个实际 owner 产出 sealed value；
2. Analysis 与 Report 只调用 SDK 的领域读取与汇总 API；
3. schema 旧了由 application 显式安装对应 SDK capability、运行 maintenance migration，再开新 snapshot。

Record adapter、锁、cache、path、sentinel 与 durable commit 顺序由 SDK／host 屏蔽；owner、领域状态、六态读取结果、
Sample denominator 与 migration requirement 必须向 Analysis 上层保留。
