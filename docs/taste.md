# NiceEval 的品味

品味是审阅 Spec 与代码时共同的判断标准：规则写不到的地方按品味选择，审阅时可以链接某条品味指出哪里不合适。这个文件存在时其中的条目生效，修改历史由 Git 保存。

## 总则 {#general}

1. 品味是判断标准，不是逐条检查的规则；条目之间需要取舍时，在变化说明或 Memory 中写明理由。 {#general-use}
2. 依据某条品味的句子旁写指向其 ID 的链接，ID 一经采用不改名、不复用。 {#general-link}

## T-1 按理想形态设计 {#t-1}

NiceEval 仍是 beta，为旧习惯保留的兼容层会让 API 和契约同时存在两套说法。

- 好的样子：API、CLI 与契约按理想形态定稿，调用方随之迁移。
- 坏的样子：为了不改调用方而保留旧参数、旧格式或双轨实现。

## T-2 docs 写目标，不写现状 {#t-2}

`docs/` 是已定稿的目标契约。把它改成当前实现的说明书，目标就跟着实现一起退化了。

- 好的样子：代码还没达到契约时，修代码，或在 Memory 中写下实现任务；文档只写目标规范与领域契约，历史交给 Git。
- 坏的样子：因为实现没做到，就把文档改成 `目前只支持……` 的说法；在 `docs/` 下堆积历史迁移备忘、草稿与临时脚本。

## T-3 core 保持中立 {#t-3}

core 偏向某个 provider 或 adapter，其它接入就只能绕路。边界以 [架构](architecture.md) 为准。

- 好的样子：provider 特有的行为留在对应 adapter 中。
- 坏的样子：core 里按 provider 名称分支。

## T-4 设计只落在 docs {#t-4}

另写的执行计划会复述一遍契约，并在下一次迭代时落后于 `docs/`。

- 好的样子：要做什么写进 `docs/` 正文，为什么写成理由句或 `reference/`，弯路写进 `memory/`；多个 agent 按 `docs/` 的目录边界分工。
- 坏的样子：维护一份任务分解或计划文件，按其中的节点切分工作。

## T-5 缓存只让运行变快，不改变结果 {#t-5}

缓存是可失败的优化。缓存故障一旦让任务失败，或把来历不明的状态当成命中，用户就只能关掉缓存，花的钱也说不清。

- 好的样子：缓存查不到、恢复失败、服务拒绝保存时，退回真实执行并照常完成，结果里标出没有用上缓存；只有被缓存的步骤本身失败时，任务才失败。
- 坏的样子：快照请求超时让依赖它的整批任务失败；恢复到一半的状态仍报告命中。

## T-6 Provider 交出原语，协议归 core {#t-6}

每个 Provider 各写一遍账本、租约、校验和失败回退，就会各有各的漏洞，core 也只能信任它们的自述。这是 [T-3](#t-3) 在接入层的延伸。

- 好的样子：Provider 声明一种能力时，同时交出这种能力需要的原语，缺一项就无法通过类型检查；多个 Provider 共用的流程由 core 实现一次。
- 坏的样子：能力名写在一个字段，实现放在另一个可选字段，运行时发现缺失就跳过；三个云 Provider 各自维护一套缓存账本。

## T-7 对比组之间的差异都是声明过的 {#t-7}

一次比较可以同时评估多个条件，但组间每一处差异都必须来自实验声明；夹带没声明的差异，结果就无法归因，整轮实验的钱白花。见 [MB-1、TB-3](user-story.md)。

- 好的样子：被测应用、模型、提示词与检索条件等变量写在实验声明里，可以同时有多个；任务、判分与预算这些没被声明为变量的条件在各组之间保持相同；无法进入同一运行条件的组合在运行前排除。
- 坏的样子：为了让某个应用能跑，悄悄给它换一个简化版运行条件，再和其它被测对象放进同一张表。

## T-8 执行错误不是被测应用失败 {#t-8}

基础设施故障记成被测应用未通过，会把服务商的问题算到被测产品头上。见 [MB-7、OPS-2](user-story.md)。

- 好的样子：判定只回答被测应用是否完成任务；Sandbox、外部服务、网络或凭据故障是执行错误，单独计数，修复后只补跑这些任务。
- 坏的样子：外部服务抖动的任务显示为未通过；为了让总数好看，把执行错误从分母里悄悄去掉。

## T-9 不知道就说不知道 {#t-9}

缺失的数据被显示成零、通过或失败，复核者就会基于不存在的证据做判断。见 [AUD-2、TUT-5、MA-1](user-story.md)。

- 好的样子：未运行、跳过、证据不足和真实结果分开显示，并说明缺口来自哪里。
- 坏的样子：没有用量数据的运行按零成本计入平均值；裁判不可用的评价记为通过。

## T-10 判据不让被测方看见 {#t-10}

被测系统能看到隐藏测试或参考答案，分数就衡量不了真实能力。见 [MB-6、TB-4](user-story.md)。

- 好的样子：隐藏判据只在被测系统交互结束后出现；所有对比组接受同一份最终检查。
- 坏的样子：为了方便调试，把测试参考答案放进工作目录；被测工具能读到判分材料。

## T-11 沿用结果靠身份证明 {#t-11}

沿用不该沿用的结果，判断就是错的；无关变化作废整批结果，用户就要多付一遍钱。见 [RUN-1、RUN-2、RUN-5、RUN-8](user-story.md)。

- 好的样子：只有影响执行的输入进入身份；身份相同才沿用，身份变化时说明是哪一项；复用运行条件时每道题仍真实执行。
- 坏的样子：改了判分标准仍沿用旧判定；只改报告标题却触发整批重跑；把复用的运行条件当成沿用的结果。

## T-12 每个数字都能追到运行 {#t-12}

只能看、不能追的汇总数字没法复核。见 [AUD-4、AUD-8](user-story.md)。

- 好的样子：完成率、成本和耗时都能展开到组成它的运行，并写明纳入和排除规则；终端、浏览器和脚本看到同一组数字。
- 坏的样子：报告里的数字只存在于渲染结果中；不同入口各算一遍口径。

## T-13 花钱之前先看清 {#t-13}

模型额度和云实例是真钱，批次跑到一半才发现配置错了，前面的花费就浪费了。见 [REL-2、TB-6、TB-8](user-story.md)。

- 好的样子：运行前就能看到题目数、运行次数、并发、能否运行及原因，以及准备能被加速到什么程度；可以先用官方答案或一个小切片验证评测链。
- 坏的样子：只有开始运行后才报告缺少运行条件；静默地为每个任务重复付一次准备费用。

## T-14 测试就是测试，不搞侵入式 Lint 与双写守护 {#t-14}

把测试包进自定义的 Lint、或把代码工程与编译器配置写入文档，会让契约和验证职责混乱；把推导生成的内容签入 Git 再逐字节比对，等于制造了第二份重复事实。

- 好的样子：`docs/` 只放 Markdown 规范与领域术语，代码契约由标准单元测试或类型测试验证；推导内容由构建管线生成，测试只验证生成逻辑本身；说红绿的一律是测试工具，不发明独立的 `lint/` 目录或伪装成 lint 的脚本。
- 坏的样子：在 `docs/` 下建 `tsconfig.json` 和代码原型强行跑 `tsc`；为了防止生成内容变化而在 Git 里双写并逐字节比对守护；用正则匹配源码文本假装做行为测试。

## T-15 一件事只查一次，快到每次都愿意跑 {#t-15}

慢的门禁会被跳过，重复的步骤不仅浪费时间，还会在两边不一致时带来困惑。

- 好的样子：门禁流水线职责清晰，关系、用词与规范由 Concord 一次性完成，各工程的类型检查与单元测试各自只跑一次；重型网络任务（如全网链接检查、外部站点渲染）作为独立或异步验证，不阻塞本地代码交付。
- 坏的样子：`concord check` 已经检查过文档正文，门禁又套一层并发重复跑；把依赖外部网络的重型站点扫描和本地代码门禁绑在同一个高频命令上。

## T-16 单一控制原语胜过多重限流 {#t-16}

重叠的限流策略只会增加调度复杂度和排查成本。

- 好的样子：并发只认唯一的最大并发限制；请求偶发受限时依靠带抖动的退避重试，不引入多重重叠的流控令牌桶或分布式租约。
- 坏的样子：同时配置并发数、RPM、TPM 与数据库行锁租约，遇到阻塞时无法判断哪个限制生效。

## T-17 统一 check 接入，断言只出 Match {#t-17}

断言入口保持极简，评价算子只输出标准匹配规则。

- 好的样子：无论是值对比、正则、语义相似度、裁判模型还是 RAG 忠实度，统一作为 Match 登记；内部状态走单参 Contextual Match 自动读取，外部返回值走双参显式传入，不让作者手动提取变量保存状态。
- 坏的样子：为每类新指标发明专属断言方法或第二套执行器；把断言机制拆成多个不兼容的求值方言，或要求作者在测试中手动搬运内部状态。

## T-18 业务代码直接调用，不强加 Adapter 壳 {#t-18}

测试的本质是普通代码调用，简单场景不引入中间层。

- 好的样子：普通函数和无状态应用直接在测试中导入并调用；Adapter 仅作为会话协议或有状态外部系统的可选连接器。
- 坏的样子：评测一个纯函数也要强制实现工厂对象、声明生命周期上下文与注册驱动器。

## T-19 链路主干统一，细节属性开放 {#t-19}

链路追踪既不能过度僵化，也不能完全失去结构。

- 好的样子：树形拓扑与核心角色（llm、retriever、tool、chain）统一，保证瀑布图与通用断言开箱即用；业务专有参数在属性中自由扩展。
- 坏的样子：为每个业务自造一套完全不兼容的追踪格式，使报表无法汇总；或写死全部字段导致自定义步骤无法表达。

## T-20 观测冷热分离，Attempt 即跑即释 {#t-20}

高并发批量评测不能让内存和存储随样本规模无限制膨胀。

- 好的样子：Attempt 结束立即封口并释放内存引用；指标与角色摘要存入主结构支持秒级聚合，大段检索文本与长 Prompt 进入分块冷存储按需读取。
- 坏的样子：全量 Trace 长期常驻内存堆直到整批跑完；把万字检索切片写入主表 JSON 导致读取报表时引发严重的 I/O 读放大。

## T-21 AI-Native 直率交付，不搞家长式脱敏与机器刷屏 {#t-21}

面向 AI 原生调用时，过度脱敏、遮蔽参数和向机器输出带终端控制符的动画，既浪费上下文 token，又阻碍排查。

- 好的样子：面向机器输出保持高信噪比与增量交付；命令、参数与模型自述完整暴露，不进行假性遮蔽或截断；非 TTY 或 `--json` 下零 ANSI 控制序列，只在状态变化时发射紧凑事件。
- 坏的样子：打着安全旗号把实际命令和报错信息遮蔽成 `tool: shell` 或 `[REDACTED]`；在管道中输出带光标回退的终端动画，撑爆 Agent 上下文；每个周期重复倒出一整包未变化的数组，浪费 token。

## T-22 委托成熟基础设施，保留现场第一方眼睛 {#t-22}

评测系统的本质是调度生命周期、断言判分与事实裁决。把执行管道、终端交互、跨机集群与长尾生态的轮子各造一遍，只会造出充斥死锁与兼容问题的劣质中间层。但属于人类现场调试的核心辅助——如单次 Attempt 调用耗时瀑布图与真实终端反馈——绝不能因推卸责任而丢弃。

- 好的样子：生命周期门禁（挂起、断点）与现场裁决归 core。容器直连、跨机矩阵调度与镜像构建委托底层原生 CLI（Docker / Instabox / Git / CI Matrix）；提供直观的单次 Attempt 耗时瀑布图与时间树，让人一眼看清瓶颈是 Sandbox 准备慢、工具调用耗时还是模型延迟。
- 坏的样子：自建中间伪终端（PTY）代理隧道或二次命令封装；自研多节点分布式任务调度集群；自写全网大模型客户端网关；为了所谓“全部推给外部 APM”而剥夺本地现场排查开箱即用的耗时瀑布图。

## T-23 标记写它对结果的作用 {#t-23}

所有条目都显示成同一种通过或失败，读者就分不清哪一条决定了判定，哪一条只是得了零分。这是 [T-9](#t-9) 在断言呈现上的延伸。

- 好的样子：决定判定的质量门、只贡献分数的条目和只供观察的条目各用各的标记；计分条目直接显示得分；汇总按作用分别计数。
- 坏的样子：零分的计分项显示为通过；只用来提前停止的条件显示成失败的质量门，让一条通过的结果看起来自相矛盾。

## T-24 Match 只承诺它看得见的事 {#t-24}

名字听起来懂语义、实际只做字面比较的 Match，会让作者以为禁区已经守住。不支持的写法被静默当成不匹配，检查就永远放行。

- 好的样子：Match 的说明写清它比较的是什么、不理解什么，并指出需要更强判断时改用哪个入口；不支持的输入在构造时报错。
- 坏的样子：路径匹配悄悄接受通配符却从不命中；把“排除这个路径”的命令算成读取，又不在任何地方说明这一点。

## T-25 成对的问题给成对的入口 {#t-25}

只提供一半的入口，另一半就由每个项目各写一个辅助函数，写法和漏洞各不相同。

- 好的样子：能声明“只许改这些”，就能同样直接地声明“不许改这些”；最常见的判据形态一行写完，仍然是一个普通 Match（[T-17](#t-17)）。
- 坏的样子：作者为了保护几个文件，自己读回内容逐个比对；三个项目各自封装同一个“满足或不满足”的裁判。

## T-26 一道题读一个文件就看懂 {#t-26}

题面、续轮回答和判据散在几个共享模块里，审阅者就说不出这道题测什么、什么算通过。

- 好的样子：每道题自己持有题面、续轮回答和全部判据；共享模块只负责取证，不登记检查；几道题确实相同的判据放在题目旁边。
- 坏的样子：一个通用函数替十道题登记检查，读题的人要跳三层才知道扣分点；为了少写几行把判据藏进配置。

## T-27 题面说用户的话，判据核对事实 {#t-27}

题面里提示了做法，测到的就是提示而不是被测对象；判据核对措辞，换一种说法的正确回答就会被判错。

- 好的样子：题面只说用户要什么，不提 API、命令或该不该验证；判据核对从公开出口读到的结果、文件和工具调用，开放式回复交给裁判并写明满足条件。
- 坏的样子：题面写“用某个函数加一条检查”；断言输入里已经出现的词；把回复里有没有某句固定的话当成完成的证据。

## T-28 分不出好坏的题就换掉 {#t-28}

一道题在所有版本上都是满分，它已经不能说明哪个版本更好，继续跑只是花钱。

- 好的样子：按判据逐项比较各个候选，找出从不变化的判据；持续满分的题换成更难或更新的场景；看过失败并据此调过的题只算开发集。
- 坏的样子：用一排满分宣称文档已经足够好；为了保持历史可比，留着一批谁来都能过的题。

## T-29 写的顺序就是执行的顺序 {#t-29}

声明读起来是一个顺序，运行时按另一套数字重排，作者就只能靠试错和额外的依赖边把顺序拼回来。

- 好的样子：同一处连续写下的准备步骤按书写顺序执行；只有跨越不同声明方时才需要显式写先后；运行前的计划展示实际顺序和理由。
- 坏的样子：每一步都要再写一遍“依赖上一步”，还要给排序数字加一、加二、加三；链式写法被暗中调换。

## T-30 失效由内容决定，不靠作者改名 {#t-30}

要作者记得改一个版本后缀才能让缓存失效，迟早会有人忘，然后在旧状态上跑出新结果。这是 [T-11](#t-11) 在准备步骤上的延伸。

- 好的样子：脚本内容、版本和声明过的输入自动进入身份，改一个字节就重新执行这一步及其后续；名字只用于定位和显示。
- 坏的样子：在标识符后面手写 `v4`、`v5`；改了脚本却要手动清缓存；显示名的修改触发重新准备。

## T-31 走慢路径时说出原因 {#t-31}

预装没被认出、缓存没命中、结果不能沿用，这些都会多花时间或钱。只做不说，用户就无从修正自己的声明。这是 [T-13](#t-13) 的另一半。

- 好的样子：每次退回到安装、重新准备或重跑，都写出是哪一项不满足，以及怎样让它下次命中。
- 坏的样子：镜像里明明装了同一版本，仍然静默重装一遍；只报告身份不匹配，却不说变的是哪一项。

## T-32 入口只指路，不复述 {#t-32}

入口文件抄了一份下游的内容，下游一改，入口就成了过期的第二事实源，而读者最先读到的正是它。

- 好的样子：每一跳只指向下一跳：一句话给出地址，安装说明把读者送到随包索引，索引指向页面；一段文本只有一个出处，别处用链接。
- 坏的样子：在项目指引里抄一张命令表，版本一升就过期；安装说明里贴一份线上教程的摘要。

## T-33 下游的绕路是上游的缺口 {#t-33}

下游为了把事情做成而写的辅助函数、版本适配和取证脚本，每一个都在说明产品少了一块。把它们留在下游，下一个用户还要再写一遍。

- 好的样子：真实项目里出现绕路写法时，先判断它是不是产品该有的能力；是，就写进契约并在产品里实现，再让下游删掉绕路。
- 坏的样子：在下游的说明里沉淀一套“这里要这样绕”的惯例；公开命令读不到需要的证据时，改去读私有文件或实现源码。

## T-34 一个功能，一个名字，贯穿契约、源码与验收 {#t-34}

同一个功能在文档、源码和测试里叫三个名字、放在三种划分方式下，找一个行为就要先猜它被归到了哪里。

- 好的样子：目录按用户要做的事划分；一个功能的契约目录、源码目录和验收仓库用同一个词；功能自己拥有它的命令、宿主入口和错误文案，公共层只做组合与路由。
- 坏的样子：按技术层堆出 `utils`、`helpers`、`services`；一个功能的命令散落在全局命令文件里；为了复用把两个功能的内部结构互相引用。
