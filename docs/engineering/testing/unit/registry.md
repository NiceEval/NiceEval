# 风险类别登记：先声明，后写测

每篇 Feature 测试文档的“类别规范”是新增测试的准入面。本页定义登记流程与预算，不逐条复述测试 case。

## 风险类别是设计输入

风险类别与 Feature 契约同批定稿。设计变更影响 `docs/feature/**` 时，同批更新对应测试文档，说明：

- 哪类行为需要证明；
- fixture 如何区分正确算法与错误算法；
- 哪类错误不能静默放走。

具体场景由测试名枚举，docs 不维护第二份 case 清单。

## 写测流程

- 测试只实现已经声明的风险类别；无法指认类别的旧测试按 [Unit 核心判据](README.md#存在资格) 删除。
- 实现中发现新类别时，先补 Feature 测试文档并评审影响面，再写测试。
- Bug 回归仍归属 Feature 类别；确认旧实现会逃逸后，用 `// bug: memory/<条目>.md` 保存现象、根因与修法凭据。
- 测试文件首行用 `// cases: docs/engineering/testing/unit/<feature>.md` 声明唯一 owner。

## 类别预算

- 一个类别按等价类、边界值和状态组合展开，不按测试数量或代码行比例补齐。
- 同一场景的第二条测试默认是维护负担；若跨故障边界保留两处，必须分别说明会放走的错误不同。
- 没有新增契约的实现重构可以零新增测试。
- fixture 的区分力规则见 [Harness](harness.md)。

## 机器守护与评审

`test/docs/cases-registry.test.ts` 只保证测试与 Feature 文档没有整册脱钩，并验证 `// bug:` 引用存在。
类别是否唯一、是否越过 E2E owner、是否真的能杀死错误算法，仍由评审对照类别规范裁决。
