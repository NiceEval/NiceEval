By default, a Sandbox is destroyed after each Attempt ends. Most problems can be located first with `niceeval show @<attempt-locator>` or `niceeval view` by looking at the verdict, assertions, file changes, commands, and the call duration waterfall timeline. For the full workflow, see the [Debugging guide](/troubleshooting/debugging).

Some problems, though, can only be seen in a live environment:

- **The environment does not start**: installing dependencies fails during setup, or the agent CLI cannot start. The agent has not started running yet, so the conversation record is empty. The fastest fix is to connect to the live Sandbox and rerun the install command by hand.
- **The change is outside `git diff`**: which packages were installed globally, what configuration was written under `$HOME`, and what `PATH` actually is. Workspace file diffs do not include these.
- **Testing hypotheses**: a cold start plus installation takes minutes. When you want to test guesses one by one, keeping the environment is much faster than rerunning every time.

## Pause or keep state while running

Add `--pause-on-failure` or `--keep-sandbox` to `niceeval exp`:

```bash
# Pause on failure, retain the Sandbox, and wait for confirmation before cleanup
pnpm exec niceeval exp local onboarding/tool-first --pause-on-failure

# Keep the Sandbox upon completion for offline debugging
pnpm exec niceeval exp local onboarding/tool-first --keep-sandbox        # Same as --keep-sandbox=failed
pnpm exec niceeval exp local onboarding/tool-first --keep-sandbox=all    # Keep passing ones too
```

`--pause-on-failure` blocks automatic teardown upon any assertion failure or error, printing native connect commands and waiting for user input.

When Sandboxes are kept, the summary clearly displays native connect and cleanup commands:

```text
╭─ KEPT SANDBOXES ─────────────────────────────────────────────────── 1 kept ─╮
│ @0123456789ABCDEFGHJKMNPQRS  onboarding/tool-first #1  errored  docker · a3f9c2d1 │
│            debug: docker exec -it a3f9c2d1 /bin/bash                       │
│            clean: docker rm -f a3f9c2d1                                    │
╰────────────────────────────────────────────────────────────────────────────╯
```

## Debug directly via native provider CLIs

NiceEval does not build intermediate terminal proxies or custom command wrappers. Developers and AI Coding Agents use battle-tested native CLIs directly:

### 1. Interactive debugging for developers
Run the native command directly in a new terminal tab:

- **Paused live Attempt (`--pause-on-failure`)**:
  The Sandbox remains running live in the background while waiting for confirmation:
  ```bash
  # Docker Sandbox (live)
  docker exec -it a3f9c2d1 /bin/bash

  # Instabox Sandbox (live)
  instabox ssh niceeval-97511d9a
  ```
- **Kept completed Attempt (`--keep-sandbox`)**:
  Docker stops the container upon completion to save memory while preserving disk state. Start it before entering:
  ```bash
  docker start a3f9c2d1 && docker exec -it a3f9c2d1 /bin/bash
  ```

Inside the container, you can rerun build commands to observe raw errors, verify `$HOME` configs, and check processes.

### 2. Automated non-interactive execution for AI Coding Agents
Coding Agents avoid entering interactive shells, and instead execute one-shot native commands to obtain structured output:

```bash
# Docker non-interactive execution (start first if container was stopped by --keep-sandbox)
docker exec a3f9c2d1 cat /workspace/build.log

# Instabox non-interactive execution
instabox exec niceeval-97511d9a -- ps aux
```

## Inspect and clean up residual resources

Sandbox resource management is delegated to mature native tools:

```bash
# Docker container management
docker ps -a --filter "label=niceeval.keep-candidate=true"                 # List kept NiceEval containers
docker rm -f a3f9c2d1                                                      # Destroy a specific container
docker rm -f $(docker ps -aq --filter "label=niceeval.keep-candidate=true")# Batch cleanup kept containers
docker container prune --filter "label=niceeval.keep-candidate=true" -f   # Prune only kept NiceEval containers

# Instabox instance management
instabox list                                                              # List active instances
instabox rm niceeval-97511d9a                                              # Destroy an instance
```

> [!NOTE]
> Running an unconstrained `docker container prune -f` removes all stopped containers system-wide. Always filter by `label=niceeval.keep-candidate=true` or use targeted `docker rm -f` to avoid deleting containers from unrelated projects.

Even if `niceeval.config.ts` has syntax errors, native CLIs remain 100% operational.

## Server-side safety net against client interruption

When evaluations run in cloud providers (Instabox, E2B) and the local client is killed by `kill -9` or a power outage:

- **Server-Side Hard TTL**: Creation requests enforce a server-side timeout deadline (derived from attempt deadline + 2m buffer, default 15m) to bound instance lifespan and mitigate billing leaks if the local client disconnects;
- **Idle Auto-Pause**: Cloud providers automatically suspend idle instances when network activity drops to zero where supported.
