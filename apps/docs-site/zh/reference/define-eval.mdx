`defineEval` 是编写评估用例的主要入口。每个评估用例文件调用一次，传入描述和 `test(t)`，并默认导出结果。

业务判据、证据和分值怎么组织，见 [NiceEval Taste](/zh/tutorials/niceeval-taste)。

```ts
import { defineEval } from "niceeval";

export default defineEval({
  description: "Brooklyn weather query",
  async test(t) {
    const turn = await t.send("What's the weather like in Brooklyn today?");
    turn.succeeded().label("Turn 完成");
  },
});
```

<Note>
  不要提供 `id` 或 `name`。NiceEval 根据文件路径生成评估用例 ID。
</Note>

## Test context: `t`

`t.note(label, value)` 记录供结果审阅使用的 JSON 值或 Quantity，例如 `t.note("延迟", ms(512))`。
它不登记 Assertion，不影响 Verdict、score 或 coverage。`null` 显示为 unavailable。
同一 Attempt 的 label 必须唯一，最多 64 项，每项 JSON 不超过 64 KiB；违规时抛出 `TypeError`。
`show @<locator>` 和 View 在 Assertions 后展示 Notes；JSON 与 Query 的 Attempt 结果包含 `notes`。
`show --exp <experiment-id>` 按 label 和单位聚合数值，展示 count、min、median、p90、max。

`t`（`TestContext`）是评估用例作者在 `test(t)` 里拿到的上下文。每调用一次检查方法，就登记一条断言。

- `t.check(subject, match)` 用匹配条件检查你显式传入的值。
- `t.check(contextualMatch)` 不传值，由 NiceEval 把当前的只读 ctx 交给匹配条件去读取。
- `t.judge(material, match)` 把材料交给 Judge 打分，走的是和 `t.check` 同一条登记路径。

root、Session 和 Turn 上的 `judge` 都要求显式传入材料。官方提供四个现成裁判，它们构造好匹配条件后同样交给 `check`。`closeQA(selector, question)` 先用 selector 选出一组材料，再让 Judge 回答一个验收问题。Agent 场景另有 `closeQA(question)`，默认读取当前作用域的完整历史，也可以传入 EventMatch 或 ToolMatch 只看部分事实。

断言默认怎样影响结果，取决于评估的类型：

- 通过制评估里，Boolean 断言默认决定 Attempt 的判定；计分制评估里，Boolean 断言默认只记录，不影响结果。
- 打分类的断言（measurement）默认不会让评估失败。两种评估里，加上 `.gate(minimum)` 后，分数低于下限才算失败。计分制里，同一条断言可以同时加 `.gate()` 和 `.score()`。
- `.orStop()` 让断言失败时停止后续步骤。Boolean 断言直接用自己的结果；measurement 写 `.orStop(minimum)`，或者在 `.gate(minimum)` 后面写不带参数的 `.orStop()`，沿用 gate 的下限。

普通的计算公式直接用 TypeScript 算，再用 `t.score(ratio, { weight: 50 }).label("完成耗时")` 登记。`ratio` 是 0 到 1 之间的数，`weight` 是非负的有限数。结果里会保留 ratio、对应的分值和实际得分。依据的数值材料拿不到时，这一项的得分记为未知。

`defineScoreEval` 的 `ScoreTestContext` 还提供 `t.score(n)`，直接登记一项得分；已有的断言用 `.score(n)` 计入分数。两处的 `n` 都必须是不小于零的有限数，写 0 也算一项明确的得分。工具调用的匹配与计数规则见 [匹配工具调用](/zh/reference/expect#匹配工具调用)。全部成员如下：

## Judge 打分

先用 `defineJudge` 声明评分标准，再直接交给 `t.check` 或 `t.judge`：

```ts
const factualSummary = defineJudge({
  name: "factual-summary",
  rubric: "根据 source 评价 summary 是否忠实保留事实，没有编造。",
});

const turn = await t.send("总结需求。");
t.judge({ source: expected, summary: turn.reply }, factualSummary)
  .gate(0.8)
  .label("事实一致");
```

Judge 材料可以是大小有上限的 JSON 值，也可以是 `judgeImage()` 生成的图片，登记时就会保存一份快照。

Judge 用哪个模型按顺序决定：先取项目配置的 `judgeProvider`，再应用评估用例的 `judge`，最后应用 Experiment 的 `judge`。后一层给的是完整 Provider 时，会整体替换服务和执行配置；只给模型字符串时，只换掉已选 Provider 的模型。评估用例的 `judge` 只决定这道题用哪个模型或 Provider，不限制能用哪些匹配条件。

通过制和计分制都可以调用 `.gate(minimum)`。计分制还可以调用 `.score(n)`，gate 失败时仍保留这一项的得分。

### 图片材料

从 `niceeval/judge` 导入 `judgeImage`，它会立即复制一份原图数据。限制如下：

- 格式只支持 PNG 和 JPEG。
- 每张最多 4 MiB、16,777,216 像素。
- 每条断言、每次模型请求最多引用 4 次图片，合计不超过 8 MiB。同一张图重复引用也会计数。
- 每个 Attempt 最多保存 32 MiB 图片。

NiceEval 只检查文件签名、文件头和尺寸，不会完整解码或转码图片。

`OpenAIProvider`、`VercelProvider` 和 `OpenRouterProvider` 默认不发送图片，需要显式设置 `supportsImages: true`，并选一个同时支持图片和工具调用的模型。`TypesafeProvider` 不支持图片。不支持时返回 `judge-capability-unavailable`，不会把图片换成文字描述再评分。

### 现成裁判与自定义 Match

`defineJudge` 和现成裁判都返回 `ScoreMatch`，可以直接交给 `t.check`。`t.judge` 只是同一条路径的简写，所以登记、快照、预算、打分、审计和结果保存都只发生一次。

| 裁判 | 输入 | 得分含义 |
| --- | --- | --- |
| `factuality()` | `{ input, output, expected }` | 一致为 1，不完整为 0.5，矛盾为 0 |
| `faithfulness()` | `{ input, output, context }` | 输出中有上下文支持的事实占比 |
| `instructionFollowing()` | `{ instructions, output }` | 满足明确要求的比例 |
| `pairwisePreference()` | `{ instructions, output, reference }` | 候选更好为 1，平局为 0.5，参考更好为 0 |
| `t.closeQA(selector, question)` | 一个从 ctx 读取材料、逐项判断的 MaterialMatch | 满足验收为 1，不满足为 0，证据不够时为 unavailable |

例如，直接使用 `instructionFollowing()` 的实例：

```ts
t.check(
  { instructions: ["说明集合地点", "不要编造具体时间"], output: post.content },
  followsInstructions,
).gate(0.7).score(25);
```

`faithfulness` 先从输出里提取事实，再逐项判断，最后由代码算比例。提取不完整时没有有效得分。TypeSafe 不支持 `extract`，所以在 `TypesafeProvider` 上结果为 `unavailable`，不会改成整体估一个分。
`pairwisePreference` 按固定顺序比较一次，适合一个候选和一个参考之间的比较。
`closeQA` 把选中的全部材料按原顺序一次交给 Judge，Judge 只根据这些材料回答验收问题。

Agent 场景可以用 `turn.closeQA(question)`、`session.closeQA(question)` 和 `t.closeQA(question)`。传入 EventMatch 时只看匹配的事件，传入 ToolMatch 时看匹配的工具调用的完整信息。

材料的情况会影响结果：选中的材料完整但为空时，得分为 0，不调用模型；材料不完整、无法判断或超出上限时，结果为 `unavailable`，不会截掉一部分再评分。

需要把多个模型步骤组合起来时，用 `defineScoreMatch` 的 `score(value, context)` 自己写评分逻辑。`context.llm` 提供 `score`、`classify`、`extract` 和 `batchClassify`，都返回 Effect。
它们和现成裁判共用调用预算、超时设置和审计记录。

- 静态的配置校验不会发网络请求。Provider、模型或 key 缺失时，也不会发请求。
- 聊天类服务用强制函数调用（forced-function）请求，TypeSafe 用 `/systemone` 接口，两者都会严格校验响应。
- 网络传输出错或超时，结果为 unavailable；HTTP 400 或协议不兼容，结果为 errored。

自定义 Match 必须可复用、不可变且无副作用，只比较显式传入的材料。它不保存调用位置、scope、label、score 或 gate，也不隐式读取 ctx。普通 evaluator 必须确定性；需要 LLM 时使用受管能力，遵守定义中的调用和材料预算。

## `Turn` 返回类型

`t.send(...)` 返回一个 `TurnHandle`。它包含从事件流整理出来的常用字段，以及一整套只针对这一轮的断言。

## 测试集导出

```ts
export default rows.map((row) =>
  defineEval({
    description: row.task,
    async test(t) {
      await t.send(row.prompt);
    },
  }),
);
```

导出数组时，每一项会得到稳定的 ID：`file/0000`、`file/0001`，依此类推。

已经有稳定的业务 key 时，也可以默认导出 `Record<string, EvalDef>`。例如 `swelancer.eval.ts` 里的 key `15193` 会生成 `swelancer/15193`。key 必须是非空的单段路径，不能是 `.` 或 `..`，不能包含 `/`、`\\` 或控制字符。评估用例按 key 的字典序排列。

### 从 ctx 读取材料，以及官方用量统计

`defineMaterialMatch<C,T>({ name, read, match, capture? })` 定义一组从 ctx 读取的材料，可以从 `niceeval` 或 `niceeval/expect` 导入。Adapter 的 `create` 提供应用自己的 ctx。在 `check` 或 `closeQA` 登记时，NiceEval 把当前的只读 ctx 传给 `read`。
`read` 返回 `{ state: "complete", items: [{ id, value }] }`，或者返回带 `reason` 的 partial 或 unavailable 状态。每项的 `id` 在本组内不能重复，最长 128 个 UTF-8 字节。

`capture` 控制保存多少材料，默认最多 256 项、48 KiB，最高可以调到 16384 项、4 MiB。

`check(materialMatch)` 返回 Boolean 断言，默认至少有一项满足条件才算通过。`closeQA(materialMatch, question, options?)` 返回 Judge 打分的断言：`question` 不能为空，最长 8 KiB；`options` 的类型是 `JudgePresetOptions`。选中的全部材料按原顺序一次交给 Judge。材料完整但为空时，得分为 0，不调用模型。
Agent 场景的 `read` 从 `AgentMatchContext<Scope>` 读取 NiceEval 整理好的工具调用（`toolCalls`）或事件（`eventOccurrences`），再分别用 ToolMatch 或 EventMatch 匹配。

`defineContextMatch<C,T>({ name, read, match, capture? })` 从 ctx 读取单个小的值。`read` 返回 `{ state: "available", value }` 或 `{ state: "unavailable", reason }`。配 BooleanMatch 时得到 Boolean 断言，配 ScoreMatch 时得到打分类断言。值拿不到时，不会调用评分逻辑。

`t.usage` 读取 NiceEval 官方记录的用量，读取时就固定下来。失败和重试的调用、缓存的分桶以及费用的计算依据都会保留。
- 普通 Adapter 的用量依据是记录下来的每一次调用（`recorded-calls`）。
- Agent 的用量依据是每次发送时上报的数字（`reported-sends`），可以按 Turn、Session 或 Attempt 查看。
- `usage.totalTokens` 等字段是 NumericMaterial。不知道的值保持未知，不会补成 0。

`t.maxTokens(max)` 限制 token 总量。`t.maxCost(usd)` 按美元成本限制：优先用实际扣费金额，扣费为 0 也算；没有实际扣费时，才用你显式配置的价格算出的估算。
`t.elapsedMs` 是从 Attempt 开始到读取这一刻经过的毫秒数，可以交给 `t.check(..., atMost(limit))`。业务里“第一次完成”的时间点仍要用业务自己的匹配条件判断。
