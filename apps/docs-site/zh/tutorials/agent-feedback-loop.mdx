你让 Coding Agent 修一个回归。它改完代码，你跑评估，把失败的输出复制给它，它再改，你再跑。来回几轮，大部分时间花在了搬运终端内容上。

更好的做法是让 Agent 自己完成这个循环：

1. 跑评估。
2. 从运行结束时的 receipt 里拿到这次的 Run ID。
3. 用 Run ID 查看结果，找到失败的那几次运行。
4. 判断该改应用、Adapter 还是评估用例。
5. 改完再跑同一范围，确认修好了。

这一页说明每一步该用哪个命令，以及 Agent 要遵守的几条边界。

## 先让 Agent 读安装版本的文档

Agent 凭训练记忆写出来的命令和 API，可能和你装的 NiceEval 版本对不上。先让它读跟着 npm 包发布的文档。

NiceEval 把中文文档放在 npm 包的 `docs-site/zh/` 目录，并在包根提供给 Coding Agent 用的 `INDEX.md`。Agent 先读 `node_modules/niceeval/INDEX.md`，再从索引进入当前任务需要的页面。

`pnpm exec niceeval init` 会初始化配置，并把一段托管指引写进项目的 `AGENTS.md`。项目只有 `CLAUDE.md` 时写进 `CLAUDE.md`；两份都没有时新建 `AGENTS.md`。升级 NiceEval 后再运行一次 `init`，就能刷新这段指引。

这段指引把两件事分开：

- 写代码时，Agent 当然可以读 `evals/`、`agents/` 等项目源码。
- 要证明某次运行发生了什么时，在终端用 `niceeval show`，要稳定的 JSON 用 `niceeval query`，浏览器审阅用 `niceeval view`。不要扫描 `.niceeval/` 下的原始文件，也不要拿当前源码反推历史运行。

这些命令看不到需要的信息时，让 Agent 直接报告“CLI 看不到”，不要绕过去读文件。

给 Agent 的起始任务可以直接写成：

```text
先读取 node_modules/niceeval/INDEX.md。
再按索引阅读与当前任务相关的页面。
使用命令运行 Experiment，并根据最后的 receipt 选择要查看的 Run。
```

## 运行并保存 receipt

让 Agent 用 `--json` 运行，并把输出存下来：

```sh
pnpm exec niceeval exp checkout --json | tee .niceeval-invocation.ndjson
```

`--json` 的每一行都描述这次运行的进度和诊断。最后恰好一行是 receipt：

```json
{
  "type": "receipt",
  "receipt": {
    "invocationId": "01J8ZK3M6P4T7V9X2C5N8QW0RY",
    "createdRunIds": ["01J9ZK3M6P4T7V9X2C5N8QW0RY"],
    "publicationCutoff": "{...}",
    "startedAt": "2026-08-09T10:00:00.000Z",
    "completedAt": "2026-08-09T10:01:00.000Z",
    "completion": "completed"
  },
  "summary": { "...": "..." }
}
```

Agent 只认最后这一行。`createdRunIds` 列出这次新建的全部 Run，后面查看结果就用它。`publicationCutoff` 不要解析，原样传给后续命令。

`completion` 是 `completed` 只说明这次运行结束了，不说明任务完成了，评估也可能没通过。receipt 也不是长期保存的结果格式，结果要通过 `createdRunIds` 去读。

## 用 Run ID 查看结果

运行结束后，Agent 先在终端打开 receipt 里的 Run：

```sh
pnpm exec niceeval show --run 01J9ZK3M6P4T7V9X2C5N8QW0RY
```

输出列出这个 Run 的分母、各评估用例的判定、分数、结果覆盖和每个 Attempt 的 locator。要细看某个 Attempt，复制它的 locator：

```sh
pnpm exec niceeval show @<attempt-locator>
pnpm exec niceeval show @<attempt-locator> --source
pnpm exec niceeval show @<attempt-locator> --execution
```

`show @<attempt-locator>` 显示这个 Attempt 的判定、断言摘要、各部分是否完整和已知限制。`--source` 显示这次运行用的评估源码和每条断言的结果。`--execution` 显示精简后的执行过程，要展开其中一项，复制它旁边的 ID 运行 `--execution --expand <stable-id>`。

需要让脚本、CI 或 Agent 稳定处理结果时，先找到可用的查询，再发送完整 request：

```sh
pnpm --silent exec niceeval query discover
pnpm --silent exec niceeval query explain --request request.json
pnpm --silent exec niceeval query run --request request.json
```

`query` 返回固定格式的 JSON。人要在浏览器里看时，用 `pnpm exec niceeval view --run <run-id>`；`view` 不接受 locator。

## 按看到的状态决定下一步

| 看到的状态 | 下一步 |
| --- | --- |
| Attempt `failed` | 对照任务允许的结果、实际产物、证据和断言条件，再决定改被测对象、Adapter 还是评估用例。 |
| `errored` | 检查错误正文、Adapter、Sandbox 或凭据。 |
| `not-recorded` | 这次计划要跑的某个 Attempt 没有结果，检查它为什么没跑。 |
| `core-invalid` | 阅读输出里写明的问题，不要把它当成没采集到。 |
| `partial` | 结果不完整。阅读分母和问题说明，确认哪些 Attempt 没有计入。 |
| `record-schema-unsupported` 或旧项目状态阻塞运行 | 保留原项目和历史数据，按[旧项目恢复指引](/zh/troubleshooting/debugging#旧项目状态阻塞运行)在项目副本里重新运行。 |
| 查询结果为 `unsupported` 或 `failed` | 只影响依赖这项输入的查看内容。阅读写明的问题。 |

处理 `failed` 时，不要为了通过一个过窄的 Match 去改本来符合任务的产物。产物满足任务、断言却拒绝了任务允许的结果，说明评估用例误判了，应该改评估用例。完整的归因流程见[排查手册](/zh/troubleshooting/debugging)。

## 修改后再跑一次

让 Agent 每次只验证一个假设：改程序或评估用例，运行同一个范围，再读新的 receipt 和 Run。

默认情况下，没受改动影响、上次已经有结论的 Attempt 会被沿用。运行前加 `--dry` 可以看到哪些会沿用、哪些会重跑，以及原因。需要所有 Attempt 都真实执行时，加 `--rerun all`：

```sh
pnpm exec niceeval exp checkout --rerun all --json
```

沿用和接受旧结果的规则见[修改后只重跑受影响的评估](/zh/tutorials/rerun-and-cache)。

运行结束只说明这次运行交接完了，不说明用户的任务完成了。

- 任务要求修好、且已有授权时，先修运行出错的问题，再只复验受影响的范围。
- 只要求分析时，只做归因，不改代码也不重跑。
- 业务失败符合任务预期时，保留这个结果并如实报告，不要为了变绿去改应用或评估用例。

## 结果保存后不能修改

已经保存的结果不会被修改。Agent 想得到不同的结果，就改程序或评估用例，重新运行，再用新 receipt 的 `createdRunIds` 查看。

需要把结果交给别人时，复制项目里的 [`.niceeval/record.sqlite`](/zh/explanation/record)，不要把终端输出或 NDJSON 当作分享格式。
