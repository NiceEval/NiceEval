写完一条评估，请同事只读正文，看对方能不能说出四件事：测什么、什么算通过、为什么这些证据够、分数怎么来。说不出来，说明判据还藏在代码里。

这一页给出写判据的原则，并用例子演示。声明与运行步骤见[编写评估用例](/zh/tutorials/authoring)，签名见 [defineEval 参考](/zh/reference/define-eval)。

## 四条原则

- **先写判据，再写代码。** 先用一句话写下业务要求，再挑最短、最忠实的写法。不要先遍历日志算出一个数，再给它起一个业务名字。
- **事实用确定性检查，含义交给 Judge。** 工具名、参数、次数直接检查；回答是否忠实、建议是否合理，才交给 Judge。
- **少造概念。** 能用已有事实、简单条件和几行算术表达，就不要命名新的业务概念。少一个概念比少几行代码更重要。
- **不知道就是不知道。** 缺记录、缺 token、材料超限时，保留“不可判定”，不要补成 0 或 false。

## 一切检查都是 `t.check`

NiceEval 只有一种检查：`t.check(事实, Match)`。事实是被检查的值，Match 是比较规则。调用时立即登记一条检查，返回的 handle 只配置这一条，比如 `.gate()`、`.score()`、`.orStop()`、`.label()`。

其它检查方法都是 `t.check` 的简写，读取的事实、比较规则和结果保存方式完全一样：

| 简写 | 等价于 |
| --- | --- |
| `turn.calledTool(m)` | `turn.check(turn.toolCalls, m)` |
| `turn.maxToolCalls(n)` | 检查本轮工具调用的确切次数，用 `atMost(n)` 比较 |
| `t.maxTokens(n)`、`t.maxCost(usd)` | 检查 Adapter 上报的用量，用 `atMost(...)` 比较 |
| `t.judge(material, judge)` | `t.check(material, judge)` |
| `closeQA(问题)` | 把问题和当前范围的材料编成评分 Match，再交给 `check` |

所以学会一套规则就够了：先选事实，再选 Match，最后在 handle 上决定它是门槛、计分还是停止条件。简写只是让常见的事实不用自己去取。

### 能用 Match 表达的，就用 Match

判据尽量写成 Match，而不是先在 JavaScript 里算出 `true` 或一个数，再交给 `check`。Match 会保留三种结果：满足、不满足、不可判定。它还会记下比较规则和命中的证据，报告里能看到为什么通过、为什么失败。

手写计算会丢掉这些信息。`calls.filter(...).length === 1` 只剩一个布尔值，记录不完整时还会把未知项当成没有发生。

| 想表达什么 | 用这些 Match |
| --- | --- |
| 选中某类工具调用或事件 | `toolMatch`、`eventMatch`，输入输出用 `jsonMatch`、`commandMatch`、`referencesAnyPath` |
| 次数 | `toolMatch(...).exactly(n)`、`.atLeast(n)` |
| 组合多个条件 | `and`、`or`、`not` |
| 集合里有几项满足、只看满足的那些、逐项投影 | `countWhere`、`filterWhere`、`mapEach`、`mapValue` |
| 先后顺序 | `inOrder` |
| 数值上下限 | `atMost`、`atLeast`、`lessThan`、`greaterThan` |
| 文本与结构 | `includes`、`pattern`、`equals`、`matches` |

对照一下两种写法：

```ts
// 不推荐：判据藏在计算里，记录不完整时会算错
const ok = items.filter((item) => item.status === "done").length >= 3;
t.check(ok, isTrue());

// 推荐：判据写在 Match 上，集合不完整时保留不可判定
t.check(items, countWhere(matches(DoneItem), atLeast(3))).label("至少完成三项");
```

`satisfies` 和 `defineValueMatch` 留到组合器确实表达不了的时候再用。它们只比较一个值，诊断里只剩你写的名字。

Match 本身不带门槛、分值和控制流。同一个 Match 在通过制里可以是门槛，在计分制里可以是 5 分，这些都写在 handle 上，不写进 Match。

被测对象是对话式 Agent 时，读完本页就够了。被测对象提供客服记录、游戏状态这类业务事实时，再读[自定义应用的评估判据](/zh/tutorials/niceeval-taste-application)。

## Agent 类评估

Agent 通过 `t.send()` 接收任务，返回消息、工具调用和 Turn 状态。这些事实 NiceEval 已经能直接读取，所以评估里直接用 Agent 的断言方法，不用再给工具名、参数或回复另写一套读取代码。

### 一个例子：查天气，再给出行建议

下面这条评估分两轮。第一轮让 Agent 查台北天气，第二轮让它根据查到的天气说要不要带伞。运行它需要两个前提：被测 Agent 提供 `get_weather` 工具，输入里有 `city` 和 `unit`；项目已经配置好 Judge。

```ts
import { defineScoreEval } from "niceeval";
import { atMost, jsonMatch, toolMatch } from "niceeval/expect";

export default defineScoreEval({
  description: "查天气后给出有依据的出门建议",
  async test(t) {
    const weather = await t.send("查询台北当前天气，温度使用摄氏度。");
    await weather.succeeded().gate().orStop();

    // 本轮必须完成正确查询，不能借用其它轮次的工具调用。
    await weather.calledTool(toolMatch("get_weather", {
      input: jsonMatch({ city: "Taipei", unit: "celsius" }),
      status: "completed",
    }).exactly(1)).gate().score(20).label("正确查询").orStop();

    const advice = await t.send("根据刚才查到的天气，说明是否需要带伞及理由。");
    await advice.succeeded().gate().orStop();

    // 验收需要查询结果和后续建议，交给 Judge 的是完整交互历史。
    t.closeQA("最后的带伞建议是否符合工具返回的天气，且理由没有编造天气事实？", {
      maxMaterialBytes: 256 * 1024,
      maxAuditBytes: 1024 * 1024,
    }).score(80).label("建议有依据");

    t.maxTokens(10_000).gate().label("用量上限");
    t.check(t.elapsedMs, atMost(30_000)).gate().label("运行耗时上限");
  },
});
```

读这条评估时，能直接看出这几件事：

- **分数怎么来。** 正确查询得 20 分，建议有依据得 80 分。用量和耗时只设门槛，不计分。
- **为什么查询要用确定性检查。** 调了哪个工具、传了什么参数，是能直接读到的事实，不需要 Judge 猜。工具名、输入、状态和次数全写在一个 `toolMatch` 上，`calledTool` 只是把本轮的工具调用交给它比较。
- **这些检查其实是同一种。** `succeeded`、`calledTool`、`closeQA`、`maxTokens` 和最后的 `t.check` 都登记一条检查，后面的 `.gate()`、`.score()`、`.orStop()` 用法也完全一样。
- **为什么建议要交给 Judge。** 回复里出现“雨”或“伞”，不能证明建议正确。工具返回下雨、Agent 也建议带伞时，还要 Judge 判断理由有没有编造天气。
- **为什么用 `.orStop()`。** 查询成功是第二轮的前提，查询失败时再问带伞就没有意义。如果你的任务允许查询失败后说明原因，就要为这条路径另写判据，不能照搬这里的前提。

### 先选范围，再选材料

同一个检查，放在哪一轮、给 Judge 哪些材料，结论可能完全不同。

| 想检查什么 | 怎么写 | 容易出错的写法 |
| --- | --- | --- |
| 这一轮有没有正确调用工具 | 在这一轮的 `turn` 上调用 `calledTool`，写明输入、状态和次数 | 整个 Attempt 里出现过一次同名调用，就判这一轮通过 |
| 这一轮的回答本身好不好 | `turn.closeQA(问题)`，用这一轮的完整历史 | 只按关键词判断解释或拒绝是否合理 |
| 后面的回答有没有遵守前文和工具结果 | 在覆盖这几轮的 Session 或整个评估上调用 `closeQA(问题)` | 只传最后一句回复，让 Judge 猜前文 |
| 某类工具调用的整体表现 | `closeQA(toolMatch(...), 问题)`，传入全部命中的调用 | 只拿第一条或成功的那条代表全部 |

给 Judge 的材料要够回答问题。传入 `toolMatch` 时只会选中工具调用；问题还涉及用户要求和回复时，就要传包含它们的完整历史。

评质量时不要先筛掉失败的调用、拒绝或澄清，它们本身就是表现的一部分。

完整历史有采集上限，所有 Adapter 都受此限制：单项消息、工具输入或工具输出的文本最多保留 16,384 字节。超限时，`show --execution` 的 Conversation 显示 `partial`，限制原因包含 `text-truncated`。Adapter 声明事件、消息或工具调用不完整时，完整历史也会是 `partial`。

这时 `closeQA(问题)` 的材料会显示 `partial / provider-limited`，检查为 `unavailable / source-unavailable`；这里的 `provider-limited` 不一定来自 Adapter。该检查若参与计分，计分制 Attempt 会是 `errored`。用 `query` 读取断言详情可查看原因，步骤见[查看结果](/zh/tutorials/viewing-results#看一条断言具体为什么得这个分)。

问题只需要任务、命令输入与回复时，可以把这些事实显式交给 `t.judge`。下面的例子需要项目已配置 Judge；它检查命令调用与完成说明是否符合任务，不评价文件正文是否正确：

```ts
import { defineScoreEval } from "niceeval";
import { defineJudge } from "niceeval/expect";

const judge = defineJudge({ rubric: "命令输入符合任务，调用状态为 completed，回复准确说明完成了什么。",
});

export default defineScoreEval({
  description: "检查命令与完成说明",
  async test(t) {
    const task = "运行 pwd，并说明当前目录。";
    const turn = await t.send(task);
    await t.judge({
      task,
      commands: turn.toolCalls.map(({ name, input, status }) => ({
        name, input, status,
      })),
      reply: turn.reply,
    }, judge).score(1);
  },
});
```

显式材料也有大小上限。材料不足或超限时保留不可判定；不要省略判据需要的工具输出，也不要用这段投影掩盖 Adapter 未采集到的调用。

多轮任务里，先想清楚每项要求属于哪一轮、哪个 Session。要检查工具调用顺序，用 `inOrder`，见 [Match 参考](/zh/reference/expect)。注意，先后发生不等于后一个调用用到了前一个的结果；要证明数据依赖，还要检查输入和输出。

### 能确定的，不要交给 Judge

两种常见写法都选错了证据：

- `judge("是否调用了天气工具？")`：调没调用是能直接读到的事实，让模型再判断一遍只会多一个出错的机会。
- `reply.includes("抱歉")`：关键词看不出拒绝是否合理，这需要 Judge 结合上下文判断。

用量和耗时也有现成的检查。`t.maxTokens(n)` 和 `t.maxCost(usd)` 比较 Adapter 上报的用量，`t.elapsedMs` 是这次运行的墙钟时间，交给 `atMost` 比较即可。不要在评估里自己累计日志、维护模型价格表，也不要把缺失的 token 补成 0。Adapter 没有上报的调用不会出现在 `t.usage` 里，字段存在不代表所有外部调用都被记下了。

### 要去现场找证据的，交给 Agent Judge

有些判据要看的东西不在回复里，而是散在运行环境里：Agent 改了哪些文件、写的代码怎么组织、命令能不能跑通。
不要先写脚本把这些内容收集起来、压缩到材料上限再交给 Judge，脚本漏收什么，Judge 就看不见什么。
被测对象有 Sandbox 时，用 `defineAgentJudge` 定义一个评审者，`t.agentJudge(reviewer, material)` 开一次评审会话，
再用 `review.judge(prompt)` 逐题打分。评审会自己读文件、跑命令，同一会话里后面的题能接着用前面看过的内容。
能直接读到的事实仍然用确定性检查；回复这类已经在手上的材料，仍然交给普通 Judge，它更便宜、更稳定。

### 判据平铺写在打分的地方

每一项检查按顺序写在评估正文里，问什么、给几分、叫什么名字都放在一处。
不要先把判据装进 `[名字, 分值, 问题]` 数组，再用循环登记：读者要在数组和循环之间来回对照，才知道某一项扣什么分。几项写法相近，重复几行也没关系。

## 交付前的共同检查

不管被测对象是 Agent 还是自定义应用，交付前都按下面三步检查。

### 分清停止、门槛和计分

`check` 登记一项检查，后面接的方法决定这项检查怎么用：

- `.gate()`：没满足就判不通过。
- `.score(weight)`：满足时贡献分数。
- `.orStop()`：没满足就停止后续步骤。它只管停，不代替 `.gate()`。

两种题型的默认值不同。计分制（`defineScoreEval`）里，普通检查默认只记录结果，加了 `.score()` 才计分、加了 `.gate()` 才成为门槛。通过制（`defineEval`）里，检查默认就影响通过与否。不要把两种题型的默认规则混用，详见[通过制与计分制](/zh/tutorials/evaluation-kinds)。

“满足就得分”的项，直接在检查上接 `.score(n)`，不要先算出布尔值再换算成分数。比如“至少完成三项得 10 分”，写成 `t.check(items, countWhere(matches(DoneItem), atLeast(3))).score(10)`。

只有业务本身定义了比例公式，组合器又表达不了时，才自己算出一个 0 到 1 之间的比例。这时用 `t.score(ratio, { weight: 50 })` 计分，贡献是 ratio × 50。只传一个数的 `t.score(points)` 表示直接加这么多分，两者含义不同。比例未知时，传入带不可用状态的值，这一项仍占 50 分的权重，不会被当成 0 分。

Judge 打分这类 0 到 1 的测量值，用 `.gate(minimum)` 设最低分，用 `.orStop(minimum)` 在低于最低分时停止。已经写了 `.gate(minimum)` 时，后面的 `.orStop()` 可以不传参数，沿用同一个最低分。证据不可用时保留不可用状态，不要先改成 `false` 或 `0` 再停止。

改写时不要顺手改变业务标准。比如“参与就加 5 分”和“每个人都必须参与”是两个要求，把 `.score(5)` 换成 `.gate()` 看起来更短，但要求变了。低分和零分可以是正确的结果，不要为了报告变绿而降低门槛或删掉失败项。

### 用真实运行验证

类型检查和构造通过，只说明写法没错，不能证明材料读取、取消、审计和业务判断都对。确认安装版本的导出和类型后，用 `pnpm exec niceeval exp <experiment>` 真实跑一次，让检查拿到真实 Adapter 提供的数据。不要私下调用 Match 的内部求值函数，也不要伪造断言上下文。

跑完后，用 `pnpm exec niceeval show @<attempt-locator>` 打开这个 Attempt，把问题分成三类：

- **技术错误**：调用或解析出了异常。
- **证据不足**：结果是缺失、partial 或 unavailable。
- **业务失败**：证据完整，但门槛没满足。

低分不是框架出错，零分也不等于证据缺失。哪一层出了问题就修哪一层，不要靠放宽断言换来通过。

交付时，分别说明 `--dry` 计划、类型检查、局部运行和真实端到端运行各验证了什么。文档构建通过不等于 Judge 验收通过；几个样本通过，也不等于长材料或整组任务都能通过。运行和读取结果的命令见[反馈闭环](/zh/tutorials/agent-feedback-loop)。

### 写作自检

提交前，用下面这些问题检查正文，并拿同一个 Attempt 的结果核对答案：

- 读者能说出目标、观察范围、每项通过条件和分值吗？
- 每项要求是“存在一次”“每一次都”还是“一次都没有”？完整性前提在哪里检查？
- 组合条件判断的是同一个事实吗？会不会混入其它 Attempt 的材料？
- 模型的选择、实际的执行和最终的结果分开检查了吗？成功属于被测对象本身吗？
- Judge 拿到了完整的相关材料吗？问题能根据这些材料回答吗？
- 缺记录、缺 token、未知费用和超出容量，都保留为不可判定，而不是零吗？
- 不打开函数实现，能读出状态、数量、阈值和组合关系吗？
- 每项判据的问题和分值就写在登记它的那一行吗？有没有藏进数组再用循环登记？
- 有没有为了给 Judge 准备材料而写取证脚本？要在运行环境里找证据的判据，交给 Agent Judge 了吗？
- 每项检查都能读成“哪个事实，用哪个 Match 比较”吗？能用现成 Match 组合的，有没有写成手算的布尔值或计数？
- 自定义 Match 只在组合器表达不了时才出现吗？它有没有被起一个多余的业务名字？
- 得分和门槛都能直接看到吗？前提不满足时，依赖它的后续检查停下了吗？
- 验证经过了真实运行和公开的结果命令吗？局部检查和真实运行分开说明了吗？
