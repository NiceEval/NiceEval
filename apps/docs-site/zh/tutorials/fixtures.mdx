评估 Coding Agent 时，只看它回了什么不够。你要给它一个真实项目，让它读写文件、运行命令，然后检查改出来的东西对不对。

这一切都写在普通的 `.eval.ts` 里，分三步：

1. 把起始项目放进 Sandbox，也就是 Fixture。
2. 给 Agent 发一个具体任务。
3. 用文件内容、命令结果和 diff 验收，开放式的质量再交给 Judge。

可运行参考见 [coding-agent-skill](https://github.com/CorrectRoadH/coding-agent-skill)（独立仓库）。

## 推荐目录结构

先把起始项目和评估用例分开放。Agent 能看到的只有你上传进 Sandbox 的部分，评估代码和验证材料留在外面：

```text
evals/
├─ api-validation.eval.ts
├─ config-schema.eval.ts
└─ ponytail-safe-path.eval.ts

workspaces/
└─ ts-starter/
   ├─ package.json
   ├─ tsconfig.json
   └─ src/

skills/
└─ zod.md

experiments/
├─ baseline.ts
└─ with-skill.ts
```

`workspaces/` 放 Agent 能看到的起始项目。`.eval.ts` 决定什么时候上传、发什么任务、怎么检查结果。`experiments/` 选择 Agent 和模型，以及是否加载 Skill 或插件。

## 把起始项目放进 Sandbox

Agent 要在一个真实项目里工作，第一步是把项目上传进 Sandbox：

```ts
import { defineEval } from "niceeval";

export default defineEval({
  description: "给 Express 路由添加请求体验证",
  async test(t) {
    await t.sandbox.uploadDirectory("../workspaces/ts-starter");

    await t.send("在 src/routes/users.ts 里实现 POST /users 路由。").then((turn) => turn.succeeded());

    t.sandbox.fileChanged("src/routes/users.ts");
  },
});
```

路径相对评估用例文件。上传的文件放在 Sandbox 的工作目录下，Agent 一开始就能看到。只缺一两个文件时，用 `t.sandbox.writeText()` 直接写入，适合小任务或安全检查脚本。

`fileChanged` 不通过时，先用 `pnpm exec niceeval show @<locator> --diff` 看 Agent 实际改了哪些文件。

## 写任务 prompt

Prompt 要像一张真实工单：写清目标和约束，但不要把验证答案透露出去。

```ts
await t
  .send(
    `在 src/config/env.ts 里实现环境变量校验。
要求：
- 用 Zod 定义 EnvSchema
- PORT 转成 number
- DATABASE_URL 必须是合法 URL
- JWT_SECRET 最少 32 个字符
- 导出 env 对象和 Env 类型`,
  )
  .then((turn) => turn.succeeded());
```

“是否防路径穿越”“是否复用现有工具”这类没写进需求的质量要求，留到验证阶段再查。这样才能测出 Skill 或插件是否真的让 Agent 主动补上了这些考虑。

## 验证文件和代码

Agent 跑完后，读出它改过的文件，检查关键代码是否到位：

```ts
import { not, pattern } from "niceeval/expect";

const code = await t.sandbox.readText("src/config/env.ts");

t.check(code, pattern(/z\.object\s*\(/));
t.check(code, pattern(/EnvSchema\.parse\s*\(\s*process\.env/));
t.check(code, not(pattern(/process\.env\.\w+\s*\?\?/)));
t.sandbox.fileChanged("src/config/env.ts");
```

`t.sandbox.fileChanged()` 只看 Agent 在 `t.send()` 期间的改动，判断目标文件有没有被它改过。你自己上传或写入的文件不算。记录规则见 [Sandbox Agent · 让文件改动能被记下来](/zh/tutorials/sandbox-agent#让文件改动能被记下来)。

## 运行项目测试或检查脚本

文本匹配只能看代码长什么样，跑一遍才知道它对不对。对 Coding Agent 任务，真实命令通常更可靠。下面在 Agent 跑完后写入一个检查脚本并执行：

```ts
await t.sandbox.writeText(
  "_test_traversal.py",
  [
    "import sys, os",
    "sys.path.insert(0, '.')",
    "from uploads import safe_upload_path",
    "base = '/var/uploads'",
    "try:",
    "    p = safe_upload_path(base, '../../etc/passwd')",
    "    assert os.path.commonpath([base, os.path.abspath(p)]) == base",
    "except (ValueError, PermissionError, AssertionError):",
    "    pass",
    "print('ok')",
  ].join("\n"),
);

const result = await t.sandbox.runCommand("python3", ["_test_traversal.py"]);
t.check(result.stdout.trim(), pattern(/ok/));
```

也可以直接跑项目自己的 test、lint 或 build 脚本：

```ts
import { commandSucceeded } from "niceeval/expect";

const result = await t.sandbox.runCommand("npm", ["test"]);
t.check(result, commandSucceeded());
```

`commandSucceeded()` 不通过时，用 `pnpm exec niceeval show @<locator>` 查看命令的退出码和输出。

## 用 Experiment 做对照组

要知道 Skill 或插件有没有用，就让同一批任务分别在装和不装的条件下跑。条件写在 Experiment 里：它选择 Agent、固定运行配置。命令行第一个参数选 Experiment，后面的参数按 ID 前缀筛选评估用例。不要把 Agent 名、插件名或 URL 写进命令行参数。

```bash
pnpm exec niceeval exp compare
pnpm exec niceeval exp compare api-validation
```

典型的 A/B 对照：

- `experiments/baseline.ts`：不加额外配置的 Agent。
- `experiments/with-skill.ts`：同一个 Agent，用生命周期 Hook 或 [Plugin](/zh/tutorials/plugins) 写入 `CLAUDE.md`。
- 两组用同一批评估用例、同一模型、同样的 `attempts` 和预算。

两组都跑完后，用 `pnpm exec niceeval show --experiment baseline --experiment with-skill` 在终端对比，或用 `pnpm exec niceeval view` 在浏览器里看。两组成绩几乎一样时，先确认 `with-skill` 的 Sandbox 里真的有 `CLAUDE.md`。

## 什么时候用 Fixture

- Agent 要修改真实文件。
- 要运行项目的测试、构建或 lint。
- 要比较代码改动。
- 评估的是 Claude Code、Codex 这类 Coding Agent。
- 要比较 Skill、插件或 Hook 能否改善真实任务的结果。

如果被测的是普通对话应用，不需要文件和命令，直接用对话 Adapter 接入更轻，见[接入你的 Agent](/zh/tutorials/connect-your-agent)。
