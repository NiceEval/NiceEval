---
title: "评估自定义应用"
description: "保留应用自己的方法与上下文，用 NiceEval 评估结构化结果和业务操作。"
---

应用可以提供发帖、生成图片、刷新时间线等方法。用 `defineAdapter` 创建连接，返回对象的顶层操作会成为评估中强类型的 `t` 方法。
Agent 是实现 `send(input, ctx) → Turn`、Session 和 Turn 的另一种 Adapter；自定义应用不要求实现这个 Agent 协议。

## 定义应用连接

下面连接一个已有的社交应用。`createSocialApp` 属于你的应用；返回对象明确列出评估需要的操作。

```ts application.ts
import { defineAdapter } from "niceeval";
import { createSocialApp } from "./src/social-app.ts";

export const social = defineAdapter({
  name: "social-app",
  create(context) {
    const app = createSocialApp({ signal: context.signal });
    context.onCleanup(() => app.close());
    return {
      post: (text: string) => app.publishPost(text),
      reply: (postId: string, text: string) => app.reply(postId, text),
      visitDiscoveryPage: () => app.visitDiscoveryPage(),
      generateImage: (prompt: string) => app.generateImage(prompt),
    };
  },
});
```

运行器每个 Attempt 调用一次 `create`，并在结束时执行已登记的 `onCleanup` 回调。实例隔离由你的 factory 实现；运行器不保证返回独立实例，也不会释放未登记 `onCleanup` 的资源。
取得资源后立即登记 `onCleanup`。
把 `signal` 传到应用的网络请求和长任务，才能响应取消。

TypeScript 自动从返回对象推导方法参数和结果，不需要手写 `t` 的类型。
应用没有提供 `send` 时，`t.send` 会报类型错误。`check` 等 NiceEval 核心名称不能覆盖；已有类实例用上面的闭包方式暴露方法。

## 调用应用动作并自定义检查

`test(t)` 同时提供应用操作与评估能力。应用返回的 Post、Reply 等对象可以直接交给 `defineValueMatch` 定义的自定义 Match。

```ts evals/publish.eval.ts
import { defineValueMatch } from "niceeval/expect";
import { social } from "../application.ts";

const hasText = defineValueMatch<{ text: string }>({
  name: "推文包含文字",
  evaluate: (post) => post.text.trim().length > 0,
});
const hasReplyTo = (postId: string) =>
  defineValueMatch<{ replyToId: string | null }>({
    name: "回复关联目标推文",
    evaluate: (reply) => reply.replyToId === postId,
  });

export default social.defineEval({
  async test(t) {
    const post = await t.post("邀请大家周末一起看流星雨");
    t.check(post, hasText).gate().label("推文生成成功");
    const reply = await t.reply(post.id, "询问集合地点");
    t.check(reply, hasReplyTo(post.id)).gate().label("回复关系正确");
  },
});
```

这里的动作签名由你的应用决定。`defineValueMatch` 只描述值怎样匹配；`t.check` 登记 Assertion，`.gate()` 显式把 Boolean 条件设为质量门。也可以复用字符串、数值或 Schema 匹配器。
需要累计分数时使用 `social.defineScoreEval`，再对检查调用 `.score(points)`。
开放式语气、人物一致性或内容质量可以交给 [Judge](/zh/explanation/judge)。

## 在连接处定义断言方法

多个评估需要同一种检查时，在 Adapter 的 `assertions` 中定义便捷方法。它取得当前 Attempt 的 `app` 和统一的 `check`，返回原有断言 handle。

```ts application.ts
import { defineAdapter } from "niceeval";
import { defineValueMatch } from "niceeval/expect";
import { createSocialApp } from "./src/social-app.ts";

const hasText = defineValueMatch<{ text: string }>({
  name: "推文包含文字",
  evaluate: (post) => post.text.trim().length > 0,
});

export const social = defineAdapter({
  name: "social-app",
  create(context) {
    const app = createSocialApp({ signal: context.signal });
    context.onCleanup(() => app.close());
    return {
      post: (text: string) => app.publishPost(text),
      readPublishedPost: () => app.readPublishedPost(),
    };
  },
  assertions({ app, check }) {
    return {
      hasPublishedText() {
        return check(app.readPublishedPost(), hasText);
      },
    };
  },
});
```

```ts evals/publish.eval.ts
import { social } from "../application.ts";

export default social.defineScoreEval({
  async test(t) {
    await t.post("邀请大家周末一起看流星雨");
    t.hasPublishedText().gate().score(1).label("推文生成成功");
  },
});
```

`hasPublishedText()` 与显式 `check` 共享评分和报告。`defineEval` 的断言方法没有 `.score()`；`defineScoreEval` 的方法提供它。动作方法 `post()` 仍只执行应用操作。

在断言方法被调用时读取证据。`assertions` 本身只组装方法，不能提前调用 `check`；返回对象不能包含 getter、非函数值或与应用及核心成员重名的方法。
方法同步返回本次 `check` 的 handle，不返回 Boolean 或 Promise。异步动作、等待和证据封存放在应用方法中，在检查前显式完成。
证据不完整时应报告明确错误，不能当作空历史来判断“没有发生”。
便捷方法使用具体参数签名。无法保留类型关联的泛型或重载便捷方法不可调用；这类组合可以使用独立 Match 和显式 `t.check`，应用操作自身的泛型方法仍可使用。

## 选择实现并运行

```ts experiments/local.ts
import { defineExperiment } from "niceeval";
import { social } from "../application.ts";

export default defineExperiment({
  adapter: social,
  attempts: 1,
});
```

```bash
pnpm exec niceeval check
pnpm exec niceeval exp local
pnpm exec niceeval view
```

实验选择的应用必须满足评估声明的接口。接口不匹配时，NiceEval 会在创建应用前报错。
具体操作的顺序、参数和重复次数由评估代码决定；应用动作不会自动获得 Agent 的消息重试。
自定义方法可以命名为 `send`，其参数和返回值仍由应用决定，不需要构造 `Turn`。如果返回对象没有定义 `send`，`t` 也不会自动获得这个方法。

## 用相同评估比较两个实现

需要替换应用实现时，创建共同的类型化契约，再分别提供实现：

```ts
import { defineAdapterContract } from "niceeval";
import type { SocialContext } from "./src/social-app.ts";

export const social = defineAdapterContract<SocialContext>({ name: "social/v1" });
export const baseline = social.implement({ name: "baseline", create: createBaseline });
export const candidate = social.implement({ name: "candidate", create: createCandidate });
```

评估通过 `social.defineEval` 编写，两个 Experiment 分别选择 `baseline` 与 `candidate`。
只有共同接口里的方法可在该评估中使用；两个独立创建但同名的契约不能互换。

需要共享断言方法时，在创建实现前调用 `withAssertions`：

```ts
const social = defineAdapterContract<SocialContext>({ name: "social/v1" })
  .withAssertions(({ app, check }) => ({
    hasPublishedText() {
      return check(app.readPublishedPost(), hasText);
    },
  }));
```

从这个返回契约创建实现和评估，各实现就会使用相同检查。`withAssertions` 返回新契约，之前创建的实现不会自动取得这些方法。

执行身份同时包含 Adapter identity（`name`、`contract`、`behaviorRevision`）和 experiment 的 `flags`。评估用例静态项目内相对 import/export 闭包变化会自动使候选失效。
Experiment 单独选择的实现、动态 import、外部包和远端服务不在自动范围内。为这些行为声明非空 `behaviorRevision`，或用显式配置表达变化；未声明版本的自定义 Adapter 不会自动复用。

## 保存应用执行轨迹

应用结束并取得完整日志后，在 Adapter 内调用 `ctx.recordTrace`。每个事件保留自己的类型、主体、摘要和已知关系。
应用不用把操作包装成聊天消息。下面的事件只表示请求已接纳；实际完成应记录另一条事件。

```ts
const attachment = await ctx.attach({
  name: "events.json",
  mediaType: "application/json",
  body: JSON.stringify({ events: archivedEvents }),
});

const receipt = await ctx.recordTrace({
  traceId: sessionId,
  schema: { id: "social-app.execution", revision: 1 },
  collection: { state: "complete", limitations: [] },
  scopes: [],
  events: [{
    key: "accepted",
    type: "post.accepted",
    source: { id: "server", eventId: archivedEvents[0].eventId },
    actor: { id: "author", label: "Author" },
    summary: "Post accepted for publication",
    evidence: [{
      key: "original",
      label: "Original event",
      artifactId: attachment.artifactId,
      pointer: "/events/0",
    }],
  }],
});
```

`key` 是这份快照内的关联键，`source.eventId` 只填写应用真实提供的 ID；没有时省略。
返回的 `receipt.events` 给出可供查看的稳定 `eventId`。同一 `traceId` 重交相同快照返回同一身份，内容冲突会拒绝。
摘要有界，大输入通过证据引用精确定位到附件中的值，查看时不需要手动扫描整份日志。

```sh
niceeval show @<attempt> --execution
niceeval show @<attempt> --execution --expand <eventId>
```

清理回调在独立时限内仍可提交轨迹。取消与完整性是两回事：取消后取得完整日志可以是 complete，
缺少日志时使用 partial 并列出 limitations；不要用空集合表示未知。窗口外事件保留为 excluded 或 unknown，轨迹导入本身不产生评分。
已保存的轨迹与证据随 Record 搬迁，查看时不调用原应用或模型。

## 阅读结果

应用结果交给 `t.check` 后，NiceEval 保存有界检查材料和判定。
没有采集的会话、工具调用和费用保持缺失。没有 Turn 不代表用了零 token，Judge 的费用也不代表整个应用的费用。
自定义应用不能声明依赖完整应用费用的 `budget`，也不能声明 Agent 专属的 Sandbox 或会话能力。
当前生命周期 Plugin 依赖 Agent 的执行准备，自定义应用配置它们会在运行前报错。

完整可运行的模拟 X 示例位于 [LLM X 源码](https://github.com/CorrectRoadH/niceeval/tree/main/examples/zh/llm-x)。
它由 LLM 生成人物、个人主页、推文、配图和后续社交动态，并使用应用原生方法进行评估。
