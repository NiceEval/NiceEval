Coding Agent 要在一个能随意改文件、跑命令的环境里工作，而且不能碰到你的机器。这个隔离环境就是 Sandbox，由 Provider 负责创建和销毁。

本地调试可以用 Docker；Agent 需要自己运行 Docker 时用 Incus VM。需要云端环境时可以用 Vercel 或 E2B；已有 OpenSandbox 服务时可以直接连接服务 API。

不管用哪种 Provider，评估用例和 Adapter 看到的都是同一个 `Sandbox` 接口。换 Provider 只改 Experiment 里的一行，评估用例不用动。

## 选择 Provider

先按你在哪里跑评估来选：

| Provider | 适合 | 需要准备 |
| --- | --- | --- |
| Docker | 本地开发和标准 CI。简单、可控，不依赖云端 | 本机 Docker。机器资源有限，冷启动和装依赖可能较慢 |
| Incus VM | Agent 需要运行 Docker 或 Compose，并拥有独立内核 | 管理员部署的 Incus 环境、可信镜像与 Provider 描述文件 |
| Vercel Sandbox | 需要云端隔离、更多资源或更稳定的环境 | Vercel token 或 OIDC 配置 |
| E2B | 需要大量并行，或者想直接用现成的 Agent template | E2B 账号和 `e2b auth login` |
| Instabox | 从固定 snapshot 启动独立云端 Linux 机器 | Instabox API key、允许关闭自动暂停的计划和已准备的 snapshot |
| OpenSandbox | 通过已有服务管理远端容器 | OpenSandbox 服务入口、API key 和镜像 |

在 Experiment 的 `sandbox` 字段里选一个：

```ts
// experiments/local.ts
import { defineExperiment } from "niceeval";
import { dockerSandbox } from "niceeval/sandbox";

export default defineExperiment({
  agent: myCodingAgent,
  model: "claude-sonnet-4-6",
  sandbox: dockerSandbox({ source: { type: "image", image: "node:24-slim" } }), // 或 vercelSandbox({ snapshotId }) / e2bSandbox({ template })
});
```

评估用例和 Experiment 都没有选择 Sandbox 时，运行会在创建任何 Sandbox 之前报错，NiceEval 不会替你猜一个 Provider。

Provider 的 SDK 不随 NiceEval 一起安装。用哪个就装哪个，用不到的依赖（以及它们的原生构建脚本）不会进入你的项目：

| Provider | 安装命令 |
|---|---|
| `dockerSandbox({ source: { type: "image", image: "node:24-slim" } })` | `pnpm add dockerode @types/dockerode` |
| `incusSandbox({ image, project, storagePool })` | 无额外 npm SDK；宿主需部署 Incus CLI 与 Provider 环境 |
| `vercelSandbox({ snapshotId })` | `pnpm add @vercel/sandbox` |
| `e2bSandbox({ template })` | `pnpm add e2b` |
| `openSandbox({ image, targetPlatform, lifetimeMs })` | `pnpm add @alibaba-group/opensandbox@1.1.1` |
| `instaboxSandbox({ snapshotId, lifetimeMs })` | `pnpm add ssh2@1.17.0` |

漏装时，创建 Sandbox 的那一刻会报错并给出安装命令，例如 `Docker sandbox requires 'dockerode'. Install it with: pnpm add dockerode @types/dockerode`。照着装好再运行即可。

### 使用 Incus VM

在评估用例里用 `sandboxRequirements()` 声明 Docker、Compose 和最低数据容量，在 Experiment 里用 `incusSandbox()` 选择环境。每个 Attempt 使用独立 VM，结束后销毁；不支持 `--keep-sandbox` 或 `sandboxReuse`。

运行前先执行 `pnpm exec niceeval sandbox provider doctor incus`。开发环境使用单独的 `--development` 检查，并在 Experiment 显式设置 `acceptDevelopmentDomain: true`。完整配置和缓存维护命令见[让 Agent 在 Sandbox 中运行 Docker](/zh/tutorials/docker-in-docker)。

### 连接 OpenSandbox

服务与 execd 使用配套的 `release-1.1.1`，SDK 使用 `1.1.1`。旧 `execd:v1.1.0` 不支持此 Provider 所需的原生 argv。

在运行 NiceEval 的机器上配置 `OPEN_SANDBOX_DOMAIN` 和 `OPEN_SANDBOX_API_KEY`。地址是完整的 HTTPS URL；本机开发可使用 HTTP。凭据只用于宿主连接，不写入 Sandbox。

```ts
import { openSandbox } from "niceeval/sandbox";

const sandbox = openSandbox({
  image: "node:24-bookworm",
  targetPlatform: { _tag: "Linux", os: "linux", arch: "x64", libc: "gnu" },
  lifetimeMs: 60 * 60_000,
  resources: { cpu: "1", memory: "2Gi" },
});
```

目标平台填写远端镜像的平台，正式实验将镜像固定到 digest。`lifetimeMs` 必须覆盖 Attempt 剩余时限并预留 30 秒收尾；正常完成会立即销毁实例。可用 `user` 选择执行身份，用 `pathPrepend` 添加可执行文件目录。

Docker、Kubernetes 等 runtime 由 OpenSandbox 服务端选择，NiceEval 无需填写。服务入口只允许可信宿主访问，或在所有 HTTP 和 WebSocket 路径前置鉴权。OpenSandbox 的 Docker proxy 路由不受控制 API key 保护，不能直接暴露到公网。

镜像必须以 root 启动 execd，并提供 Bash 和 Git；用 `user` 让 Agent 以非 root 身份执行。交互 Coding Agent 还需要 Node.js 24。

命令取消或超时会销毁整个实例。此 Provider 不支持保留现场或跨 Attempt 复用；运行中的 Sandbox 也不会自动获得 Docker daemon。

服务启用 rootfs 快照后，digest-pinned 镜像可使用 before 准备缓存。缓存保存文件系统内容，每个 Attempt 从快照创建独立实例。它不保存运行中的进程、卷或 tmpfs；需要运行中的服务放在不可缓存的 command 步骤里启动。新增挂载或已知敏感内容会使该 Attempt 继续执行而不发布缓存。

用 `sandboxCache: { before: "bypass" }` 或 `--sandbox-before-cache bypass` 排障时，准备步骤会重新执行，并跳过缓存读取与发布。快照请求发出后若失败，当前 Attempt 会终止，已完成的准备步骤不会在该 Attempt 自动重跑。

接入服务时，需要验证销毁成功响应代表实例及其进程已停止。仅受理异步删除的服务不能满足这项要求；填写 runtime 名称无法替代验证。

### Instabox：从 snapshot 启动

在宿主的 `.env` 设置 `INSTABOX_API_KEY`，然后选择已就绪的具体 snapshot ID：

```ts
import { instaboxSandbox } from "niceeval/sandbox";

const sandbox = instaboxSandbox({
  snapshotId: "sn_your_snapshot_id",
  lifetimeMs: 60 * 60_000,
  spec: "instabox-medium",
});
```

Snapshot 需要 Linux x64 GNU 环境、Bash、Git、Node.js 24 或更新版本，以及可免密 sudo 的非 root 登录用户。默认工作目录是 `/data/home/workspace`。稳定依赖在构建 snapshot 时准备；服务启动和 Agent 鉴权在运行时处理，避免把登录凭据保存到 snapshot。

`spec` 优先支持官方标准规格 `instabox-small`、`instabox-medium`、`instabox-large`、`instabox-xlarge`、`instabox-2xlarge`，以及数值别名 `2/4`、`4/8`、`8/16`、`16/32`、`32/64`。显式 `resources: { vcpus, memMiB }` 优先于 `spec`；两者均省略时使用 `instabox-medium`。

每条 Attempt 创建独立 Machine，完成后删除；基础 snapshot 保留。`lifetimeMs` 是 60 秒至 24 小时的整秒毫秒数，至少覆盖 Attempt 剩余时限加 30 秒。它控制失联后的自动删除，正常收尾会提前删除。命令取消或超时也会删除整台机器。

此 Provider 不支持保留现场、跨 Attempt 复用或 before 快照缓存。SSH 连接需要宿主能够访问 Instabox gateway，HTTP API key 和 SSH token 都不会写入机器。创建会关闭 Vault 和 Org Secrets 自动注入。

Snapshot 构建步骤见[预制 Sandbox](/zh/tutorials/prebuilt-sandbox)。

### Docker Compose：`workspaceService` 指定主 Sandbox

一道题需要不止一个容器时（比如应用容器加一个数据库），用 `dockerComposeSandbox` 声明整份 Compose 环境：

```ts
import { dockerComposeSandbox } from "niceeval/sandbox";

sandbox: dockerComposeSandbox({
  file: new URL("docker-compose.yaml", import.meta.url),
  workspaceService: "client", // 主 Sandbox
})
```

`workspaceService` 指定 Compose 文件里哪个 service 是主 Sandbox。Agent、`t.sandbox` 的命令和文件操作、`workdir`、文件改动记录，都只落在这一个容器上。

其它 service（数据库、mock server 之类）只是陪跑的资源：不能对它们 `runCommand`、上传或读写文件，也看不到它们的文件改动。要用到它们，只能靠网络访问，例如在 `client` 容器里通过 Compose 内置 DNS 访问 `db:5432`。

### 让 Agent 自己运行 Docker

Agent 需要执行 `docker build`、`docker run` 或 `docker compose` 时，用 Incus VM 提供独立内核和 VM 内的 Docker daemon。配置步骤见[让 Agent 在 Sandbox 中运行 Docker](/zh/tutorials/docker-in-docker)。OpenSandbox 的服务端使用 Docker，并不代表 Agent 可以在容器里运行 Docker。

## 在 Adapter 和评估用例里操作 Sandbox

不管用哪种 Provider，Adapter 和评估用例拿到的都是同一个 `Sandbox` 接口。常用操作：

| 方法 | 用途 |
|---|---|
| `runCommand(cmd, args)` | 运行命令 |
| `runCommandOrThrow(cmd, args)` | 运行命令，非零退出时抛错 |
| `runShell(script)` | 运行 shell 脚本 |
| `runShellOrThrow(script)` | 运行 shell 脚本，非零退出时抛错 |
| `readText(path)` / `readBytes(path)` | 读取文本或二进制文件 |
| `writeText(path, content)` / `writeBytes(path, content)` | 写入文本或二进制文件 |
| `pathExists(path)` | 检查路径是否存在 |
| `uploadFile(source, target)` / `uploadDirectory(source, target?)` | 上传文件或目录 |
| `workdir` | Provider 里真实的工作目录。省略的 `cwd` / `targetDir` 都指向这里 |
| `runCommand(..., { cwd })` | 让单条命令在别的目录运行。相对路径按 `workdir` 解析 |
| `stop()` | 销毁环境 |

两个 `OrThrow` 方法抛出的错误消息会附带 stderr 的末尾几行，已经清理、脱敏并截断。stderr 为空时改用 stdout。排查时先看这段摘要，需要完整输出时再读 `SandboxCommandExitError.result`。

## 按顺序准备 Sandbox

Agent 开始工作前，Sandbox 里通常要先装工具、写配置、放好素材。用 `.before()` 写这些准备步骤，用 `.after()` 写无论成败都要执行的收尾。每个 Provider 函数都返回一个可以继续追加步骤的 `SandboxLayer`，追加时不会修改原来的值：

```ts
import {
  changeFrequency,
  dockerSandbox,
  shell,
  writeText,
} from "niceeval/sandbox";

const sandbox = dockerSandbox({
  source: { type: "image", image: "node:24-slim" },
})
  .before(shell({
    id: "install-tools",
    command: "corepack enable && pnpm install --frozen-lockfile",
    changeFrequency: changeFrequency.rare,
  }))
  .before(writeText({
    id: "experiment-env",
    path: ".env",
    text: "FEATURE_X=1\n",
    changeFrequency: changeFrequency.frequent,
  }));
```

同一个 layer 的 `.before()` 按书写顺序执行，回调也算一步，`.after()` 不会切断这条链。后一步的 `changeFrequency` 即使更小，也会等待前一步。

`changeFrequency` 决定不同链之间怎样交错：依赖满足后，数值小的步骤先执行。把稳定的准备步骤写在链的前面，只改后面的步骤时，前面的步骤可以沿用缓存。频率是普通的非负数，内置常量方便阅读：

```ts
changeFrequency.rare     // 10
changeFrequency.normal   // 100
changeFrequency.frequent // 1000
```

Experiment、评估组、评估用例和 Sandbox Agent 的准备步骤进入同一个依赖图。每条链保持书写顺序，跨链用 `dependsOn` 或 capability 声明依赖，再按频率选择已经就绪的步骤。每个 Plugin 的准备数组单独成链，与作者 layer 之间不自动连边。

脚本超过几行时，放进独立文件，用 `script` 代替 `command`：

```ts
shell({
  id: "prepare-runtimes",
  label: "准备运行环境",
  script: new URL("./scripts/prepare-runtimes.sh", import.meta.url),
  user: "root",
  env: { CANDIDATE_VERSION: "0.20.0" },
})
```

`script` 接受模块相对的 `file:` URL，与 `command` 二选一。文件必须在项目根内；URL 不能含 query 或 fragment，symlink 也不能指向项目外。文件不存在、不可读或不是 UTF-8 文本时，运行在创建 Sandbox 前失败并指出路径。

NiceEval 在规划时读一次脚本，冻结原始内容，执行时不重读。脚本内容和 `env` 的值进入指纹；文件路径、文件名和 `label` 不进入。改一个字节会使这一步及后缀重新执行。

运行进度只显示 `label`，省略时显示 `id`。`label` 必须非空、不含控制字符，最多 256 Unicode code points。内置 action 和自定义 family 都遵守这条规则。用 `niceeval debug <experiment> <eval>` 查看完整脚本、相对路径与摘要；用 `niceeval show @<locator> --execution` 查看实际执行命令。

很短的进度更新可能被合并显示。需要分步观察时，把长脚本拆成几个有名字的 action。NiceEval 不追踪 shell 脚本内部的步骤。动态回调的进度由 `context.progress()` 自己报告。

### 声明准备缓存覆盖范围

在支持的 Provider 上，没变的准备步骤下次运行可以直接沿用，不重新执行。为此，每个 `.before(action)` 都要如实说明它会改动 Sandbox 的哪些部分：

- 不写 `cache.state` 等于 `sandboxState.all`：这个步骤的全部改动都要能被保存和恢复。它不是让 Provider 自己挑一部分目录缓存的开关。
- Incus 使用 `sandboxState.all` 保存完整准备状态，包括 VM 根盘与 Docker 数据盘。无需单独声明 Docker 数据目录。

`cache.state` 写在步骤定义处或单次调用处都可以，但只能写一处，调用处也不能覆盖定义处。

步骤的 ID、输入、展开后的命令、声明的范围和内容摘要都会被自动比较。执行内容变了，这一步就重新执行；执行顺序不变时，仅改变所属实验或声明位置不会使相同内容失去缓存。`cache.fingerprint` 只用来补充 NiceEval 看不到的版本信息，不能代替自动比较。

各 Provider 能保存的范围不同：

| Provider 情况 | 能保存的范围 | 结果 |
| --- | --- | --- |
| 本地单容器 Docker，所有改动都在外层容器的可写文件系统里 | `all` | 从头开始最长的一段没变的步骤直接沿用 |
| Incus VM，完整准备状态通过核对 | `all` | 从头开始最长的一段没变的步骤直接沿用，包含根盘和 Docker 数据盘 |
| 启用 rootfs 快照的 OpenSandbox，镜像固定到 digest，准备内容不依赖卷或 tmpfs | `all`（rootfs 文件内容） | 沿用从头开始没变的步骤，每个 Attempt 创建独立实例；进程不保存 |
| Docker Compose、E2B、Vercel 或自定义 Provider | 无 | 显示 `Unsupported`，步骤真实执行 |

沿用只能从第一步开始连续往下。遇到第一个无法保存的步骤，比如默认 `all` 但 Provider 不支持、写了 `opaque` 的回调，或者 Provider 不支持的范围，这一步和它后面的所有步骤都会真实执行。后面的步骤也不能跳过，因为它依赖的前面状态没有被保存。

在本地单容器 Docker 上，只改了最后的 `.env` 步骤时，前面固定的 Git checkout、目录上传和工具安装都不会重跑。每个 Attempt 都从缓存结果的一份独立副本启动，不会继承上一个 Agent 留下的改动。

想确认哪些步骤会沿用，运行 `pnpm exec niceeval debug <experiment> <eval>` 查看计划，见[运行前检查 Sandbox 计划](/zh/tutorials/debug-lifecycle-plan)。

### 定义可复用的准备步骤

内置的 `shell()`、`writeText()`、`uploadDirectory()` 和 `gitCheckout()` 都是 `SandboxAction`。同一类准备步骤要在多处用时，可以用相同的机制定义自己的步骤：

```ts
import { Schema } from "effect";
import {
  defineSandboxAction,
  sandboxStep,
} from "niceeval/sandbox";

const installTool = defineSandboxAction({
  id: "@acme/install-tool",
  input: Schema.Struct({ version: Schema.String }),
  cache: { fingerprint: "2" },
  steps: ({ version }) => [
    sandboxStep.exec({
      executable: "tool",
      args: ["install", version],
    }),
  ] as const,
});

const sandbox = e2bSandbox({ template: "niceeval-agents" })
  .before(installTool(
    { version: "1.4.0" },
    { changeFrequency: 20 },
  ));
```

自定义步骤只能组合 NiceEval 提供的固定操作，拿不到运行中的 `Sandbox`。上面关于缓存范围和自动比较的规则同样适用。

### 写入、上传与 Git checkout

这些内置函数可以直接传给 `.before()`：

| 内容来源 | 使用 |
| --- | --- |
| 已有文本或字节 | `writeText()` / `writeBytes()` |
| 定义文件旁边的固定文件或目录 | `uploadFile()` / `uploadDirectory()` |
| 公开 Git 仓库的固定 commit | `gitCheckout()` |
| shell 或参数列表形式的命令 | `shell()` / `command()` |

`uploadFile()` 和 `uploadDirectory()` 接收 `new URL("fixture/", import.meta.url)` 这样的地址，不接收会随当前目录变化的相对路径。文件内容、权限和目录结构都会被自动比较。`gitCheckout()` 只接受不含凭据的 HTTPS 地址和完整的 commit ID。

要等 Agent 返回后才给出的隐藏内容，不要放进 `.before()`。先用 `sandboxContent.file()` 或 `sandboxContent.directory()` 取得一个句柄，再在 `test(t)` 里调用 `t.sandbox.upload(handle, targetPath)`。句柄只带内容摘要，不暴露宿主机路径。

### 动态回调与收尾

只有运行时才能决定的分支，直接写 `.before(async (sandbox, context) => ...)`。回调每次都真实执行，它后面的步骤也不再沿用缓存。

成功取得资源后，立即用 `context.onCleanup()` 登记释放。闭包里可以直接保存这次拿到的句柄，不需要再写一个回调去猜资源状态：

```ts
const sandbox = e2bSandbox({ template: "niceeval-agents" })
  .before(async (sandbox, context) => {
    const forwarder = await startLogForwarder(sandbox, {
      signal: context.signal,
    });

    context.onCleanup(async () => {
      await forwarder.stop();
    });
  });
```

回调里的 `sandbox.sandboxId` 是当前 Sandbox 在 Provider 那边的原生 ID。一般只把它当作关联用的值，不要解析它。只有这个 layer 明确绑定了某个 Provider 时，你自己的可信代码才应该把它交给对应 SDK，去创建这个 Attempt 用的辅助资源。

这些辅助资源不归 NiceEval 管理，也不会被缓存；创建成功后必须立即登记可重复执行的清理。第一个回调开始前，NiceEval 可能换掉底下的 Sandbox 实例；回调开始之后，这个 Attempt 的清理和 `.after()` 看到的都是同一个 ID。

无论成败都要执行、而且可以重复执行的收尾，写成 `.after()`。所有登记过的收尾按登记顺序的相反顺序执行，前面的收尾失败也会继续执行后面的：

```ts
const sandbox = dockerSandbox({
  source: { type: "image", image: "node:24-slim" },
})
  .before(shell({
    id: "start-helper",
    command: "./helper start",
  }))
  .after(shell.after({
    id: "stop-helper",
    command: "./helper stop || true",
  }));
```

回调里的 `context.progress()` 只更新当前 Attempt 的临时状态，`context.diagnostic()` 保存事后需要回看的问题。环境没法继续时直接抛错，NiceEval 会把这个 Attempt 记为环境错误，而不是 Agent 做错了题。

不带 Sandbox 的 `defineAgent` 没有准备步骤。Sandbox Agent 可以在自己的 `sandbox` 字段里加 `sandboxLayer()` 形式的命令步骤，但不能选择或替换 Provider 和 template。

## 预制环境

每个 Attempt 都要下载或安装的同一份内容，如果稳定、昂贵或体积大，就把它做进预制环境，让 Attempt 直接从装好的环境启动。三种 Provider 的写法统一：

```ts
dockerSandbox({ source: { type: "image", image: "my-evals:node24" } })
vercelSandbox({ snapshotId: "snap_abc123" })
e2bSandbox({ template: "my-evals" })
```

怎样从官方基线派生镜像、快照和 template，以及怎样用运行时 checkpoint 在 Attempt 之间延续缓存，见[预制 Sandbox 环境](/zh/tutorials/prebuilt-sandbox)。

## 瞬时错误重试

OpenSandbox 创建请求不自动重试，因为连接中断时，服务可能已经分配了实例。以下创建重试适用于 Docker、Vercel 和 E2B。

内置 Provider 创建 Sandbox 时，遇到限流、`fetch failed`、连接重置、5xx、临时网络不可达这类临时失败，会自动按指数退避重试。模板不存在、凭据缺失这类配置错误第一次就报错。重试用完后，这个 Attempt 记为 `errored`。`defineSandbox` 自定义 Provider 的 `create` 是你自己的函数，NiceEval 不替它重试。

`readText`、`readBytes`、`downloadFile`、`uploadFile`、文件写入和目录上传，遇到 429、5xx、`fetch failed`、连接重置等临时传输错误时，会自动重试有限次。文件不存在、权限错误、取消和 Sandbox 已终止不重试。

`runCommand` 和 `runShell` 不自动重试，因为命令可能已经产生了副作用。只有你确认某条命令可以安全重复时，才在 hook 或评估用例里自己重试。

## 自定义 Provider

要接入其它服务，用 `defineSandbox`。你要自己负责文件系统、进程、网络和凭据的隔离，NiceEval 不会为任意一个 `Sandbox` 实现自动补上这些安全边界。

`create` 拿到的 `feedback` 用来报告创建阶段的状态，比如分配实例、拉镜像或恢复快照：

```ts
import { defineSandbox } from "niceeval/sandbox";

export default defineSandbox({
  name: "modal",
  recommendedConcurrency: 8,
  async create({ timeout, runtime, feedback }) {
    feedback.progress({ message: "分配 Modal Sandbox" });
    const instance = await allocateModal({ timeout, runtime });

    if (instance.usedFallbackRegion) {
      feedback.diagnostic({
        code: "modal-fallback-region",
        level: "warning",
        message: `主区域不可用，使用 ${instance.region}`,
        data: { region: instance.region },
      });
    }

    return new ModalSandbox(instance);
  },
});
```

返回值实现 `Sandbox` 接口即可。`recommendedConcurrency` 是没有其它设置时的默认并发数。

不要把 Provider SDK 的原始日志直接写到宿主进程的 `stdout` / `stderr`：临时状态用 `feedback.progress`，需要保留的问题用 `feedback.diagnostic`，无法创建环境时抛错。这样终端的进度面板不会被日志打乱，CI 里也只有一份有序的输出。

## 权限和执行身份

不同 Provider 对执行用户、网络、文件系统和进程生命周期的限制不同。写 Fixture 时尽量不要依赖宿主机环境，把依赖写进 `package.json` 或 Fixture 的准备步骤。

## 性能建议

- 把稳定的重依赖做进 image、template 或快照，或者写成低频的 `.before()` 步骤。
- 减小 Fixture 依赖的体积。
- 动态内容用小而明确的缓存或预先检查。
- 控制 `maxConcurrency`（Experiment 字段或 `--max-concurrency`），避免本地 Docker 资源耗尽。
- 把慢的检查拆开：必须通过的保留为 gate，可有可无的用 `.optional()`。

### 在 Attempt 之间复用 Provider 启动

在支持复用的 Provider 上，Sandbox 启动时间占了大头时，可以在 Experiment 里声明 `sandboxReuse: true`。Incus 和 OpenSandbox 不支持这项配置。多个 Attempt 会依次共用一台 Sandbox：每台只创建一次，每个 Attempt 仍然执行自己的 `.before()` / `.after()`，题与题之间工作目录会被重置。Docker 上没变的准备步骤还可以直接沿用。

```ts
export default defineExperiment({
  agent: codexAgent(),
  sandbox: e2bSandbox({ template: "acme-evals", lifetimeMs: 60 * 60_000 }),
  sandboxReuse: true,
  maxConcurrency: 3,
});
```

复用写在 Experiment 文件里，不是命令行开关：同一个实验不能临时打开或关闭。需要全新 Sandbox 做对照时，另写一个不声明复用的实验。代价、各层生命周期的执行次数和准备代码要满足的要求见[复用 Sandbox](/zh/tutorials/sandbox-reuse)。
