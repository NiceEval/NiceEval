Coding Agent 要在一个能随意改文件、跑命令的环境里工作，而且不能碰到你的机器。这个隔离环境就是 Sandbox，由 Provider 负责创建和销毁。

NiceEval 提供三种官方 Provider：本地 Docker、Vercel 和 E2B。本地调试用 Docker 最方便；需要大量并行，或者本机跑不动时，换成云端的 Vercel 或 E2B。

不管用哪种 Provider，评估用例和 Adapter 看到的都是同一个 `Sandbox` 接口。换 Provider 只改 Experiment 里的一行，评估用例不用动。

## 选择 Provider

先按你在哪里跑评估来选：

| Provider | 适合 | 需要准备 |
| --- | --- | --- |
| Docker | 本地开发和标准 CI。简单、可控，不依赖云端 | 本机 Docker。机器资源有限，冷启动和装依赖可能较慢 |
| Vercel Sandbox | 需要云端隔离、更多资源或更稳定的环境 | Vercel token 或 OIDC 配置 |
| E2B | 需要大量并行，或者想直接用现成的 Agent template | E2B 账号和 `e2b auth login` |

在 Experiment 的 `sandbox` 字段里选一个：

```ts
// experiments/local.ts
import { defineExperiment } from "niceeval";
import { dockerSandbox } from "niceeval/sandbox";

export default defineExperiment({
  agent: myCodingAgent,
  model: "claude-sonnet-4-6",
  sandbox: dockerSandbox({ source: { type: "image", image: "node:24-slim" } }), // 或 vercelSandbox({ snapshotId }) / e2bSandbox({ template })
});
```

评估用例和 Experiment 都没有选择 Sandbox 时，运行会在创建任何 Sandbox 之前报错，NiceEval 不会替你猜一个 Provider。

三个内置 Provider 的 SDK 不随 NiceEval 一起安装。用哪个就装哪个，用不到的依赖（以及它们的原生构建脚本）不会进入你的项目：

| Provider | 安装命令 |
|---|---|
| `dockerSandbox({ source: { type: "image", image: "node:24-slim" } })` | `pnpm add dockerode @types/dockerode` |
| `vercelSandbox({ snapshotId })` | `pnpm add @vercel/sandbox` |
| `e2bSandbox({ template })` | `pnpm add e2b` |

漏装时，创建 Sandbox 的那一刻会报错并给出安装命令，例如 `Docker sandbox requires 'dockerode'. Install it with: pnpm add dockerode @types/dockerode`。照着装好再运行即可。

### Docker Compose：`workspaceService` 指定主 Sandbox

一道题需要不止一个容器时（比如应用容器加一个数据库），用 `dockerComposeSandbox` 声明整份 Compose 环境：

```ts
import { dockerComposeSandbox } from "niceeval/sandbox";

sandbox: dockerComposeSandbox({
  file: new URL("docker-compose.yaml", import.meta.url),
  workspaceService: "client", // 主 Sandbox
})
```

`workspaceService` 指定 Compose 文件里哪个 service 是主 Sandbox。Agent、`t.sandbox` 的命令和文件操作、`workdir`、文件改动记录，都只落在这一个容器上。

其它 service（数据库、mock server 之类）只是陪跑的资源：不能对它们 `runCommand`、上传或读写文件，也看不到它们的文件改动。要用到它们，只能靠网络访问，例如在 `client` 容器里通过 Compose 内置 DNS 访问 `db:5432`。

### 让 Agent 自己运行 Docker

Agent 需要执行 `docker build`、`docker run` 或 `docker compose` 时，可以挂载宿主机已有的 Unix socket，也可以选择 raw privileged 或 managed rootless Docker-in-Docker。三种模式的适用场景、Dockerfile 和完整配置见[让 Sandbox 使用 Docker](/zh/tutorials/docker-in-docker)。

## 在 Adapter 和评估用例里操作 Sandbox

不管用哪种 Provider，Adapter 和评估用例拿到的都是同一个 `Sandbox` 接口。常用操作：

| 方法 | 用途 |
|---|---|
| `runCommand(cmd, args)` | 运行命令 |
| `runCommandOrThrow(cmd, args)` | 运行命令，非零退出时抛错 |
| `runShell(script)` | 运行 shell 脚本 |
| `runShellOrThrow(script)` | 运行 shell 脚本，非零退出时抛错 |
| `readText(path)` / `readBytes(path)` | 读取文本或二进制文件 |
| `writeText(path, content)` / `writeBytes(path, content)` | 写入文本或二进制文件 |
| `pathExists(path)` | 检查路径是否存在 |
| `uploadFile(source, target)` / `uploadDirectory(source, target?)` | 上传文件或目录 |
| `workdir` | Provider 里真实的工作目录。省略的 `cwd` / `targetDir` 都指向这里 |
| `runCommand(..., { cwd })` | 让单条命令在别的目录运行。相对路径按 `workdir` 解析 |
| `stop()` | 销毁环境 |

两个 `OrThrow` 方法抛出的错误消息会附带 stderr 的末尾几行，已经清理、脱敏并截断。stderr 为空时改用 stdout。排查时先看这段摘要，需要完整输出时再读 `SandboxCommandExitError.result`。

## 按顺序准备 Sandbox

Agent 开始工作前，Sandbox 里通常要先装工具、写配置、放好素材。用 `.before()` 写这些准备步骤，用 `.after()` 写无论成败都要执行的收尾。每个 Provider 函数都返回一个可以继续追加步骤的 `SandboxLayer`，追加时不会修改原来的值：

```ts
import {
  changeFrequency,
  dockerSandbox,
  shell,
  writeText,
} from "niceeval/sandbox";

const sandbox = dockerSandbox({
  source: { type: "image", image: "node:24-slim" },
})
  .before(shell({
    id: "install-tools",
    command: "corepack enable && pnpm install --frozen-lockfile",
    changeFrequency: changeFrequency.rare,
  }))
  .before(writeText({
    id: "experiment-env",
    path: ".env",
    text: "FEATURE_X=1\n",
    changeFrequency: changeFrequency.frequent,
  }));
```

`changeFrequency` 决定步骤的顺序：数值小、很少变的步骤排在前面，数值大、经常变的排在后面。这样只改了后面的步骤时，前面的步骤可以直接沿用上次的结果。它是一个普通的非负数，内置常量只是方便阅读：

```ts
changeFrequency.rare     // 10
changeFrequency.normal   // 100
changeFrequency.frequent // 1000
```

Experiment、评估组、评估用例和 Sandbox Agent 的准备步骤排进同一个顺序：先满足显式的 `dependsOn`，再按数值从小到大执行。所以评估组里很少变的步骤，可以排在 Experiment 里经常变的步骤前面。

运行时，每个准备步骤都会显示在进度里，但不会泄露内容：

- `shell()` 显示你写的 command，不显示外面包的 `/bin/sh -lc`；`command()` 和 `exec` 显示可执行文件和参数。
- `writeText()` / `writeBytes()` 只显示目标路径、字节数和摘要，不显示正文。
- 上传只显示摘要、目标路径和字节数，不显示宿主机上的源路径。
- Git checkout 的地址会去掉用户信息、query 和 fragment；环境变量只列出名字。

很短的进度更新可能被合并显示。想稳定看到一个长脚本的细粒度进度，把它拆成几个较小的步骤，并让每一步本身运行得足够久，或者自己报告进度。NiceEval 不追踪 shell 脚本内部的步骤。动态回调的进度由 `context.progress()` 自己报告。

### 声明准备缓存覆盖范围

在支持的 Provider 上，没变的准备步骤下次运行可以直接沿用，不重新执行。为此，每个 `.before(action)` 都要如实说明它会改动 Sandbox 的哪些部分：

- 不写 `cache.state` 等于 `sandboxState.all`：这个步骤的全部改动都要能被保存和恢复。它不是让 Provider 自己挑一部分目录缓存的开关。
- 只有步骤的全部改动都限于 Sandbox 里已经停止写入的 `/var/lib/docker` 时，才写 `sandboxState.dockerData`。完整的 Docker profile 示例见[让 Sandbox 使用 Docker](/zh/tutorials/docker-in-docker#managed-rootless-dind)。

`cache.state` 写在步骤定义处或单次调用处都可以，但只能写一处，调用处也不能覆盖定义处。

步骤的 ID、输入、展开后的命令、声明的范围和内容摘要都会被自动比较，任何一项变了，这一步就重新执行。`cache.fingerprint` 只用来补充 NiceEval 看不到的版本信息，不能代替自动比较。

各 Provider 能保存的范围不同：

| Provider 情况 | 能保存的范围 | 结果 |
| --- | --- | --- |
| 本地单容器 Docker，所有改动都在外层容器的可写文件系统里 | `all` | 从头开始最长的一段没变的步骤直接沿用 |
| Docker profile 配置了独立、预先分配好、固定大小的存储位和种子数据 | `dockerData` | 只沿用从头开始、连续声明了 `dockerData` 的那一段 |
| 共享 loop 或 project-quota 的 Docker profile | 无 | 显示 `Unsupported`，步骤真实执行 |
| Docker Compose、E2B、Vercel 或自定义 Provider | 无 | 显示 `Unsupported`，步骤真实执行 |

沿用只能从第一步开始连续往下。遇到第一个无法保存的步骤，比如默认 `all` 但 Provider 不支持、写了 `opaque` 的回调，或者 Provider 不支持的范围，这一步和它后面的所有步骤都会真实执行。后面的步骤即使声明了 `dockerData`，也不能跳过，因为它依赖的前面状态没有被保存。

在本地单容器 Docker 上，只改了最后的 `.env` 步骤时，前面固定的 Git checkout、目录上传和工具安装都不会重跑。每个 Attempt 都从缓存结果的一份独立副本启动，不会继承上一个 Agent 留下的改动。

想确认哪些步骤会沿用，运行 `pnpm exec niceeval debug <experiment> <eval>` 查看计划，见[运行前检查 Sandbox 计划](/zh/tutorials/debug-lifecycle-plan)。

### 定义可复用的准备步骤

内置的 `shell()`、`writeText()`、`uploadDirectory()` 和 `gitCheckout()` 都是 `SandboxAction`。同一类准备步骤要在多处用时，可以用相同的机制定义自己的步骤：

```ts
import { Schema } from "effect";
import {
  defineSandboxAction,
  sandboxStep,
} from "niceeval/sandbox";

const installTool = defineSandboxAction({
  id: "@acme/install-tool",
  input: Schema.Struct({ version: Schema.String }),
  cache: { fingerprint: "2" },
  steps: ({ version }) => [
    sandboxStep.exec({
      executable: "tool",
      args: ["install", version],
    }),
  ] as const,
});

const sandbox = e2bSandbox({ template: "niceeval-agents" })
  .before(installTool(
    { version: "1.4.0" },
    { changeFrequency: 20 },
  ));
```

自定义步骤只能组合 NiceEval 提供的固定操作，拿不到运行中的 `Sandbox`。上面关于缓存范围和自动比较的规则同样适用。

### 写入、上传与 Git checkout

这些内置函数可以直接传给 `.before()`：

| 内容来源 | 使用 |
| --- | --- |
| 已有文本或字节 | `writeText()` / `writeBytes()` |
| 定义文件旁边的固定文件或目录 | `uploadFile()` / `uploadDirectory()` |
| 公开 Git 仓库的固定 commit | `gitCheckout()` |
| shell 或参数列表形式的命令 | `shell()` / `command()` |

`uploadFile()` 和 `uploadDirectory()` 接收 `new URL("fixture/", import.meta.url)` 这样的地址，不接收会随当前目录变化的相对路径。文件内容、权限和目录结构都会被自动比较。`gitCheckout()` 只接受不含凭据的 HTTPS 地址和完整的 commit ID。

要等 Agent 返回后才给出的隐藏内容，不要放进 `.before()`。先用 `sandboxContent.file()` 或 `sandboxContent.directory()` 取得一个句柄，再在 `test(t)` 里调用 `t.sandbox.upload(handle, targetPath)`。句柄只带内容摘要，不暴露宿主机路径。

### 动态回调与收尾

只有运行时才能决定的分支，直接写 `.before(async (sandbox, context) => ...)`。回调每次都真实执行，它后面的步骤也不再沿用缓存。

成功取得资源后，立即用 `context.onCleanup()` 登记释放。闭包里可以直接保存这次拿到的句柄，不需要再写一个回调去猜资源状态：

```ts
const sandbox = e2bSandbox({ template: "niceeval-agents" })
  .before(async (sandbox, context) => {
    const forwarder = await startLogForwarder(sandbox, {
      signal: context.signal,
    });

    context.onCleanup(async () => {
      await forwarder.stop();
    });
  });
```

回调里的 `sandbox.sandboxId` 是当前 Sandbox 在 Provider 那边的原生 ID。一般只把它当作关联用的值，不要解析它。只有这个 layer 明确绑定了某个 Provider 时，你自己的可信代码才应该把它交给对应 SDK，去创建这个 Attempt 用的辅助资源。

这些辅助资源不归 NiceEval 管理，也不会被缓存；创建成功后必须立即登记可重复执行的清理。第一个回调开始前，NiceEval 可能换掉底下的 Sandbox 实例；回调开始之后，这个 Attempt 的清理和 `.after()` 看到的都是同一个 ID。

无论成败都要执行、而且可以重复执行的收尾，写成 `.after()`。所有登记过的收尾按登记顺序的相反顺序执行，前面的收尾失败也会继续执行后面的：

```ts
const sandbox = dockerSandbox({
  source: { type: "image", image: "node:24-slim" },
})
  .before(shell({
    id: "start-helper",
    command: "./helper start",
  }))
  .after(shell.after({
    id: "stop-helper",
    command: "./helper stop || true",
  }));
```

回调里的 `context.progress()` 只更新当前 Attempt 的临时状态，`context.diagnostic()` 保存事后需要回看的问题。环境没法继续时直接抛错，NiceEval 会把这个 Attempt 记为环境错误，而不是 Agent 做错了题。

不带 Sandbox 的 `defineAgent` 没有准备步骤。Sandbox Agent 可以在自己的 `sandbox` 字段里加 `sandboxLayer()` 形式的命令步骤，但不能选择或替换 Provider 和 template。

## 预制环境与运行时 checkpoint

每个 Attempt 都要下载或安装的同一份内容，如果稳定、昂贵或体积大，就把它做进预制环境，让 Attempt 直接从装好的环境启动。三种 Provider 的写法统一：

```ts
dockerSandbox({ source: { type: "image", image: "my-evals:node24" } })
vercelSandbox({ snapshotId: "snap_abc123" })
e2bSandbox({ template: "my-evals" })
```

NiceEval 不提供跨 Provider 的通用构建命令。Docker image、Vercel 快照和 E2B template 的凭据、构建方式、发布和过期规则各不相同。用 Provider 自己的官方工具维护构建脚本，把最终的 ID 或名字写进 Experiment。

### 从官方基线继续构建以提速

系统包、Agent CLI、编译好的二进制、大模型缓存这类稳定、体积大、每个 Attempt 都一样的内容，应该在跑评估之前做进 Provider 的预制环境。三个内置 Provider 都可以从官方基线继续构建，不用从空白环境装 Agent。NiceEval 只负责读取构建结果的 ID（`image` / `snapshotId` / `template`），不提供跨 Provider 的构建语法。

Adapter 和 Sandbox 各管一边：Adapter 检查需要的 CLI 在不在，Sandbox 配置选择 Provider 和预制环境。Claude Code 和 Codex 缺少 CLI 时会在运行时安装，安装包在评估网络之外准备好，通过文件接口送进 Sandbox。所以预制只是为了更快，不预制也能跑。

- Codex 送进去的是自带运行时的原生安装包，镜像里没有 Node 也能装。
- Claude Code 要求镜像里有 npm。
- 默认的 Bub 0.4.0 安装除了 OTel 插件，还固定了 `any-llm-sdk==1.17.0` 和 `openai==2.31.0`。Bub 版本、这两个依赖、OTel 插件和 Python 插件列表任何一项变了，都会重新安装，不能仅凭 `command -v bub` 判断已经装好。用旧安装标记做的预制环境会重装一次。你显式选择其它 Bub 版本时，它依赖的其它包由你自己负责。

三种 Provider 的预制环境都只在依赖变化时构建一次，每次构建换一个带版本号的名字。不要把构建放进每个 Attempt 都会执行的动态回调。

#### E2B：从官方与公共模板派生

E2B 官方提供 Claude Code 的 `claude` template 和 Codex 的 `codex` template。NiceEval 提供一个 E2B 专用的薄封装，让你从这两个官方起点继续用 E2B 原生 API 构建。E2B 没有官方的 Bub template，所以 Bub 分支和 `bubAgent()` 使用同一套固定依赖和 OTel 插件。

NiceEval 还发布了三份任何 E2B Team 都能引用的公共模板。完整的名字和版本由 NiceEval 维护，直接用常量：

```ts
import {
  NICEEVAL_CLAUDE_CODE_E2B_TEMPLATE,
  NICEEVAL_CODEX_E2B_TEMPLATE,
  NICEEVAL_BUB_E2B_TEMPLATE,
} from "niceeval/sandbox/e2b-template";

e2bSandbox({ template: NICEEVAL_CLAUDE_CODE_E2B_TEMPLATE })
e2bSandbox({ template: NICEEVAL_CODEX_E2B_TEMPLATE })
e2bSandbox({ template: NICEEVAL_BUB_E2B_TEMPLATE })
```

这些模板都实际启动验证过：Claude Code `2.1.207`、Codex `0.144.1`、Bub `0.4.0`。模板版本号跟着里面的 Agent 走，形如 `0.144.1-r1`，即 Agent 版本加 NiceEval 的构建修订号。三个 Agent 各自独立发版，和 NiceEval 库的版本无关。所以项目里直接用常量，不要复制这些字符串，也不用自己跟踪版本。派生模板需要记下基础模板时，同样用常量的值。

这批公共模板里，Claude Code 模板沿用 E2B 官方的 `/usr` npm prefix，普通用户不能直接写全局模块。运行时要再装 pnpm、yarn 等全局 Node 工具时，显式装到 `/usr/local`，两个模板都已经把它加进 PATH：

```ts
await t.sandbox.runCommand("npm", [
  "install", "-g", "--prefix", "/usr/local", "pnpm@10.34.5",
]);
```

不要改用 `sudo npm install -g`，模板里已有的 root 全局包可能产生文件冲突。NiceEval 会在之后发布的模板里统一这个默认 prefix；在发布说明明确新模板已经处理之前，继续保留 `--prefix /usr/local`。

从官方 Codex template 派生自己的模板：

```ts title="scripts/build-e2b-template.ts"
import { Template } from "e2b";
import { e2bCodingAgentTemplate } from "niceeval/sandbox/e2b-template";

const template = e2bCodingAgentTemplate("codex")
  .aptInstall(["ripgrep", "jq"])
  .runCmd("corepack enable && pnpm --version")
  .copy("fixtures/toolchain.lock", "/opt/evals/toolchain.lock");

await Template.build(template, "acme-codex-evals:0.144.1-r1", {
  cpuCount: 2,
  memoryMB: 4096,
});
```

```bash
e2b auth login
pnpm tsx scripts/build-e2b-template.ts
```

然后在 Experiment 里只引用构建结果：

```ts
import { e2bSandbox } from "niceeval/sandbox";

sandbox: e2bSandbox({ template: "acme-codex-evals:0.144.1-r1" })
```

也可以直接从 NiceEval 公共模板继续派生，只为项目自己的依赖付构建时间：

```ts
import { NICEEVAL_CODEX_E2B_TEMPLATE } from "niceeval/sandbox/e2b-template";

const template = Template()
  .fromTemplate(NICEEVAL_CODEX_E2B_TEMPLATE)
  .aptInstall(["ripgrep", "jq"])
  .runCmd("corepack enable");
```

`e2bCodingAgentTemplate("claude-code" | "codex" | "bub")` 返回 E2B 原生的 `TemplateBuilder`，可以继续用 `.aptInstall()`、`.runCmd()`、`.copy()` 等 E2B 能力。构建出的 alias 把官方起点和项目依赖固定在同一个可复现的结果里。依赖变了就重新构建，换一个带版本号的 alias。

Bub Adapter 配了 `pythonPlugins` 时，构建模板时要把同一组包传给 factory。这样运行时才会识别出插件已经预装：

```ts
e2bCodingAgentTemplate("bub", {
  bubPythonPackages: ["bub-plugin-memory==1.3.0"],
})
```

#### Docker：使用 NiceEval 维护的镜像，或从官方 node 基础镜像派生

要直接运行 NiceEval 内置的 `claude-code`、`codex` 或 `bub` Adapter，可以用对应的公开镜像：[`niceeval/claude-code`](https://hub.docker.com/r/niceeval/claude-code)、[`niceeval/codex`](https://hub.docker.com/r/niceeval/codex) 或 [`niceeval/bub`](https://hub.docker.com/r/niceeval/bub)。

每个镜像只装自己的 Agent CLI，同时提供 `linux/amd64` 和 `linux/arm64` 版本。tag 和对应的 E2B 公共模板同号，版本号是镜像里 Agent 的版本。稳定的 CI 用具名常量或 digest，不要用会变的 `latest`：

```ts
import { NICEEVAL_CODEX_DOCKER_IMAGE, dockerSandbox } from "niceeval/sandbox";

sandbox: dockerSandbox({ source: { type: "image", image: NICEEVAL_CODEX_DOCKER_IMAGE } })
```

这些是 NiceEval 维护的公开镜像，不是 Docker 的 `library/*` 官方镜像。Agent 版本或构建方式变化时才发布新 tag，和 NiceEval 库的发版节奏无关。

只需要一个 Agent，或者还要加项目自己的依赖时，写 Dockerfile 从 Docker 官方的 `node:24-slim` 派生：

```dockerfile title="Dockerfile"
FROM node:24-slim
# slim 镜像不带 ca-certificates / git，Agent 和 npm 都要用
RUN apt-get update \
  && apt-get install -y --no-install-recommends ca-certificates git \
  && rm -rf /var/lib/apt/lists/*
# npm 全局装进 /usr/local/bin，正好在 Sandbox 的 PATH 上
RUN npm install -g @openai/codex@0.144.1
```

```bash
docker build -t acme-codex-evals:0.144.1-r1 .
```

然后在 Experiment 里只引用构建结果：

```ts
import { dockerSandbox } from "niceeval/sandbox";

sandbox: dockerSandbox({ source: { type: "image", image: "acme-codex-evals:0.144.1-r1" } })
```

Docker Sandbox 用镜像自己声明的用户运行命令。上面的 Dockerfile 没写 `USER`，所以默认以 root 运行，`/usr/local/bin` 已经在 root 的 PATH 上，`npm install -g` 装的命令可以直接用。

需要非 root 用户时（比如 Claude Code 在 root 下会拒绝 `--dangerously-skip-permissions`），在 Dockerfile 里加一行 `USER node`，`node:24-slim` 自带这个用户。也可以用 `dockerSandbox({ source: { type: "image", image }, user: "node" })` 覆盖。

Agent 装到别处时（比如 `~/.local/bin`），记得把那个目录加进 PATH。`dockerSandbox` 必须写明 image，稳定的 CI 引用不会变的 tag。

#### Vercel：从官方 runtime 拍快照

Vercel 没有 E2B 那样的 template 仓库，也不用 Dockerfile。Vercel 的快照是从一台运行中的 microVM 拍下来的：用 Vercel SDK 从官方 runtime（`node24`）启动一台 Sandbox，装好 Agent CLI，调用 `.snapshot()` 拿到 `snap_...`，再交给 `vercelSandbox({ snapshotId })`：

```ts title="scripts/build-vercel-snapshot.ts"
import { Sandbox } from "@vercel/sandbox";

const sandbox = await Sandbox.create({ runtime: "node24" }); // 从官方 runtime 启动 microVM
await sandbox.runCommand({
  cmd: "npm",
  args: ["install", "-g", "@openai/codex@0.144.1"],
  sudo: true, // 全局装进 /usr/local/bin，正好在 Sandbox 的 PATH 上
});
const { snapshotId } = await sandbox.snapshot();
console.log(snapshotId); // snap_...
await sandbox.stop();
```

```bash
pnpm tsx scripts/build-vercel-snapshot.ts
```

然后在 Experiment 里引用打印出的 ID：

```ts
import { vercelSandbox } from "niceeval/sandbox";

sandbox: vercelSandbox({ snapshotId: "snap_xxx" })
```

Vercel 快照不能像 E2B 那样公开发布。快照 ID 受创建它的 Team/Project 权限控制，同一个项目的成员可以复用，其他人要在自己的 Vercel Project 里重新拍一份。NiceEval 项目自己验证过、永不过期的快照是 `snap_7sIjfs71xfmVly0WEUTGhTBoMGeL`，但它不能跨账号使用。

### 运行时 checkpoint

`createCheckpoint()` / `restoreCheckpoint()` 解决的是另一件事：把 Sandbox 里指定的 Linux 路径打包成 `Buffer`，再恢复到另一台已经创建好的 Sandbox：

```ts
import { createCheckpoint, restoreCheckpoint } from "niceeval/sandbox";

const data = await createCheckpoint(sandbox, ["/home/user/.cache/tool"]);
await restoreCheckpoint(nextSandbox, data);
```

它适合运行时的缓存，不会产生可发布的 image、template 或快照，也不管共享、版本和过期。打包或恢复失败会直接抛错。

要让这些目录在 Attempt 之间延续，在动态 `.before()` 里调用 `restoreCheckpoint()`。恢复成功后，用 `context.onCleanup()` 登记 `createCheckpoint()`，这样回存会在 Sandbox 销毁之前完成。

`sandboxReuse: true` 只在一次 `niceeval exp` 命令内部保留同一台 Sandbox。几个终端同时运行、都要读写同一份 checkpoint 时，在 Experiment 顶层声明 `sharedState: { key }`。NiceEval 在 Experiment `setup` 和创建 Sandbox 之前取得这个 key 的租约，等 checkpoint 回存、Sandbox 销毁和 Experiment `teardown` 都完成后才释放。它只保证同一时刻只有一方在用，不负责保存 checkpoint、出错回滚或跨机器协调。

## 瞬时错误重试

内置 Provider 创建 Sandbox 时，遇到限流、`fetch failed`、连接重置、5xx、临时网络不可达这类临时失败，会自动按指数退避重试。模板不存在、凭据缺失这类配置错误第一次就报错。重试用完后，这个 Attempt 记为 `errored`。`defineSandbox` 自定义 Provider 的 `create` 是你自己的函数，NiceEval 不替它重试。

`readText`、`readBytes`、`downloadFile`、`uploadFile`、文件写入和目录上传，遇到 429、5xx、`fetch failed`、连接重置等临时传输错误时，会自动重试有限次。文件不存在、权限错误、取消和 Sandbox 已终止不重试。

`runCommand` 和 `runShell` 不自动重试，因为命令可能已经产生了副作用。只有你确认某条命令可以安全重复时，才在 hook 或评估用例里自己重试。

## 自定义 Provider

要接入其它服务，用 `defineSandbox`。你要自己负责文件系统、进程、网络和凭据的隔离，NiceEval 不会为任意一个 `Sandbox` 实现自动补上这些安全边界。

`create` 拿到的 `feedback` 用来报告创建阶段的状态，比如分配实例、拉镜像或恢复快照：

```ts
import { defineSandbox } from "niceeval/sandbox";

export default defineSandbox({
  name: "modal",
  recommendedConcurrency: 8,
  async create({ timeout, runtime, feedback }) {
    feedback.progress({ message: "分配 Modal Sandbox" });
    const instance = await allocateModal({ timeout, runtime });

    if (instance.usedFallbackRegion) {
      feedback.diagnostic({
        code: "modal-fallback-region",
        level: "warning",
        message: `主区域不可用，使用 ${instance.region}`,
        data: { region: instance.region },
      });
    }

    return new ModalSandbox(instance);
  },
});
```

返回值实现 `Sandbox` 接口即可。`recommendedConcurrency` 是没有其它设置时的默认并发数。

不要把 Provider SDK 的原始日志直接写到宿主进程的 `stdout` / `stderr`：临时状态用 `feedback.progress`，需要保留的问题用 `feedback.diagnostic`，无法创建环境时抛错。这样终端的进度面板不会被日志打乱，CI 里也只有一份有序的输出。

## 权限和执行身份

不同 Provider 对执行用户、网络、文件系统和进程生命周期的限制不同。写 Fixture 时尽量不要依赖宿主机环境，把依赖写进 `package.json` 或 Fixture 的准备步骤。

## 性能建议

- 把稳定的重依赖做进 image、template 或快照，或者写成低频的 `.before()` 步骤。
- 减小 Fixture 依赖的体积。
- 动态内容用小而明确的缓存或预先检查。
- 控制 `maxConcurrency`（Experiment 字段或 `--max-concurrency`），避免本地 Docker 资源耗尽。
- 把慢的检查拆开：必须通过的保留为 gate，可有可无的用 `.optional()`。

### 在 Attempt 之间复用 Provider 启动

Sandbox 启动时间占了大头时，在 Experiment 里声明 `sandboxReuse: true`。多个 Attempt 会依次共用一台 Sandbox：每台只创建一次，每个 Attempt 仍然执行自己的 `.before()` / `.after()`，题与题之间工作目录会被重置。Docker 上没变的准备步骤还可以直接沿用。

```ts
export default defineExperiment({
  agent: codexAgent(),
  sandbox: e2bSandbox({ template: "acme-evals", lifetimeMs: 60 * 60_000 }),
  sandboxReuse: true,
  maxConcurrency: 3,
});
```

复用写在 Experiment 文件里，不是命令行开关：同一个实验不能临时打开或关闭。需要全新 Sandbox 做对照时，另写一个不声明复用的实验。代价、各层生命周期的执行次数和准备代码要满足的要求见[复用 Sandbox](/zh/tutorials/sandbox-reuse)。
