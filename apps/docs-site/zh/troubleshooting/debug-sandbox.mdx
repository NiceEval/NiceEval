Sandbox 默认在每个 Attempt 结束后销毁。大多数问题先用 `niceeval show @<attempt-locator>` 或 `niceeval view` 查看判定、断言、文件改动、命令和调用耗时瀑布图就能定位，完整路线见[排查手册](/zh/troubleshooting/debugging)。

但有些问题只能进活的环境里看：

- **环境起不来**：setup 阶段装依赖失败、agent CLI 启动不了。这时 agent 还没开始跑，对话记录是空的，最快的方式是连入现场手动重跑一遍安装命令。
- **改动落在 `git diff` 之外**：全局装了什么包、`$HOME` 下写了什么配置、`PATH` 实际是什么，工作区文件变动不包含这些内容。
- **验证假设**：冷启动加安装要几分钟。想逐条验证猜测时，留着现场敲命令比每次重跑快得多。

## 跑的时候挂起或保留现场

在 `niceeval exp` 上加 `--pause-on-failure` 或 `--keep-sandbox`：

```bash
# 失败时立即暂停并保留现场，终端等待确认后再清理
pnpm exec niceeval exp local onboarding/tool-first --pause-on-failure

# 跑完直接留下现场，事后离线排查
pnpm exec niceeval exp local onboarding/tool-first --keep-sandbox        # 等价 --keep-sandbox=failed
pnpm exec niceeval exp local onboarding/tool-first --keep-sandbox=all    # 通过的也保留
```

`--pause-on-failure` 会在发生断言失败或异常时阻断自动销毁流程，终端直接打印底层 Provider 的原生直连命令并进入等待。

留存发生时，终端收尾面板会清晰给出底层 Provider 的原生调试与清理命令：

```text
╭─ KEPT SANDBOXES ─────────────────────────────────────────────────── 1 kept ─╮
│ @0123456789ABCDEFGHJKMNPQRS  onboarding/tool-first #1  errored  docker · a3f9c2d1 │
│            debug: docker exec -it a3f9c2d1 /bin/bash                       │
│            clean: docker rm -f a3f9c2d1                                    │
╰────────────────────────────────────────────────────────────────────────────╯
```

## 使用原生 CLI 接入现场排查

NiceEval 不自建中间终端代理或二次命令封装，开发者或 AI Coding Agent 依据指引直接使用底层的成熟 CLI：

### 1. 人类开发者交互调试
直接在另一个终端窗口中执行原生直连命令：

- **单步挂起现场（`--pause-on-failure`）**：
  Sandbox 在等待确认期间仍在后台活跃运行，直连命令立即可用：
  ```bash
  # Docker Sandbox（活跃运行中）
  docker exec -it a3f9c2d1 /bin/bash

  # Instabox Sandbox（活跃运行中）
  instabox ssh niceeval-97511d9a
  ```
- **评测收尾留存现场（`--keep-sandbox`）**：
  评测结束后 Docker 会将容器挂起（`docker stop`），停用内存但完整保留磁盘文件。连入前需先将其启动：
  ```bash
  docker start a3f9c2d1 && docker exec -it a3f9c2d1 /bin/bash
  ```

进入后可直接手跑构建命令看报错、检查 `$HOME` 配置、核对环境变量与后台进程。

### 2. AI Coding Agent 自动化排查
Coding Agent 避免进入交互式 Shell，而是直接调用原生的单次非交互命令，获取结构化标准输出：

```bash
# Docker 非交互执行（若为 --keep-sandbox 留存的容器需先 docker start）
docker exec a3f9c2d1 cat /workspace/build.log

# Instabox 非交互执行
instabox exec niceeval-97511d9a -- ps aux
```

## 查看与销毁残留资源

Sandbox 的生命状态与销毁动作彻底委托给底层的成熟工具链：

```bash
# 先列出 NiceEval 容器，再检查目标的状态与 Run 标签
docker ps -a --filter "label=niceeval.keep-candidate=true"
docker inspect a3f9c2d1

# 确认所属 Run 已结束且无需保留现场后，按 ID 删除
docker rm -f a3f9c2d1

# Instabox 同样先检查，再删除指定实例
instabox list
instabox rm niceeval-97511d9a
```

`niceeval.keep-candidate=true` 在创建容器时就会设置，不表示容器已经停止或留存。标签筛选结果可能包含活跃 Run，不应直接批量删除。

原生 CLI 不加载 `niceeval.config.ts`，但仍需要可用的 Provider 连接与凭据。

## 线上 Sandbox 中断防泄漏

创建云端 Sandbox 时，NiceEval 发送服务端生命周期上限。未显式指定时，使用 Attempt 超时加 2 分钟；没有 Attempt 超时时默认 15 分钟。

本地进程遭遇断网、断电或 `kill -9` 后，服务端上限仍用于约束远端实例生命周期。到期动作和计费规则由 Provider 决定，应通过原生工具确认状态。生命周期上限与空闲自动暂停是不同机制，不能据此推断断网后会立即暂停或停止计费。
