# NiceEval

**An agent-native eval framework and Harness for your AI applications**

</div>

[NiceEval](https://niceeval.com/) is an agent-native eval framework and Harness inspired by [eve](https://eve.dev): `defineEval` makes clear what to test, while the Harness connects to the subject under test, runs it, scores it, and generates reports. Together, they form a complete loop from writing evals through inspecting results to improving your Agent. NiceEval puts developer experience first: a project can usually integrate it in about 10 minutes, eval files stay intuitive, and results stay easy to read.

It is also framework-agnostic and general-purpose. You can evaluate coding-agent plugins, Hooks, and Skills for Claude Code / Codex, or evaluate your own AI Agent application. Whether your application uses AI SDK, LangGraph, Pi, or a custom Agent loop, you can connect it through an Adapter.

As a Run proceeds, it publishes completed Attempts to the project's single Record. Use `niceeval show` for a quick review, `query` for automation, and `niceeval view` to inspect the same facts in detail, including pass rate, cost, and latency.

## Architecture

[NiceEval](https://niceeval.com/) supports two integration modes, depending on whether the subject under test needs an isolated Workspace.

### Mode 1: Sandbox

Run coding Agents such as Codex and Claude Code that need a Sandbox:

<SandboxMode />

### Mode 2: Direct

Connect directly to your own AI Agent:

<DirectMode />

- **NiceEval runner** discovers evals, schedules runs, scores them, and publishes Run and Attempt facts.
- **Agent Adapters** are the open boundary: you decide how to call the subject under test and how to map its output into the standard event stream.
- **Sandbox** provides file-system isolation: coding Agents that need a real Workspace use Docker or a cloud Sandbox. Your own web Agent can connect directly and does not need Docker.

## Core concepts at a glance

| Concept | In one sentence |
|---|---|
| [Eval](/explanation/evals) | A test case: written in `evals/*.eval.ts`, it describes what to test. |
| [Experiment](/explanation/experiment) | A checked-in run configuration: it chooses an Adapter, model, and flags. |
| [Adapter](/explanation/adapter) | The layer that connects to the subject under test: implement `send` and translate its response into the standard event stream. |
| [Sandbox](/tutorials/sandbox-providers) | Needed only for coding Agents that need an isolated Workspace. A direct web Agent does not need one. |
| [Tier](/explanation/tier) | Three investment levels for Adapter integration: Tier 1 connects only `send`, Tier 2 adds OTel for a call waterfall, and Tier 3 makes application changes for feature A/B tests. |

For the complete terminology map, see [Architecture Overview](/explanation/overview).

## Example

One eval needs two files: the eval itself (what to test) and an Experiment (which Agent to run). The CLI does not accept a bare eval id—within `niceeval exp <experiment> <eval-prefix>`, the Experiment decides which subject under test is connected. The example below is a real direct web Agent scenario. Its complete project is under `examples` / `zh` / `ai-sdk` in the repository. It verifies that an Agent calls a tool for a live weather question and answers from the result instead of inventing one:

```ts
// evals/weather-tool.eval.ts
import { defineEval } from "niceeval";
import { closedQA, includes } from "niceeval/expect";

export default defineEval({
  judge: true,
  description: "Verify that the agent calls a tool for a live weather question and answers from the result",

  async test(t) {
    const turn = await t.send("What's the weather like in Beijing today?");
    turn.succeeded().label("Turn completed");

    await t.group("Calls get_weather and answers about the weather", () => {
      t.calledTool("get_weather").label("Calls the weather tool");
      t.check(turn.message, includes("weather")).label("Describes the weather");
    });

    turn.check(
      { input: turn.input, output: turn.message },
      closedQA("Does the assistant answer using the weather data returned by the tool?").atLeast(0.7),
    )
      .gate()
      .label("Answer is grounded");
  },
});
```

```ts
// experiments/local.ts
import { defineExperiment } from "niceeval";
import { webAgent } from "./adapter"; // Your Adapter, which connects to the web Agent under test

export default defineExperiment({
  agent: webAgent({ baseUrl: "http://127.0.0.1:5188" }),
  model: "gpt-5.4",
});
```

```sh
npx niceeval exp local weather-tool
pnpm exec niceeval query discover  # Discover fixed JSON operations for AI, scripts, and CI
pnpm exec niceeval view            # Review results interactively in a browser
```

If the subject under test is a coding Agent that needs an isolated Workspace, such as Codex or a Claude Code Plugin / Skill, use `t.sandbox.uploadDirectory()` in the eval to set up the Workspace. Use attribution assertions such as `t.sandbox.fileChanged()` to check file changes, and run tests with `t.sandbox.runCommand()`. See the standalone [coding-agent-skill](https://github.com/CorrectRoadH/coding-agent-skill) repository.

## FAQ

<AccordionGroup>
  <Accordion title="Do I need to sign up for an account?">
    No. Running evals and reviewing results with `niceeval view` both happen locally. You need a Sandbox Provider such as Docker or E2B only when the subject under test needs an isolated Workspace.
  </Accordion>
  <Accordion title="My Agent is not written in TypeScript / JavaScript. Can I still connect it?">
    Yes. An Adapter sends to and receives from the interface your application already exposes—HTTP, gRPC, and WebSocket all work. [NiceEval](https://niceeval.com/) does not care which language your application uses or where it is deployed. See [Adapter](/explanation/adapter).
  </Accordion>
  <Accordion title="Can I integrate it with CI?">
    Yes. See [CI Integration](/tutorials/ci-integration).
  </Accordion>
</AccordionGroup>
